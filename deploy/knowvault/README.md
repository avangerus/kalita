# KnowVault — установка

KnowVault — поиск по документам в периметре компании: загружаете файлы,
KnowVault их индексирует и отвечает на вопросы со ссылками на источники,
не показывая ничего за пределами доступных сотруднику рабочих пространств.
Весь стек поднимается одной командой.

## Требования

- Docker и Docker Compose (`docker compose version` — v2).
- Доступ к серверу эмбеддингов и чата, совместимому с OpenAI API (LM Studio,
  Ollama, vLLM и т. п.) — KnowVault сам не считает модели, а обращается к
  уже развёрнутому серверу по адресу, который вы укажете.

## Быстрый старт

```bash
cd deploy/knowvault
cp .env.example .env
# отредактируйте .env — см. "Обязательные переменные" ниже
docker compose up -d
```

Поднимутся: журнал (PostgreSQL), векторное хранилище (Qdrant), сервис
индексации, сервис поиска и сам узел KnowVault на порту `8080` (или на порту
из `KV_NODE_PORT`).

## Обязательные переменные `.env`

Скопируйте `.env.example` в `.env` и заполните:

| Переменная | Назначение |
|---|---|
| `POSTGRES_PASSWORD` | пароль журнала событий (PostgreSQL). Задайте свой, не оставляйте значение по умолчанию. |
| `KALITA_BOOTSTRAP_SECRET` | общий секрет, которым сервисы индексации и поиска подтверждают, что они «свои», при первом запуске. Придумайте длинную случайную строку. |
| `KV_LM` | адрес сервера моделей (эмбеддинги + чат), например `http://host.docker.internal:1234` для LM Studio на хосте. |

Необязательные, но обычно стоит проверить:

- `KV_EMBED_MODEL` — модель эмбеддингов (по умолчанию
  `text-embedding-nomic-embed-text-v1.5`).
- `KV_CHAT_MODEL` — модель для ответов на вопросы (по умолчанию
  `openai/gpt-oss-20b`).
- `KV_NODE_PORT` — порт, на котором KnowVault слушает снаружи (по умолчанию
  `8080`).
- `BRAND_NAME` — имя, под которым узел представляется во внутренних
  заголовках (по умолчанию уже `KnowVault`).

## Первый вход

Создайте первого пользователя — администратора KnowVault:

```bash
docker compose exec node kalita user add --id admin --role VaultAdmin --password 'придумайте-пароль'
```

Откройте `http://localhost:8080` (или ваш `KV_NODE_PORT`) и войдите под этим
логином и паролем. Из-под администратора заведите рабочих пространства
(Workspace) и, при необходимости, остальных сотрудников:

```bash
docker compose exec node kalita user add --id anna --role VaultWorker --password '...'
```

`VaultAdmin` — полный доступ, включая настройки. `VaultWorker` — обычный
сотрудник: заводит источники и загружает документы, но не трогает настройки
KnowVault.

## Как загрузить документы

1. Войдите в KnowVault, создайте рабочее пространство (Workspace) — это
   контур видимости: документы одного пространства не видны из другого.
2. Внутри пространства добавьте источник (Source):
   - **Загрузка файла** — прикрепите документ прямо в интерфейсе, самый
     простой способ для разовых файлов;
   - **Папка** — укажите каталог через встроенный проводник (для регулярно
     обновляемого корпуса документов на сервере).
3. Индексация начинается автоматически — статус источника пройдёт
   `New → Indexing → Indexed`. Изменённые файлы переиндексируются сами,
   раз в пару минут, без ручных действий.

Для интеграций и AI-агентов то же самое доступно программно — MCP-инструмент
`knowvault.upload` (см. `packs/knowvault/product_mcp.dsl`) принимает
рабочее пространство и файл и создаёт источник тем же способом.

## Как искать

В интерфейсе KnowVault откройте экран поиска, задайте вопрос на естественном
языке — ответ приходит вместе со ссылками на конкретные фрагменты документов,
из которых он собран. Результат всегда ограничен рабочими пространствами,
доступными вошедшему пользователю — увидеть чужой периметр нельзя.

Каждый поисковый запрос фиксируется в журнале (кто спросил, из какой роли,
сколько результатов вернулось) — это неотъемлемая часть аудита KnowVault, а
не отдельная настройка.

## Бэкап и проверка целостности

Коротко:

```bash
# бэкап журнала (запускайте по расписанию, например ежедневно cron'ом)
docker compose exec postgres pg_dump -U postgres knowvault > backups/$(date +%F).sql

# проверка, что журнал не был подделан задним числом
docker compose exec node kalita verify --pub node.pub
```

`chain ok` + `checkpoints ok` в ответ на `kalita verify` означает, что история
доказуемо не переписана. Полный порядок действий — регулярность проверок,
восстановление из бэкапа, что делать при сбое — см. `docs/OPERATIONS.md`.
