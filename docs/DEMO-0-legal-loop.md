# DEMO-0 — минимальная Legal-петля (10-минутное демо пилота)

Дата: 2026-07-02. Автор: Fable. Цель: определить МИНИМАЛЬНЫЙ сквозной governed-
цикл, который доказывает продукт живому Legal-покупателю, и срез сборки под него
(из LLD-05/06 + пак legal). Дисциплина DESIGN-REVIEW A4: строим минимум, чтобы
доказать петлю, остальное — валидированный бэклог.

## 1. Петля (что показываем за 10 минут)

1. **Submit.** Человек подаёт договор (файл/текст) — через продуктовый тул
   `legal.submit_contract` (LLD-06 façade) или действие в UI. Под bearer’ом
   пользователя (pass-through), актор в журнале = человек.
2. **Периметр.** Текст договора — враждебные данные по определению (контрагент
   писал). Проходит promptbox/детектор (H4): инъекция флагуется, не исполняется.
3. **Агент.** Легал-агент (agent_runner/handle_legal, локальная модель) читает
   договор → выдаёт СТРУКТУРНЫЕ находки (риск-клаузы) → создаёт записи Finding,
   связанные с Contract, под least-privilege identity агента. **Агент НЕ может**
   сменить статус, подписать решение, прочитать чужое — движок отклоняет
   независимо от того, что вернула модель.
4. **Показ находок.** Находки видны в UI (RiskCardFace, LLD-05) и/или KChat.
5. **HITL-решение.** Человек-ревьюер одобряет/отклоняет договор — governed-переход
   с подписью (dev-подпись достаточна для демо; WebAuthn = LLD-02, НЕ демо-блокер).
   Решение журналируется, доказуемо.
6. **Гарантии на витрину.** Всё: аудит, права, откат (undo). Демо-«вау»:
   - governed: агент НАШЁЛ риски, но решил ЧЕЛОВЕК; каждый шаг в аудите;
   - безопасно: отравленный договор → агент не может само-одобрить/сменить статус
     (доказательство правами, honeypot-уровень A, H4);
   - обратимо: откат решения одной операцией.

## 2. Минимальный срез сборки (Demo-0)

**Пак legal (L2):**
- `Contract` (поля + pii-пометка на ФИО/стороны — LLD-16, но шифрование можно
  отложить за демо, пометка достаточна как заявка), `Finding` (риск, severity,
  цитата-клауза, ref→Contract).
- workflow: `Draft → UnderReview → (Approved | Rejected)`; переход в Approved/
  Rejected — под HITL(Reviewer).
- роли: `Submitter` (create Contract, submit), `LegalAgent` (least-privilege:
  read Contract, create Finding — и НИЧЕГО про статус/подпись), `Reviewer`
  (решение под подписью).
- секция `product.mcp`: `legal.submit_contract`, `legal.findings`.

**Агентный путь:** handle_legal: договор → JSON-находки (схема) → create Finding;
promptbox на входе (H4). Свободный текст агента не исполняется.

**LLD-06 (обвязка продукта):**
- PR-1 пак `assistant` (Session/Message) — governed чат-история.
- PR-2 `workers/product_mcp` façade: pass-through auth (САМОЕ важное — ревью
  Fable), читает `product.mcp` из манифеста пака, периметр на входных тулах.
- PR-3 `chat_runner` + ChatFace — KChat «проверь этот договор». Для Demo-0
  ЖЕЛАТЕЛЕН, но если дорого — демо проходит и через тул + RiskCardFace/KInbox;
  KChat = Demo-0.5.

## 3. Приёмка (доказуемо ВЖИВУЮ, не «по ощущениям»)

1. Submit договора под пользователем → Contract создан, актор=человек.
2. Отравленный договор (honeypot-корпус) → детектор флагует; агент создаёт
   Finding, но попытка сменить статус/подписать от агента → permission denied
   (показать в журнале).
3. Findings видны (RiskCardFace или KChat).
4. Reviewer одобряет → governed-переход с подписью в журнале; агент такого
   перехода сделать не мог.
5. Откат решения → компенсирующее событие, состояние вернулось.
6. `kalita verify` подтверждает цепочку офлайн.
7. Façade: тул под bearer’ом A пишет как A; без bearer → отказ; façade своего
   write-токена не имеет (pass-through, LLD-06 §1).

## 4. Что НЕ в Demo-0 (парковка)

WebAuthn (LLD-02, dev-подпись ок) · crypto-shredding (LLD-16, pii-пометка
достаточна для заявки) · federation · WASM · DR/ключи (пром) · слоёные пресеты
(LLD-19 — legal первый, machinery на втором) · полный каталог компонентов
(LLD-15 — хватит RiskCardFace/KInbox/KDetail). Всё это — после того, как петля
доказана.
