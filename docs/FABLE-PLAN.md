## 1. Архитектурный тезис Fable (рамка, в которой всё остальное)

- **Цикл, не водопад** (`ROADMAP.md`): L0 ядро+язык → L1 фронт-фреймворк → L2
  рыночные паки; каждый гэп, который вскрывает пак, течёт обратно в L0. Язык не
  проектируется до полноты в вакууме — рынок говорит, чего не хватает.
- **Четыре слоя с тестом принадлежности** (T8): **Core**(Go) — «нужно ЛЮБОМУ паку
  и не выразимо в DSL»; **Core-pack**(системный DSL) — «нужно почти каждому паку,
  выразимо в DSL» (users, справочники, нумераторы, нотификации); **Product pack** —
  «продаётся/удаляется без поломки соседей»; **Worker** — «нужен процесс, секрет
  или внешний мир». Правило против соблазна: тянет фичу в ядро «потому что так
  быстрее» — сигнал делать её паком/воркером.
- **Граница порядок/свобода** (`PORTAL-VISION.md`): портал/заявки/статусы/оплаты/
  документы — **порядок** (DSL, гарантии); витрина/лендинг/дизайн — **свобода**
  (кастомный слой поверх API). Смешивать нельзя.
- **Секреты — только на уровне node или worker**, в DSL запрещены (T0/SECURITY #5).

## 2. Что Fable ПОСТРОИЛ (фундамент — для контекста «откуда стартуем»)

- **Ядро:** event store (PG + hash-chain + immutability), durability/replay
  (100k событий ~1.07с), permission engine (default-deny, row/field-level,
  deny>allow), workflow + HITL (подпись **токеном**), automation (schedule/create/
  update/stuck; agent/notify/webhook/escalate/create/update), task-пул (lease/
  complete/fail/report_progress), MCP-шлюз (все v0-инструменты), change-pipeline
  (propose_change→validate→apply live→revert) **без рестарта**.
- **Язык:** rich-типы, serial, computed **с арифметикой**, null в выражениях,
  **rich condition language** (and/or/not/in/ref-path `project.owner`/$me/$now —
  T13 A/B/C, который он звал «критическим следующим блоком»), dashboards/aggregates
  (count/sum/avg/min/max, group by), hours/minutes_since, business-calendar
  `[код: engine/calendar.go]`, array[file], file-поля + content-addressed.
- **L1 фронт:** meta-driven UI (list/form/board/dashboard/пикеры, без билда),
  audit-timeline + diff + rewind/undo, agent-work-board, HITL-inbox с превью
  работы агента, customer-portal (invite + self-register + row-level), white-label.
- **Core-pack-сдвиги (сделаны ПОСЛЕ написания доков):** `core.User` как реальная
  built-in сущность `[код: api/coreuser.go]` (V1-GATE звал его «stub string»),
  Comment-примитив `[код: engine/comments.go]` (блокер B1).
- **Паки (dogfood):** collections, dev_department, boards/tracker, contracts,
  finance, crm, knowvault, servicedesk, eshop. ABAC two-hop ref-path.
- **APPS-GAP блокеры B1–B7 закрыты** (`APPS-GAP-PLAN.md` строка 85): comment,
  арифметика, null, dashboard, hours_since, array[file].

### 3.2 Мысли T1–T15, ещё не реализованные (`THOUGHTS-INBOX.md`)

- **T1. Telegram-коннектор 🔥** — «для RU-SMB интерфейс == мессенджер; учётная
  система с фронтом в Telegram — пустая ниша», кандидат в killer-фичу. Коннектор =
  worker-агент, клиент пишет боту → запись в kalita → статусы обратно в чат.
  `[код: отсутствует]`
- **T3. Поглощение легаси (strangler) 🔥** — наш enterprise-клин. Bridge-агенты
  читают/пишут легаси, записи зеркалятся; процессы мигрируют в DSL по одному;
  мимикрия — ВРЕМЕННАЯ фаза с записанной датой конца. Первый шаг (T11 Pain-5):
  **read-only mirror** — воркер реплицирует легаси в пак, клиент получает поиск/
  дашборды/журнал над умирающей системой без записи. Артефакт: методология +
  absorption-пак на пилоте.
- **T4. Git-экспорт/синк определений узла** в git-репо (бэкап, версии, внешний
  PR-ревью предложений) — воркер, не ядро. «Дёшево, но не раньше полигона».
- **T6.4. Экспорт чекпойнтов клиенту** («ваш нотариус»: лог не переписан) — P1,
  сильный аргумент доверия.
- **T9. Data-packs** — пак несёт не только схему, но и seed-данные с версией:
  единицы (SI), валюты ISO 4217, страны ISO 3166, таймзоны IANA. **Производственный
  календарь** по странам, обновляемый ежегодно — отдельный продукт-подписка и основа
  для business-days в SLA. Заложить формат seed-данных до маркетплейса.
- **T10. Generic journal-sink worker** — journal→Store.Since(seq)→своя БД; одна
  кодовая база, N приёмников (ClickHouse-аналитика, full-text, journal→Kafka).
- **T11. «Дёшево/мощно» (недели, не месяцы):** shadow mode → стоимость работы в ₽
  → egress-отчёт → **rationale в действиях** (act/complete несут краткое «почему» —
  журнал читается как объяснённая история). Плюс **Excel-eater** (загрузил главный
  Excel отдела → агент предлагает пак: схема+права+workflow из реальных данных) и
  **генерация README пака из DSL** (`kalita pack describe` → витрина для
  маркетплейса).
- **T12. KnowVault как «троянский» продукт 🔥** (главная стратегия продаж, фаундер
  2026-06-14): компания ставит KnowVault как приложение, не зная про kalita →
  workspaces, загрузка документов, индексация, вопросы, подключают 1С — и лишь потом
  узнают, что под капотом kalita «и можно что угодно». Нужно: (1) поставка =
  бренд KnowVault, слова kalita нет нигде; (2) продуктовый UI (поиск + RAG-ответы +
  drag-drop загрузка), универсальный UI остаётся как «Администрирование»; (3)
  **загрузка файлов в UI** в приоритет; (4) **Q&A-воркер** (search_perimeter +
  генерация ответа из VaultSettings); (5) **1С через API** (Source kind=Database +
  1С-коннектор-воркер, OData); (6) **механика reveal** («у вас уже есть kalita») —
  раздел «Автоматизация» предлагает паки/агентов поверх их данных = момент апсейла

- **T14. Портфель приложений (GTM «расселить платформу») 🔥** — очередь паков

## 4. Порядок исполнения и стратегические ворота (его слова)

- **Execution order к 1.0** (`V1-GATE`): operations → security P1 → core
  completeness → deployment product — **параллельно с пилотом**, «который сортирует
  приоритеты лучше любого плана».
- **Приоритет-правило** (`ROADMAP-TREE`): сначала всё, что нужно живому пилоту
  (знакомый с Bitrix), потом публичный рост, потом стратегические слои.
- **Kill-gate** (`BACKLOG-MVP`): +3 месяца, ноль внешних пользователей → закрыть,
  план B (видео-инциденты).
- **Две двери продаж:** дверь #1 = KnowVault-троян (T12, land-and-expand); дверь #2 =
  набор готовых паков в репо как витрина (T14, партнёры/vibe-coders разворачивают).

## 5. Opus magnum — конечная цель Fable (`APPS-GAP-PLAN` §⭐)

**«Jira, где задачи делают агенты, и ты можешь назначать задачи им».** Не новый
гэп — КОМБИНАЦИЯ всего построенного в одном приложении. Уже есть: tracker-пак,
assignee=agent, task-пул, MCP, HITL-подпись, dev_department, dogfood. Чего не
хватало для ПРОДУКТА: (a) Comment — диалог с агентом в задаче *(сделано, B1)*;
(b) report/dashboard — видеть прогресс *(сделано, B6)*; (c) **надёжный
agent-runner-воркер** (Claude Code как сервис, берёт задачи из пула и реально
делает) — воркер, не ядро *(runner.py есть; «надёжный как сервис» — открыто)*;
(d) UI-кнопка «назначить задачу агенту» (создаёт Task с assignee=agent)
*(открыто)*. Вывод Fable: opus magnum = **tracker-пак + Comment + agent-runner**,
это **СБОРКА, не новый фундамент**, делать ПОСЛЕ блокеров — «финальный dogfood:
kalita управляет своей разработкой агентами, как продукт».

## 6. Одной строкой

Fable построил **доверенный governed-рантайм с языком, MCP и UI** и дошёл до
порога продаваемости. Не успел: **операционку прода** (upgrade/backup/деструктивные
миграции), **security P1** (WebAuthn/секреты/lockdown), **deployment-продукт**
(shadow mode / стоимость-в-₽ / egress) — это его «причины покупать», — и **рыночные
доделки**: Telegram (T1), legacy-strangler (T3), data-packs/произв-календарь (T9),
WASM escape hatch, payment-воркер, KnowVault-троян (T12), очередь паков (T14),
calendar-view (T15). Стратегические слои федерации/маркетплейса/репутации —
сознательно отложены за 1.0.
