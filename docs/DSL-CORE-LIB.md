# DSL-CORE-LIB — устав и состав `dsl.core.*` (L1 стдлиб)

Дата: 2026-07-02. Автор: Fable. Родитель: LLD-19 (слои L0–L4), T8, LLD-13
(data-pack), LLD-16 (pii). Определяет ЧТО входит в `dsl.core.*`, по какому
ГЕЙТУ, и что НЕ входит.

**Опасность, которую снимает устав.** Если валить всё «общее» в core, он
раздувается и становится хрупким: ломать `core.*` = ломать все паки сразу
(LLD-19 §2). Поэтому ГЕЙТ важнее списка, а список — каталог-кандидатов, не
план стройки (DESIGN-REVIEW A4).

---

## 1. Три слоя — не путать (сортировка исходного списка)

Список «пользователи, справочники, сложные типы, права, CMS, documents,
LLM-агенты, горизонтальный сахар» смешивает ТРИ разных слоя:

- **L0 (язык/рантайм) — это НЕ `core.*`, это сам язык.** Скалярные типы
  (text/number/money/date/bool/enum/ref/file/geo), ДВИЖОК прав (ABAC deny>allow),
  движок workflow, computed, automation, event/emit, undo. → «Сложный тип
  данных», если это НОВЫЙ скаляр (geo, LLD-15) — L0 (компилятор). «Права» —
  ДВИЖОК L0; ШАБЛОНЫ ролей — L1.
- **L1 `dsl.core.*` — стдлиб.** Переиспользуемые DSL-ОПРЕДЕЛЕНИЯ из L0-примитивов:
  сущности (core.User), миксины полей, шаблоны ролей, фрагменты workflow,
  универсальные справочники.
- **L2 пресет/продукт.** CMS, документооборот, LLM-оркестрация — это ДОМЕНЫ
  (паки/продукты), НЕ core. В core уходит лишь их домен-нейтральный ПРИМИТИВ
  (Attachment, Tag, agent-role), не домен.

## 2. Гейт допуска в `core.*` (важнее списка)

Символ входит в `dsl.core.*`, только если выполнены ВСЕ четыре:
1. **Кросс-вертикальный** — нужен ≥2 НЕсвязанным вертикалям (второй потребитель
   ДОКАЗАН, не гипотеза).
2. **Стабильный** — форма не будет часто меняться (ломать core = ломать всех).
3. **Домен-нейтральный** — без отраслевой семантики (`core.User` да;
   `legal.Contract` нет).
4. **Примитив-кирпич, не решение** — строительный блок, не workflow/продукт
   (Attachment да; документооборот нет).

Не прошёл хоть один пункт → живёт в паке, пока не заслужит промоушен.

## 3. Состав `core.*` по под-namespace

Пометки: **seed** — очевидно строить (есть/ближайшее); **каталог** — кандидат,
промоушен по второму потребителю, НЕ строить наперёд.

### core.identity
- **seed:** `core.User` (есть).
- **каталог:** базовые роль-шаблоны (Owner/Approver/Viewer), `agent-role` миксин
  (identity агента + promptbox-биндинг H4 — но БЕЗ запуска LLM, тот воркер).

### core.fields — миксины полей («горизонтальный сахар»)
- **каталог:** Auditable (created/updated by·at), Assignable (owner/assignee),
  Named (name/slug), Sequenced (человеко-читаемый номер, напр. INV-2026-0001),
  Archivable (governed-архив, НЕ hard-delete), Money (amount+currency), Address,
  Period (from/to), Contact (email/phone), Pii (subject-маркер, LLD-16).
- ⚠ ~~**БЛОКЕР — см. §4:** миксины полей СЕГОДНЯ невыразимы (нет include в DSL).~~
  **РЕАЛИЗОВАНО (LLD-22, `include core.*`):** миксины полей есть, компилятор
  инлайнит их в entity (LLD-22 §2; parser.go:224-256, semantic.go:487-528).

### core.content — примитивы (это НЕ CMS)
- **seed:** `core.Comment` (есть).
- **каталог:** Attachment (file+meta, content-addressed), Tag, Category/Taxonomy,
  Note. Домен публикации/CMS = пак `site` (L2). Core даёт существительные, пак —
  глаголы.

### core.reference — справочники
- **Механизм:** обычная сущность + data-pack (LLD-13), НОВЫЙ примитив НЕ нужен.
- **Универсальные в core:** Currency, Country, Timezone, Unit, Language,
  ProductionCalendar-RU (LLD-13). Отраслевые (типы юр-документов) = пак.

### core.workflow — фрагменты
- **каталог:** типовые машины (Draft→Review→Approved→Archived), Approval-gate
  миксин (HITL-переход). Зависит от §4 (нужна композиция фрагментов).

### core.agent — тонкие конвенции
- **каталог:** паттерн task-for-agent, promptbox/периметр-контракт (H4),
  born-agentic-триггер. **Запуск LLM = воркер (T8), НЕ core.** Полноценная
  LLM-оркестрация/чат = пак `assistant` (LLD-06), это L2.

### core.notify — уведомления (проходит гейт §2: кросс-вертикально, стабильно,
домен-нейтрально, примитив). **seed-кандидат, строить потом.**
Горизонталь для всех: событие → канал → шаблон → настройка. Состав:
- **Notification** — примитив-факт `{recipient, channel, template, payload}`.
  Порождается из `after`-хука/handler'а: `after approve: notify(user, "…")`.
- **Канал** — pluggable адаптер (email/telegram/in-app). Core задаёт КОНТРАКТ
  канала; доставка внешним каналом = **воркер** (T8), не ядро.
- **Шаблон** — декларативный (текст + подстановки из payload).
- **Настройка** — предпочтения получателя (какой канал, opt-out) на роль/юзера.
- **Два вида, не путать (как факт vs сигнал):**
  - **in-app** — просто факт в журнал + `view` (базовый, синхронно, без егресса);
  - **внешний** (email/telegram) — это **ЕГРЕСС**: домен в whitelist (SECURITY
    правило 3), доставка **durable** через обвязку LLD-21 (at-least-once, не
    fire-and-forget). Extended.
- Ревью Fable при постройке: внешняя доставка = егресс + durable (не «дёрнул SMTP
  и забыл»). Отдельный LLD когда строим (триггер — второй потребитель после Legal).

## 4. ЯДРОВЫЙ ГЭП: нет механизма миксинов (пак вскрыл ядро)

> **Статус: РЕАЛИЗОВАНО (LLD-22, 2026-07-06)** — `include core.<Mixin>` в
> начале тела entity; компилятор инлайнит поля миксина до всех семантических
> проверок (parser.go:224-256, semantic.go:487-528, mixinRegistry в core.go).
> Текст ниже — история вскрытия гэпа, оставлен как есть.

Проверено: DSL не имеет `include`/`mixin`/композиции-в-сущность. Следствие:
- **Переиспользование СУЩНОСТИ** (core.User, Comment, Attachment) — работает
  СЕГОДНЯ через ref/compose.
- **Переиспользование ГРУППЫ ПОЛЕЙ** (Auditable-таймстампы, Money=amount+currency,
  Address вложенно) — **НЕВЫРАЗИМО:** это поля НА хосте, не отдельная сущность.
  Без include весь «горизонтальный сахар» (§core.fields) нереализуем — каждый
  пак копипастит `created_at/by`.
- **Решение (нужно, L0-фича):** композиция полей — `entity Contract { include
  core.Auditable, core.Money }`, компилятор инлайнит поля миксина. Аддитивно
  (I-1), но это ЯЗЫКОВАЯ фича L0 → ревью Fable, отдельный LLD когда строим
  §core.fields (триггер — второй потребитель сахара). До этого `core.*` = только
  entity-by-ref, без миксинов.

Это ровно метод «пак вскрывает недостающий примитив ядра»: список «сахара»
обнажил отсутствующую композицию полей.

## 5. Дисциплина роста

`core.*` стартует МАЛЫМ: User, Comment (есть) + Attachment/Tag/Auditable
(очевидные ближайшие, Auditable — после §4). Остальное — каталог, промоушен
строго по второму потребителю (LLD-19 §2), не наперёд (DESIGN-REVIEW A4).
Универсальные справочники — как core data-packs (LLD-13).

## 6. Что НЕ в `core.*` (явно)

CMS/публикация (пак `site`) · документооборот/RAG (KnowVault) · LLM-оркестрация/
чат (пак `assistant`, LLD-06) · отраслевые справочники и сущности · любой домен
с бизнес-семантикой. В core — только их домен-нейтральный примитив, если он
проходит гейт §2.
