# Kalita Next — архитектурная база N1

**Дата:** 2026-10-07. **Статус:** проект для планирования; реализация и коммерческая готовность не заявлены. Кодовая база: `main`, HEAD `67f3587fbcebeb552be9f3debcb30efd7e494608` плюс существующие локальные изменения. Состояние кода описано отдельно в [AS_IS.md](AS_IS.md).

Kalita развивается в корпоративную среду совместной работы человека, агентов и данных: человек задаёт цель и пределы, агенты выполняют ограниченную работу, компания сохраняет полномочия, историю ответственности и результаты. Чат и представления — способы доступа; смысл работы существует независимо от них.

## Порядок чтения и авторитет документов

1. [PRODUCT_CONTRACT.md](PRODUCT_CONTRACT.md) — кому нужен продукт, какую работу он улучшает и как проверять ценность.
2. [HLD.md](HLD.md) — границы системы, компоненты, данные, инварианты и отказы.
3. [DECISIONS.md](DECISIONS.md) — решения N-ADR, альтернативы, статус и явно заменённые старые правила.
4. [GLOSSARY.md](GLOSSARY.md) — единый словарь.
5. Детальные контракты LLD и [Client Delivery](packs/CLIENT_DELIVERY.md).
6. [ROADMAP.md](delivery/ROADMAP.md) → [RELEASES.md](delivery/RELEASES.md) → [ITERATIONS.md](delivery/ITERATIONS.md) → [TASKS.md](delivery/TASKS.md).
7. [TRACEABILITY.md](TRACEABILITY.md), [REVIEW.md](REVIEW.md), [VALIDATION.json](VALIDATION.json) — связь требований, задач и документальной проверки.

Для новой разработки действует порядок: **PRODUCT_CONTRACT → HLD → принятые N-ADR → LLD → pack → delivery tasks**. Изменение верхнего контракта сначала отражается в решении и зависимых документах. Решение со статусом `provisional` допускает только оговорённый эксперимент, не снимает инвариант безопасности. Задача не может молча расширить HLD.

N1 заменяет целевые правила прежних HLD/roadmap только в областях, перечисленных в [DECISIONS.md](DECISIONS.md). Существующие DSL grammar, API текущей версии, журнальные форматы и release evidence сохраняют силу для выпущенных/существующих реализаций. Новые типы и `/api/next` не становятся существующими API от публикации этих документов. Исторические отчёты не переписываются как доказательства новой архитектуры.

## Как пользоваться планом

Единственный машинный каталог задач — [TASKS.json](delivery/TASKS.json); Markdown-каталог создан из него. R0–R7 — плановые release gates, не Git tags и не версии уже выпущенного продукта. I00–I15 — ограниченные итерации, не обещание календарных сроков. Все implementation tasks имеют статус `planned`; утверждение документов не означает прохождение их проверок.

Первый поддерживаемый путь: один процесс одной компании, два реально выбранных источника, подтверждаемые обязательства и очередь. После доказательства ценности добавляются ограниченные действия, выразительные представления, проверяемые методы и эксплуатационная повторяемость. Новые отрасли и межорганизационная работа включаются по отдельным gates.

## Основания и ограничения

Исходная критика Astra/high выполнена **до** составления N1; её выводы и последующая проверка перечислены в [REVIEW.md](REVIEW.md). Исследования [starter packs](../research/STARTER_PACK_SELECTION.md) и [future-2036](../research/future-2036/SYNTHESIS.md) дают гипотезы для выбора, а не измеренное подтверждение рынка. Набор сценариев 2036 — качественная проверка вариантов, не вероятностный прогноз.

Открытые решения имеют владельца, эксперимент и stop condition в I00; они не скрыты за словом «архитектура». Без доступа к реальной первой компании нельзя считать выбранными её источники, экономику и допустимый deployment.
