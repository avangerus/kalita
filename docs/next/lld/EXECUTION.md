# Execution runtime — LLD

**Статус:** проектная спецификация; не является описанием уже реализованной функции.  
**Область:** долговечное выполнение бизнес-процессов и задач в одной инсталляции Kalita.  
**Соседние документы:** `WORK_MODEL.md`, `INTEGRATIONS.md`, `EXPERIENCE.md`, `VIEWS.md`, `OPERATIONS.md`; обзор и решения — [HLD](../HLD.md), `DECISIONS.md`.

## 1. Цель и границы

Исполнение должно переживать рестарты и повторную доставку, сохранять авторство и причинную связь, а также безопасно продолжаться при изменении прав и версии модели. Журнал фактов бизнеса остаётся append-only источником бизнес-истории. Отдельные операционные таблицы исполнения становятся источником истины для `Run`, `Attempt`, `Lease`, `Grant`, бюджетных резервов и статуса внешнего эффекта. Проекция может быть перестроена, но намерение отправить письмо, удержание бюджета или факт неизвестного исхода внешнего вызова не выводятся из бизнес-проекции.

Первая версия ограничена одним PostgreSQL deployment, существующими Go DSL-сущностями, workflow, ABAC и моделью задач. Python worker остаётся исполнителем одной задачи за раз; он не владеет бизнес-состоянием и не получает долгоживущих credentials. Это не универсальная BPM-платформа и не новый язык workflow. Workflow DSL задаёт состояния, переходы, guards и назначение; адаптер отвечает за долговечную оркестрацию уже описанных шагов.

Перед началом реализации нужен короткий gate I00: на реальном сценарии сравнить PostgreSQL-адаптер с Temporal по crash recovery, повторным эффектам, восстановлению оператором, сложности on-prem эксплуатации и объёму нового кода. Gate документирует критерии, сценарии отказа и решение. Базовый вариант этого LLD — один встроенный PostgreSQL durable execution adapter: данные уже рядом с журналом, транзакции доступны на узле, остаётся один поддерживаемый installation profile (Go control plane, PostgreSQL, executor/broker). Для deployment разрешён ровно один execution adapter. Нельзя одновременно вести одну задачу в локальном адаптере и Temporal или автоматически переключать источник истины после ошибки. При выборе Temporal этот LLD требует пересмотра границ транзакций и восстановления; два конкурирующих адаптера не поддерживаются.

## 2. Источники истины и модель выполнения

`Run` — конкретное исполнение workflow для бизнес-объекта, включая `run_id`, `object_ref`, `workflow_id`, закреплённые `definition_version` и `schema_version`, инициатора, родительский run, correlation/basis, дедлайны и итог. Создание запуска идемпотентно по `(tenant, idempotency_key)` с привязкой к хешу canonical request: повтор того же запроса возвращает тот же run, несовпадающий payload даёт conflict.

`Attempt` — один ограниченный интервал работы над step. Он имеет монотонный `attempt_no`, `lease_owner`, случайный `lease_token`, возрастающий `fence`, `leased_until`, heartbeat, начало/конец и классифицированный результат. Повтор step создаёт новую попытку, не перезаписывает прошлую. Lease ограничивает право записывать результат; токен fencing не позволяет старому worker завершить задачу после перевыдачи lease. Для живого lease продление требует совпадения `run_id`, `step_id`, `attempt_id`, `lease_token` и `fence`.

Состояния run: `queued`, `running`, `waiting_approval`, `waiting_retry`, `succeeded`, `failed`, `cancel_requested`, `cancelled`, `blocked`. Состояния попытки: `leased`, `running`, `completed`, `failed`, `expired`, `cancelled`. Внешний эффект имеет собственную машину состояний: `prepared`, `dispatching`, `succeeded`, `failed`, `unknown`, `reconciling`. `unknown` означает, что запрос мог быть принят удалённой системой, а локальное подтверждение потеряно; это не обычная ошибка и не разрешение на слепой повтор. Терминальные статусы не меняются задним числом: исправление оформляется отдельным событием/операцией reconcile.

Переходы бизнес-сущности и события результата фиксируются по существующему контракту журнала. Операционная транзакция адаптера атомарно пишет ledger, необходимое canonical journal event и outbox. Outbox доставляет уже принятое событие в projections/notifications после commit; он не заменяет атомарность ledger + journal. Нельзя предполагать, что текущий `Append` и обновление проекции уже атомарно компонуются с новыми таблицами: интерфейс транзакции должен быть спроектирован и реализован явно. Сбой проекции после commit восстанавливается повторным чтением outbox; повторная обработка события дедуплицируется по стабильному `event_id`.

## 3. Транзакционные правила

Каждая команда изменения execution state выполняется в одной PostgreSQL-транзакции с блокировками в фиксированном порядке: `root budget/authority row` → упорядоченные `domain aggregate/run rows` → `step/effect row` → `attempt row` → append журнал-события/outbox. При операции без бюджета пропускается первый ряд. Код не должен брать эти блокировки в обратном порядке. Операции, нуждающиеся в нескольких runs, сначала сортируют ключи и блокируют в одном порядке. Уровень изоляции и retry на serialization/deadlock — контракт адаптера; сетевые вызовы запрещены внутри транзакции.

Создание child и его ограничений атомарно относительно корневого budget/authority row. До commit проверяются лимиты числа детей, глубины, срока и допустимого subtree ceiling. Child ceiling ограничивает ту же сумму расходов и не резервирует её второй раз. Перед каждым платным call/effect отдельно резервируется worst-case amount под root lock: доступный остаток уменьшается, reservation увеличивается вместе с durable intent. spent + unresolved call reservations не превышают root hard cap; subtree counters ограничивают тот же расход. Неиспользованный child ceiling не считается списанием. Завершение эффекта переводит резерв в списание или освобождение идемпотентной операцией settlement. При неизвестном исходе эффект удерживает резерв, пока reconcile не подтвердит успех или отказ. Лимит бизнес-действий (например, максимальная сумма платежа) отделён от вычислительного бюджета, лимита попыток, rate limit и кредитного остатка: один показатель не может подменять другой.

Hash-chain журнала требует глобального упорядочивания append-операций. Если append сериализуется глобальным lock/advisory lock, execution-транзакция берёт его после строковых блокировок в указанном порядке; любой существующий путь, берущий журнал раньше этих строк, должен быть приведён к тому же порядку; отдельная outbox транзакция допустима лишь для производной доставки после canonical commit. Это обязательное решение протокола, а не деталь реализации: иначе конкурирующий reserve/append может образовать deadlock. Нельзя удерживать глобальный журнал lock во время вызова брокера или внешней сети.

## 4. Получение задачи, heartbeat и fencing

`claim` атомарно выбирает готовую задачу с учётом schedule, отмены, права исполнителя и лимита параллелизма, увеличивает fence/attempt number, записывает lease и выдаёт одноразовый token. Выбор использует `FOR UPDATE SKIP LOCKED` или эквивалент с явным доказательством отсутствия двойной выдачи. `claim` возвращает ограниченный пакет заданий, а не неограниченный список. Рабочий регулярно вызывает `heartbeat`; истёкший lease переводит попытку в `expired`, а дальнейший `complete` со старым токеном получает `stale_lease` и не меняет состояние.

Перезапуск не считает истёкший lease доказательством отсутствия эффекта. Для чистого вычисления можно безопасно выдать новую попытку. Если step объявляет внешний эффект, адаптер сначала читает состояние `Effect` и endpoint-specific idempotency receipt. Продление lease и отмена сериализуются с финализацией попытки. Heartbeat истёкшего lease не оживляет его. Worker может завершить только свою текущую попытку, с правильным fence и неизменной версией step contract.

Псевдопротокол:

```text
POST /api/next/worker/claims
  -> {attempt_id, lease_token, fence, leased_until, input_ref, contract_version}
POST /api/next/attempts/{attempt}:heartbeat
  {lease_token, fence, progress?} -> {leased_until}
POST /api/next/attempts/{attempt}:complete
  {lease_token, fence, outcome, output, basis} -> {run_state, event_id}
```

`progress` — короткие безопасные метаданные, не stdout/stderr или секреты. Вход и выход проходят размерные лимиты и typed schema validation. Неподдерживаемая версия контракта не должна молча исполняться старым worker: задача блокируется с диагностикой совместимости.

## 5. Ошибки, retry и отмена

Retry policy задаёт владелец workflow: допустимые классы ошибок, backoff, jitter, deadline, максимальное число попыток, лимит времени и поведение после исчерпания. Случайная ошибка сети не становится автоматически retryable для внешнего side effect. Ошибка до dispatch может быть безопасно повторена; ошибка после dispatch требует receipt/reconciliation либо подтверждённого endpoint idempotency. Нельзя считать idempotency нашего API доказательством идемпотентности удалённой системы.

Отмена является запросом, а не стиранием истории. `cancel_requested` прекращает новые claims, сигнализирует живым workers и блокирует необязательные будущие эффекты. Попытка может быть `cancelled`, если она ещё не отправила эффект. При уже отправленном/неизвестном эффекте run остаётся `cancel_requested` или `blocked` с явной причиной до завершения либо reconcile. Отмена не отзывает уже совершённое действие и не может ретроспективно отменить внешний перевод/письмо.

DLQ — классифицированное состояние для операторского разбора с `failure_code`, безопасным кратким контекстом, retry count и ссылками на basis. Replay из DLQ создаёт новую попытку; он не удаляет историю, не сбрасывает бюджет без явного ledger settlement и не пропускает повторную авторизацию. Операторское ручное разрешение фиксирует actor, причину, снимок контракта и выбранный результат.

## 6. Детерминизм и совместимость

При старте run закрепляются версия определения и схема. Исполняемый step не должен при каждом retry заново интерпретировать новый definition как будто это тот же договор. Политика обновления модели задаёт: продолжить по закреплённому шагу, безопасно остановить до следующего шага либо пройти явную migration/rebase-процедуру. Новая версия workflow не переписывает старые run автоматически.

Входные данные для повторяемых решений фиксируются ссылками на версии/события, а time/random/unique IDs поступают через явные детерминированные параметры адаптера. Чтение «последнего текущего значения» при replay может изменить решение, поэтому оно либо снапшотится в basis, либо объявляется внешним observation с временем и авторитетом. Повторное воспроизведение реконструирует orchestration decisions; оно не повторяет side effects. Сырые model output не являются правдой бизнес-журнала. Записать можно валидированный outcome, источник и provenance согласно retention policy.

## 7. Переход от текущей task pool

Миграция сохраняет задачи, task IDs и совместимые read-сценарии `/api/tasks`/MCP. Write workers обязательно обновляются до Attempt ID/token/fence; старый completion по actor ID запрещён, поскольку запоздалый ответ того же actor неотличим от новой попытки. Старые writers дренируются/останавливаются до переключения. Перед запуском измеряются незакрытые задачи, владельцы, lease-поля, исторические completion и дубликаты. Legacy task преобразуется в run/step только после явного отображения типа задачи, caller/owner, разрешённых действий и retry-семантики. Неизвестная авторизация или неоднозначный результат остаются в `blocked`/manual review, а не получают новые права по умолчанию.

Порядок включения: добавить таблицы/индексы и dual-read наблюдение без двух активных writers; импортировать активные задачи идемпотентно; сверить количества и выборочные хеши/ссылки; переключить claim одного deployment feature flag; сохранить совместимые read-ответы через фасад и требовать новый fencing protocol для writes; затем отключить старый внутренний claim путь только после измеренного отсутствия legacy writers. Rollback приложения не должен уничтожать новые execution rows: временно возвращается совместимый reader/операторский режим, а не второй dispatcher. Удаление старых данных не входит в миграцию.

### Минимальные критерии приёмки

- Два параллельных claim не получают одну и ту же attempt; старый worker не может завершить задачу после fencing.
- Рестарт на каждом commit boundary восстанавливает queued, leased, retry и waiting approval без потери причинной ссылки.
- Сбой после dispatch и до receipt переводит effect в `unknown`, сохраняет резерв и требует reconcile/idempotency до повтора.
- Повтор idempotency key с тем же телом возвращает исходный run; иное тело получает conflict.
- Отмена до dispatch блокирует effect; отмена после dispatch не обещает отозвать внешний результат.
- Конкурентные child run не превышают общий reserve, attempt budget или глубину delegation.
- Replay не пересылает письма и не применяет новый definition к старой попытке без явного rebase.

Матрица crash points и тестовые сценарии подлежат реализации вместе с адаптером. Настоящий документ не утверждает, что эти проверки уже выполнены.

## Ресурсные границы и agent loop

Для hard monetary budget каждый model/tool call имеет enforceable maximum input/output/duration и pricing revision. Worst-case reserve создаётся до call; unknown billing сохраняет резерв. Provider без доказуемого bound доступен только как явно soft estimate вне hard mode. Actual > bound — incident с блокировкой новых calls до проверки. Child ceiling не складывается второй раз с call reserves; единственный root ledger считает spent + unresolved reservations, а subtree counters ограничивают ту же сумму. Каждый reservation имеет logical key и одно settlement.

Durable agent decision loop, ограниченные plan revisions, model call intents/checkpoints и termination описаны в [AGENT_PROTOCOL](AGENT_PROTOCOL.md). Run может включать утверждённые dynamic steps в ResponsibilityContract; изменение цели/grant не является обычным plan patch.

### Admission barrier: committed heads и актуальные проекции

Async projection не разрешает admission по устаревшему owner/criteria/ACL. В каждой Tx business mutation обновляет durable aggregate_head (revision, last_event_seq) и затронутые authority/policy heads вместе с canonical event. Heads — consistency metadata журнала, не независимый writer бизнес-значений. Все legacy business writes в N1 соблюдают этот контракт. Guard/If-Match/ABAC используют consistent projection snapshot с applied heads; под соответствующими authority/domain head locks в Tx сравниваются durable revisions. При отставании admission ждёт ограниченное время или возвращает projection_not_ready/fail closed, не вычисляет разрешение по старому owner. Protected reads/context выдаются только после такой freshness barrier для данных и ACL. Ответ содержит applied revision; stale projection не выглядит актуальной. Новое изменение после read всё равно проверяется при mutation/dispatch.

Проверка: A commits owner/criteria rev11, projection apply падает; B с rev10 и старым owner пытается read/If-Match command. Ни защищённый контент, ни команда по старой authority не проходят. Rebuild/outbox догоняет heads, затем admission разрешается на rev11. Если dependency ACL heads нельзя полно описать, deployment использует консервативную общую projection barrier; ускорение допустимо лишь после доказательства эквивалентности. Lock order authority heads → domain heads/run → step/effect → attempt → journal head сохраняется.
