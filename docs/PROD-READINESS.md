# PROD-READINESS — разбор готовности к промышленной эксплуатации (day-2)

Дата: 2026-07-02. Статус: проект для обсуждения. Второй слой поверх RELEASE-1.0.
Опирается на: SECURITY.md (threat model T1–T6, гэпы P0/P1/P2), EVENT-STORE-v0
(§3 чекпоинты/якорь, §6 забвение), RELEASE-1.0 (N1–N11), HLD-V1 (I-1..I-6).

## 0. Рамка

RELEASE-1.0 отвечает на «узел ПЕРЕЖИВЁТ год чужими руками» на уровне ФИЧ и
ЦЕЛОСТНОСТИ. Этот документ — про **day-2**: что происходит, когда узел уже
живёт в контуре клиента и начинаются будни — бэкапы, диски, ключи, инциденты,
регулятор, удаление персональных данных. Это НЕ дубль N-точек: где день-1
(N*) закрывает механику, день-2 (O*) закрывает эксплуатацию этой механики.

«O-точка» = место, где законное эксплуатационное/регуляторное требование
сталкивается с уже принятым инвариантом ядра (чаще всего с append-only I-1 или
доказуемостью I-5). Нумерация O*, чтобы не путать с релизными N*.

Секции SECURITY.md уже закрыли P0 (TLS, dev-headers, CORS) и назвали P1/P2 —
здесь они разбираются как напряжения с решением, а не списком.

## 2. Разбор точек

### O1. Право на забвение — crypto-shredding (→ LLD-16)
**Напряжение (острейшее для юр-ICP).** Вся ценность — вечный доказуемый журнал
(I-1/I-5). Но договор/резюме/жалоба содержат перс.данные, и 152-ФЗ/GDPR дают
субъекту право на удаление. Физически стереть событие = сломать hash-цепочку =
убить доказуемость всего журнала. Прямое противоречие двух обещаний.
**Решение (зарезервировано EVENT-STORE §6).** Чувствительный payload шифруется
ключом НА СУБЪЕКТА; удаление = уничтожение ключа: данные нечитаемы, а hash-цепочка
цела (хэш считается по шифртексту). Слот в схеме уже есть: `payload {encrypted:
true, key_id}`. Детали (что шифруется, поведение проекций после шреддинга,
offline-verify, маппинг на 152-ФЗ) — LLD-16. Это P2 SECURITY #8, но для Legal-
пилота с перс.данными — поднять приоритет.

### O2. Backup / DR (→ LLD-17)
**Напряжение.** N3 упомянул `pg_dump` для upgrade, но это не DR. Прод требует:
RPO/RTO, регулярный бэкап, ПРОВЕРКУ бэкапа (untested backup = отсутствующий),
шифрование бэкапа (в нём перс.данные), и СОГЛАСОВАННОСТЬ трёх хранилищ — журнал
(PG) + файлы (content-addressed blob) + ключи (шреддинг-ключи O1, ключ узла).
Восстановить журнал без файлов/ключей = битые ссылки и нечитаемые payload.
**Решение.** Бэкап-набор как единица (журнал+файлы+манифест ключей на момент),
restore-учение в DoD, шифрование бэкапа, точка согласованности = seq+checkpoint.
LLD-17.

### O3. Внешний якорь чекпоинтов (→ LLD-17)
**Напряжение.** Чекпоинт подписан ключом УЗЛА (EVENT-STORE §3). Против инсайдера
с доступом к PG (T4) это ловит переписывание — НО если скомпрометирован сам узел/
оператор, он мог пере-подписать. Регулятору/страховщику нужно доказательство,
не зависящее от нашего узла.
**Решение.** Экспорт чекпоинта во ВНЕШНИЙ якорь: клиентский офлайн-бэкап (уже
можно), опц. RFC-3161 TSA (доверенная метка времени) или нотариус-хэш. Якорь —
декларативный конфиг (какой якорь, как часто), само событие якоря в журнале.
SECURITY P2 #9. LLD-17.

### O4. Секреты и ключи: хранение, инъекция, ротация (→ LLD-18)
**Напряжение.** SECURITY P1 #5: PG DSN в env/.env — нужен конфиг-файл 0600 +
docker secrets. Глубже: ключ УЗЛА подписывает чекпоинты — его ротация не должна
рвать проверяемость старых чекпоинтов (I-5). `actor.key_rotated` в taxonomy уже
есть для акторов; для узла нужна эпоха ключа: verify выбирает ключ по эпохе
события. Плюс инъекция секретов в воркеров (I-4: секрет только node/worker) без
утечки в журнал/DSL.
**Решение.** Key-lifecycle: конфиг-файл 0600/docker-secrets; событие ротации
ключа узла с overlap-периодом; verify по эпохам ключей; контракт инъекции
секрета воркеру. LLD-18.

### O5. Наблюдаемость (спека §ниже, LLD позже)
**Напряжение.** Есть /healthz,/readyz. Прод требует метрик (мутаций/с, p99,
глубина очередей HITL/task, лаг automation, ошибки-события N2, replay-время),
структурных логов и АЛЕРТОВ — но SECURITY правило 6 запрещает внешние SaaS.
**Решение (secure-by-perimeter).** `/metrics` в формате Prometheus, скрейпится
СТЕКОМ В КОНТУРЕ клиента (их Prometheus/Grafana или наш on-prem образ) — ноль
внешних зависимостей. Дашборд узла показывает «красные состояния»: незакрытые
op-скобки (N2), inconsistent-записи, automation.abandoned, очередь подписей >
порога, приближение к disk/replay-порогам (O8/N9). Структурные логи (JSON) в
stdout — оператор направляет куда хочет. Полноценный LLD — при первом клиенте с
их observability-стеком (правило второго потребителя). НЕ тащить трейсинг в 1.0.

### O6. Конфигурация узла (спека §ниже)
**Напряжение.** Флаги расплодились (--tls-*, --insecure-*, --require-human-
signature, --map-tiles, egress, DSN…). Риск: небезопасный дефолт срабатывает
МОЛЧА (напр., забыли подпись — прод принимает токен-approve).
**Решение (fail-fast, secure-by-default).** Единая валидируемая конфиг-модель
(файл + env + флаги, приоритет фиксирован); валидация ПРИ СТАРТЕ — узел
отказывается стартовать в небезопасной комбинации (non-loopback без TLS уже
так — распространить: прод-профиль требует подписи, локальную модель, egress-
whitelist). `kalita config check` печатает эффективную конфигурацию и
предупреждения. Дефолты безопасны; небезопасное — только явным флагом с
warning (паттерн --insecure-* уже есть). Спека — раздел деплой-гайда; отдельный
LLD не нужен, если N11-гигиена включит config-check.

### O7. Воркеры в проме — супервизия и blast-radius (спека §ниже)
**Напряжение.** T8: воркеры (agent_runner, connectors, bridge, chat_runner,
product_mcp) — вне ядра, ядро их НЕ супервизит. В проме упавший/зависший/
устаревший воркер = тихо не выполненная работа (эскалация, синк, коннектор).
**Решение.** Контракт воркера: (1) health-эндпоинт/heartbeat-событие; (2)
ресурс-лимиты и рестарт — на слой процессов (docker restart/systemd), НЕ в
ядро (граница T8 цела); (3) версия воркера в его heartbeat, дашборд ловит
рассинхрон версий; (4) blast-radius: воркер под least-privilege identity (уже
паттерн inbound.py/bridge) — упавший/взломанный воркер ограничен своими правами
(I-2). Гайд воркера (N11) фиксирует контракт. Ядро остаётся простым (не
оркестратор). Полный LLD — если появится потребность в узловом супервизоре
(пока — процессный слой достаточно).

### O8. Исчерпание ресурсов (спека §ниже, стык N9)
**Напряжение.** T6 (DoS): журнал append-only и файлы растут ВЕЧНО; лимитов мало.
Прод: диск переполнится за годы; большой файл/запрос/каскад может положить узел.
**Решение.** Лимиты входа: размер запроса, размер и число файлов на запись,
глубина каскада (N2 плоско), rate-limit (N7). Disk-watermark: алерт на дашборде
при N% (стык N9 tiered-порога) → оператор архивирует старые партиции/эры (N3
export). Файлы — GC осиротевших блобов по журналу. Backpressure: при близком
исчерпании узел деградирует к read-only с явным событием, а не падает молча
(дух I-3). Спека — раздел деплой-гайда + пороги в паспорте (N6).

### O9. Data residency (спека §ниже)
**Напряжение.** 152-ФЗ: перс.данные граждан РФ — на серверах в РФ.
**Решение.** On-prem/частное облако клиента (ключевой дифференциатор студии)
закрывает это ПО ПОСТРОЕНИЮ — данные в контуре клиента, мы их не хостим.
Требует лишь: (1) явной записи в SECURITY/договоре «узел и все данные — в
инфраструктуре клиента»; (2) запрета дефолтного облачного egress (уже: SECURITY
правило 6, локальная модель по умолчанию, O6 config-check). Кода почти нет —
это гарантия архитектуры, её надо задокументировать как продажный/комплаенс-
аргумент, не построить.

### O10. Runbook’и и учения (стык N3/N7, DoD)
**Напряжение.** DoD RELEASE §4.8 требует, чтобы нетехнарь провёл бэкап/рестор/
upgrade/lockdown по runbook. Процедуры разбросаны по N3/N7/O2 — не собраны и не
отрепетированы. Непроверенный runbook = его нет.
**Решение.** Единый `docs/runbooks/` (backup, restore/DR, upgrade, эра-миграция,
lockdown, ротация ключа, шреддинг субъекта, восстановление воркера) + плановое
учение (можно на себе по таймеру) как ворота RC. Каждый runbook кончается
«критерий успеха» (проверяемо, не «сделал шаги»).

## 3. Что уходит в LLD, что остаётся спекой

**Углубляется в LLD (архитектурно-необратимое, сталкивается с инвариантами):**
- **LLD-16** crypto-shredding / право на забвение (O1) — сталкивается с I-1/I-5.
- **LLD-17** backup/DR + внешний якорь (O2/O3) — согласованность трёх хранилищ
  + доказуемость третьей стороне.
- **LLD-18** секреты и ключи/ротация (O4) — эпохи ключа узла VS I-5.

**Остаётся спекой в деплой-гайде / N11 (инженерная рутина, «кодим без Fable»):**
- O5 наблюдаемость (/metrics в контуре, красные состояния) — LLD при первом
  observability-стеке клиента.
- O6 config-модель + `kalita config check` (secure-by-default, fail-fast).
- O7 контракт супервизии воркера (health/heartbeat/версия/лимиты на процесс-слое).
- O8 лимиты ресурсов + disk-watermark + GC блобов + read-only backpressure.
- O9 data-residency — документируется, не строится.
- O10 набор runbook + учение (ворота RC).

## 4. Дополнения к Definition of Done (к RELEASE-1.0 §4)

11. Право на забвение: удаление субъекта делает его payload нечитаемым, hash-
    цепочка и offline-verify целы (LLD-16 приёмка).
12. DR-учение: потеря диска → восстановление из бэкап-набора (журнал+файлы+ключи)
    на чистой машине; узел консистентен; внешний якорь подтверждает нетронутость.
13. Ротация ключа узла: после ротации старые чекпоинты verify проходят по своей
    эпохе; новые — по новой (I-5 не нарушен).
14. `/metrics` доступен в контуре; дашборд показывает красные состояния; ноль
    внешних SaaS-зависимостей.
15. `kalita config check` на прод-профиле: небезопасная комбинация НЕ стартует
    (secure-by-default доказан).
16. Runbook’и (§O10) проведены нетехнарём в учении; каждый — с критерием успеха.

## 5. Сознательно НЕ в проме-1.0 (триггеры)
Полный observability-стек с трейсингом (триггер: клиент с APM) · узловой
супервизор воркеров (триггер: >N воркеров/потребность в оркестрации) · авто-DR/
георепликация (триггер: SLA с RTO<часы) · HSM для ключа узла (триггер:
регуляторное требование) · TSA/нотариус-якорь по умолчанию (триггер: спор/
страховка) — эскиз в LLD-17, включение по факту.
