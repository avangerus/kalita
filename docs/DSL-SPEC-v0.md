# Kalita DSL — Specification v0

Status: **frozen** — this reflects the grammar the shipped compiler accepts
(authoritative companion: `internal/mcp/grammar.go`, served live by `get_grammar`,
kept in lockstep with the parser). New constructs are additive and arrive through
the pack feedback loop (see `docs/ROADMAP.md`); this surface does not change under
packs already built on it. Keywords are English (HLD §10). Files: `*.dsl`, UTF-8,
4-space indent, no tabs. Pack = a directory with `pack.dsl` (manifest) + module
files (entities / workflows / security / ops, split however the pack prefers).

## 0. Grammar philosophy

1. **Narrowness is the source of guarantees.** Every construct is either fully
   checkable by the compiler, or it does not belong in the grammar.
2. **One way to express one thing.** No synonyms or sugar — a smaller drift
   surface when packs are generated by agents.
3. **Errors are written for agents:** every compilation error =
   `{code, file:line, message, fix_hint}` — machine-readable, with a fix hint
   (the agent self-correction loop).
4. **Complexity lives in the kernel, not the language.** A module stays a short
   declarative file; the engine does the hard part. Every construct must pay for
   itself.
5. Names: `snake_case` for fields, `PascalCase` for entities / states / roles.

## 1. Pack manifest

```
pack collections
version 0.1.0
requires kalita >= 0.1
depends core >= 0.1        # base pack: core.User, core.Calendar, mdg dictionaries
```

### 1.1 Product manifest (optional, LLD-05 §3, PK-4)

A pack shipped as a standalone product may declare a `product:` block —
white-label identity and default auth mode. `--brand*` node flags default
from it; the frontend reads it via `/api/meta`. Absent entirely for packs
that are not standalone products (I-1: zero impact on existing packs).

```
product:
    name "KnowVault"
    logo "https://cdn.example.com/logo.svg"
    color accent "#4da3ff"
    home SearchFace          # a Face name (frontend concept, opaque to the DSL)
    auth password            # password | invite | token
```

`#` starts a comment in this DSL, so hex colors must be quoted strings, not
bare `#RRGGBB` tokens. `home` names a renderer-side "face" template (LLD-05
§1) — the DSL does not validate it against a known face list, since faces are
a frontend-library concept, not a backend one.

### 1.2 product.mcp — façade tool registry (optional, LLD-06 §1, PK-2)

A pack may declare `product.mcp:` — the domain-facing MCP tools a generic
façade worker exposes over the node MCP (the façade worker itself, LLD-06
PR-2, is a separate build; this section is pure manifest DATA it reads).
Shares the `product` leading token with §1.1 but is a distinct block —
disambiguated by the `.mcp` that follows — and the two coexist freely.

```
product.mcp:
    tool legal.submit_contract "Create a contract and send it to legal review":
        in:
            title:        string required
            counterparty: ref[Counterparty] required
            terms:        text required
        compose:
            create Contract(title: $title, counterparty: $counterparty, terms: $terms) -> $contract
            act send_to_legal on $contract
        out: contract
```

`in` reuses the entity field grammar (§3). `compose` is one node-call
composition step per line, captured as raw text — this compiler does not
interpret it; the façade worker does, executing each step as a pass-through
call under the CALLER's own bearer token (LLD-06 §1: strict pass-through, no
service-account writes — ABAC/HITL apply exactly as if the caller invoked
`create_record`/`act` directly). `out` names which step's binding the tool
returns. Absent entirely for packs with no façade tools (I-1).

## 2. Data types (closed list)

| Type | Note |
|---|---|
| `string` | up to 1 KB, indexable |
| `text` | unlimited, full-text searchable |
| `int`, `float`, `bool` | |
| `money` | a bare number, or `{amount, currency}` for multi-currency |
| `date`, `datetime` | TZ-aware |
| `email`, `url`, `phone` | validated strings |
| `duration` | e.g. `2d4h` |
| `percent` | 0–100 |
| `color` | `#RRGGBB` |
| `decimal`, `json` | exact decimal; opaque JSON value |
| `serial` | auto document number; `format="INV-{year}-{seq:5}"` |
| `enum[A, B, C]` | closed list of values |
| `ref[Entity]` | `+ on_delete = restrict \| set_null \| cascade`; `ref[core.User]`, `ref[core.Calendar]` reference built-ins |
| `mdg[Name]` | master-data field: provisions a `core.Name` dictionary (code, name, parent, active) with picker + permissions + screen, out of the box — so a "positions" lookup is a field, not an entity-with-permissions to hand-roll |
| `array[ref[Entity]]` | multiple references |
| `array[string]` | free tags |
| `array[enum[A, B]]` | multiselect / components |
| `array[file]` | multiple attachments |
| `file` | single attachment (stored by the core) |

`core.*` are built-in system entities, never declared: `core.User` (people
directory projected from the identity registry), `core.Calendar` (business
calendars), and the `mdg` dictionaries. Read by all, written by the owner.

Not in v0: geo types, nested record structures.

## 3. Entities

```
entity Debtor "Debtor":                          # optional human label (i18n)
    company:      string required label="Company"
    contract:     ref[Contract] on_delete=restrict
    debt:         money
    position:     mdg[Position]                   # master-data dictionary field
    opened:       datetime default=$now
    rate:         money default=contract.rate     # derived from a picked ref
    overdue_days: int computed = days_since(contract.due_date)
    status:       enum[OnTime, Overdue, Claim, Legal, Settled] default=OnTime
    manager:      ref[core.User] default=$me

constraints:
    unique(company, contract)
```

Field modifiers: `required`, `unique`, `default=<expr>` (incl. `$me`, `$now`, and
`<ref>.<field>` derived defaults), `computed=<expr>` (read-only, recalculated by
the core), `on_delete=…`, `label="…"` (i18n). An entity may be `singleton` (at
most one record). Every entity automatically gets `id`, `created_at/by`,
`updated_at/by`, a full change history (event store), and a comment thread — no
declaration needed.

## 4. Workflow

```
workflow Debtor on status:
    OnTime  -> Overdue: auto when overdue_days > 0
    Overdue -> Claim:   send_claim assignee=agent(Collector) label="Send claim"
    Claim   -> Legal:   escalate requires approval(FinDirector)
    any     -> Settled: auto when debt = 0
```

Transition: `Source -> Target: action [auto] [when <guard>] [assignee=<Role>|agent(Role)|auto] [requires approval(<Role>)] [label="Button"]`.

- `auto` — executed by the core when the guard becomes true;
- `assignee` — who gets the task to execute the transition (`agent(Role)` queues
  it in that agent role's pool);
- `requires approval(Role)` — HITL: the transition parks in the signing queue;
  **it does not exist without the signature** (Ed25519, offline-verifiable). An
  agent cannot fast-forward it. Sequential `requires approval` transitions give
  multi-party sign-off (e.g. legal then commercial), each a distinct signer.
- The compiler checks reachability of every state, no transitions to/from
  non-existent states, and conflicts among auto-guards.

## 5. Roles and permissions

```
roles:
    Accountant
    FinDirector
    Collector agent          # agent marker: the role is fulfilled by an agent

permissions:
    Collector:
        read  [Debtor, Contract]
        act   [send_claim]
        deny  [update Debtor.debt, delete *, read Contract where classified = true]
    Accountant:
        full  [Debtor]
        read  [Contract]
    FinDirector:
        approve [escalate]
        read    all
```

- Verbs: `read | create | update | delete | act [actions] | approve [actions] | full`.
- Row-level scope: `Entity where <expr>` (e.g. `read Debtor where manager = $me`,
  or indirect `read Task where project.owner = $me`). Direct and ref-path
  `= $me[.attr]` scopes are served from secondary indexes — the permitted-set
  query stays sub-linear at scale (ADR-005).
- Field-level: `deny update Debtor.debt`. `deny` may also carry `delete *`,
  `read … where …`, and `act […]`.
- **Deny is stronger than allow. For agent roles the deny block is mandatory** —
  an agent role without explicit boundaries does not compile.
- No rule = no access (default deny). Unevaluable condition = deny, never allow.

## 6. Automation

```
automation:
    on schedule daily at 09:00 for Debtor when status = Overdue:
        agent Collector: draft_reminder(tone = soft)
        notify email(manager)

    on update Debtor when status changed to Legal:
        webhook out "https://legal.example.com/intake"

    on stuck Debtor in Claim for 10d:
        escalate_to FinDirector
```

Triggers: `on schedule <schedule> [for <Entity>] [when …]` (`when` requires
`for`), `on create|update|delete <Entity> [when …]`, `on stuck <Entity> in
<State> for <duration>`. Actions (closed list): `agent <Role>: <task>(args)`,
`notify email(field)`, `webhook out <url>` (outbound only — egress is visible in
the spec), `create|update <Entity> set {…}`, `escalate_to <Role>`.

## 7. Expressions

One boolean/arithmetic language for guards, permission scopes, filters, and
computed fields. Deliberately limited — no loops, no user-defined functions, no
outbound calls.

- Operands: literals, field paths and one-hop ref-paths (`project.owner`),
  barewords (enum values), `$me`, `$me.<attr>` (actor attribute — the ABAC
  subject), `$self` (the current record, in roll-ups), `$now`, `true`, `false`,
  `null`.
- Comparisons `= != > < >= <=`, `field in [a, b]`, `and / or / not`, parentheses.
  `null` is presence: `field = null` (empty) / `field != null` (filled).
- **Computed fields** additionally allow:
  - arithmetic `+ - * / ( )` over fields (`amount - amount * discount / 100`);
  - elapsed/remaining time: `days_since|hours_since|minutes_since(path)`, their
    forward mirror `days_until|hours_until|minutes_until(path)` (negative once
    past), and `business_days_since|…(path[, calendar])` which count working time
    only (skip weekends/holidays/off-hours; the calendar arg is a code or a
    ref-path so each record picks its own);
  - roll-ups over related records: `count(Entity where reffield = $self)` and
    `sum|avg|min|max(Entity.field where reffield = $self)`.

## 8. UI and dashboards

```
ui Debtor:
    list: [company, debt, overdue_days, status] sort=-overdue_days
        filters: [status, manager]
        view "My debtors": where manager = $me
    form:
        section "General": [company, contract, debt]
    board: by status

dashboard Receivables "Receivables":
    tile "Overdue":   count Debtor where status = Overdue
    tile "Total debt": sum debt Debtor
    tile "By status": count Debtor group by status
```

`dashboard` tiles aggregate the **whole table** (`count` takes no field;
`sum/avg/min/max` take a numeric field; optional `group by` and `where`). Totals
respect each viewer's row permissions — a row-scoped user sees totals over only
their own rows, with no separate "see all" grant.

`link FromEntity -> ToEntity as forward_name / inverse_name` declares a named
bidirectional relation (both sides kept in sync). Built-in without declaration:
the **approval inbox** (signing queue), each record's **journal** (event
history), per-record **undo / rewind / diff** (compensating events — see
MCP-CONTRACT), the **comment thread**, and global search. Not in v0: charts,
custom widgets, themes.

## 9. Migrations (additive only in v0)

Allowed by diff: a new entity; a new field (nullable or with a default); a new
enum value (appended at the end); a new state/transition; a new role/permission;
new automation; any UI/dashboard change. Forbidden in v0 (require an explicit
export/migrate procedure): changing a field type, deleting/renaming a field or
entity, deleting an enum value or state. Each accepted diff is a new
SystemDefinition version; application is atomic; rollback is a reverse proposal
through the same signing queue.

## 10. Reserved words (not implemented; forbidden as identifiers)

`component` (escape hatch / WASM), `integration` (inbound connectors), `simulate`
(layer-2 dry-run), `metric`, `system` (system-pack marker), `federation` /
`remote` (cross-node references) — reserved so packs built today do not collide
with these when they land.

## 11. System packs (v1 plan)

The core is described in kalita itself as far as possible: `core` is a pack
(`core.User`, master data, calendars, attachments). The difference from an
ordinary pack is the `system` marker — its contents change only via a platform
update; the ordinary change pipeline rejects edits to it (protection, not
privacy). Principle: everything that CAN be a pack MUST be a pack; only what
cannot (journal, permissions, compiler, runtime) stays in the core.

## 12. Node federation (layer 3 plan)

One node = one perimeter, but nodes can interoperate: a pack may declare an
external reference to an entity in another instance. Reserved: `remote[node.Entity]`;
exchange via typed contracts over an MCP bridge, both node identities present, a
log on both sides. Not implemented until layer 3.

## 13. Examples

`examples/collections/` (receivables) and `examples/dev_department/` are grammar
acceptance packs. `examples/pangram/` exercises every construct. Reference
product packs live in `packs/` (servicedesk, crm, eshop, devtrack, finance,
contracts, hr, tracker, knowvault, boards).

## 14. What is deliberately absent from v0 — and why

| Absent | Why | When |
|---|---|---|
| Escape hatch (`component`) | the WASM capability model needs its own design | v1 |
| Inbound integrations / connectors | perimeter security; outbound webhooks suffice for now | v1 — likely the first market-driven core gap (ROADMAP L2) |
| Document / report generation | heavier rendering semantics | v1 |
| Ref-paths deeper than one hop in expressions | compiler complexity grows fast | v1 |
| Destructive migrations | risk #1 of the project (HLD §9) | v2 |
