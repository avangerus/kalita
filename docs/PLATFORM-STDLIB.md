# Батарейки платформы — что kalita даёт из коробки

Цель: универсальный enterprise-скелет **уже внутри платформы**, его не строят заново.
Это список-цель стройки. Устав допуска в core — в [DSL-CORE-LIB.md]; здесь —
ЧТО и в каком ПОРЯДКЕ. Родитель: ARCHITECTURE.md (принципы), LLD-13 (data-pack),
LLD-16 (pii), core.notify (DSL-CORE-LIB §3).

Дата: 2026-07-05.

---

## Универсальный скелет (одинаков у всех enterprise-приложений)

Запись+метаданные · идентичность+права · процесс+согласования · аудит ·
справочники · комментарии/вложения/лента · уведомления · поиск/виды ·
автоматизация · интеграции · локализация. Домен — тонкий слой сверху.

## A. Уже бесплатно из архитектуры — НЕ строить, только ВЫСТАВИТЬ

Следствия журнала (event-sourcing) + одного choke point. На каждой сущности
присутствуют без объявления:
- **аудит** — кто/что/когда;
- **полная история** записи + **обратимость/откат**;
- **лента активности** — проекция журнала (не пишется руками);
- **метаданные** `created_at/by`, `updated_at/by` — деривятся из событий, НЕ поля;
- **гранулярные права** — до поля и строки (Permission Engine).

⚠️ Требование: платформа обязана авто-выставлять это на любой entity без
деклараций. Если для истории/аудита нужно что-то объявлять — это баг архитектуры.

## B. Строить сейчас — приоритет (самое повторяющееся)

1. ⚙️ **KEYSTONE — `include`/миксины + `core.fields`.** Стандартная обвязка
   записи как переиспользуемые миксины: **Sequenced** (человеко-номер INV-2026-
   0001), **Assignable** (owner/assignee), **Taggable**, **Named** (name/slug),
   **Period** (from/to), **Money** (amount+currency). Компилятор инлайнит поля.
   Аддитивно (I-1), но это L0-фича языка → ревью Fable, отдельный LLD.
   **Блокер всей горизонтали** (DSL-CORE-LIB §4): без него каждый пак копипастит.
2. **`reference` (turnkey) + `core.reference`** — Currency, Country, Timezone,
   Unit, Language, ProductionCalendar-RU (LLD-13). Первоклассный конструкт справочника.
3. **`core.User` + оргструктура** (Department + иерархия подчинения) + шаблоны
   ролей (Owner/Approver/Viewer).

## C. Строить следом

- **`core.notify`** — событие→канал→шаблон→настройка (спека: DSL-CORE-LIB §3;
  in-app=факт, внешнее=егресс+durable).
- **`core.content`** — Comment (есть) + Attachment (content-addressed) + Tag.
- **Авто-виды/поиск/фильтры** — платформа рендерит список/доску/карточку сама;
  пишешь только сохранённый фильтр.
- **Шаблоны workflow** — Draft→Review→Approved→Archived, Approval-gate миксин;
  **SLA/таймеры/эскалация** через `on schedule` / `on stuck`.

## D. Отложено (за триггером)

Локализация (i18n/tz/форматы) · конфиг-среды (dev/test/prod) · федерация (LLD-22).

## Порядок и почему

**Keystone (B1) — первый:** самое универсальное (обвязка на каждой записи)
сейчас невыразимо; пока нет `include`, `core.fields` не построить и горизонталь
не поедет. Дальше B2–B3 (справочники, идентичность) — очевидные потребители
миксинов. C — насыщение. Дисциплина роста и гейт допуска — DSL-CORE-LIB §2/§5:
промоушен в core строго по второму доказанному потребителю, не наперёд.

**Смысл:** половину скелета (блок A) не строят — она есть по устройству; вторую
(B/C) строят один раз в платформе, а не в каждом продукте. Отсюда «3–6 месяцев
до прототипа».
