# kalita HLD-V1 — High-Level Design расширений (релиз 1.0 → вертикали → флот)

Дата: 2026-07-02. Статус: draft для ревью фаундером → основа LLD-серии.
Отношение к `HLD.md` (v0.1): **расширяет, не заменяет**. Конституция (7+5
принципов, MASTERPLAN §2) и ядро не пересматриваются. Скоуп: подсистемы из
RELEASE-1.0 (N1–N5, N10), PLATFORM-NEXT (`event`, Product Kit, паспорт,
data-heavy), федерация и штаб (эскизно, до их триггеров).

**Сквозные инварианты HLD-V1 (обязательны для каждого LLD):**
- **I-1 Аддитивность.** Любой v0-пак компилируется и любой существующий журнал
  реплеится без изменений. Новые виды событий и поля envelope — только
  аддитивные (`schema_v`).
- **I-2 Один choke point.** Ни одна новая поверхность (event, WASM, чат, bridge,
  продуктовый MCP) не мутирует состояние мимо Permission Engine и журнала.
- **I-3 Ошибка — это событие.** Побочное действие либо произошло (событие),
  либо его отказ записан (событие). Тихих провалов не существует по построению.
- **I-4 Секреты — только node/worker.** Ничего нового в DSL/журнале.
- **I-5 Офлайн-доказуемость.** Всё, что называется подписью, проверяется
  `kalita verify` без доступа к живому узлу.

---

## H1. Подпись человека — WebAuthn/passkey (N1)

**Цель.** Approve человека = криптографическая подпись, которую сервер не мог
изготовить сам; офлайн-проверяемая.

**Архитектура.**
- Регистрация: при онбординге (invite redemption / первый вход) браузер создаёт
  passkey (`navigator.credentials.create`); в журнал — событие
  `actor.credential_registered {actor, credential_id, cose_public_key, aaguid}`.
  Приватный ключ не покидает устройство (принцип EVENT-STORE §4 сохраняется).
- Подпись решения: каноническая строка
  `approval-v1||task_id||record_ref||transition||grant||basis||head_seq` →
  SHA-256 → **challenge** WebAuthn-assertion. Событие
  `approval.decided` дополняется `{credential_id, authenticator_data,
  client_data_json, signature}` — полный материал офлайн-верификации.
- Верификация: (а) challenge внутри clientDataJSON == хэш канонической строки;
  (б) подпись assertion валидна по cose_public_key из журнала. Расширить
  `kalita verify --pub` (I-5).
- Enforcement: узловой флаг `--require-human-signature` — прод отказывает
  approve без passkey; dev/демо живут на токенах. Потеря ключа = новая
  регистрация новым событием; старые подписи остаются валидными (ключи в журнале).
- Агенты — Ed25519 как есть. Модель «человек-WebAuthn / агент-Ed25519 /
  узел-checkpoint» из EVENT-STORE закрывается целиком.

**Решения.** Библиотека — чистый Go (go-webauthn), CGO запрещён (single binary).
Хранение credential — журнал, не таблица (проекция identity расширяется fold'ом).

**LLD-вопросы (LLD-02):** формат COSE-ключей в payload (base64 CBOR);
мульти-девайс (несколько credential на актора — да, список); UX Inbox.decide;
поведение MCP-транспорта (человек через MCP не подписывает — только UI/SDK).

**Риски.** Браузерная совместимость на он-прем интранетах (не-HTTPS невозможен
— уже требуем TLS); программируемая «подпись» через удалённый рабочий стол —
вне модели угроз (фиксируем в SECURITY).

## H2. Целостность каскадов: ошибки-события и операционные скобки (N2)

**Цель.** Инвариант I-3 в коде; kill -9 в любой точке не оставляет тихого
рассинхрона.

**Архитектура.**
- Новые события: `automation.failed {rule, trigger_seq, action, error, attempt}`;
  ретрай тиком с экспоненциальным backoff (cap N попыток) →
  `automation.abandoned {…}` + **задача оператору через сам task-пул**
  (эскалация механизмом платформы, не спец-кодом).
- Скобки: многошаговая операция (rewind, каскад automation, будущий emits-цепочки)
  пишет `op.begin {op_id, kind, target}` … `op.end {op_id}`. Replay при старте:
  незакрытая скобка → `op.aborted {op_id}` дописывается, затронутая запись
  помечается `inconsistent` (поле проекции, не журнала) + задача оператору.
  Никакой авто-магии доигрывания — простота и явность.
- Идемпотентность обязательная: все мутации обоих транспортов требуют
  `IdempotencyKey` (REST-заголовок / поле MCP-тулов); `ByIdemKey` в Store уже
  есть. Сервер генерирует op_id сам.
- CI-гейт: запрет паттерна `_, _ =` на путях побочных действий
  (go-analyzer или grep-гейт по списку функций).

**LLD-вопросы (LLD-01):** таксономия kind скобок; глубина вложенности (каскад
внутри каскада — запретить, плоско); лимит цепочки automation (сейчас есть
anti-loop? — проверить, задать глубину); формат inconsistent-задачи.

## H3. Upgrade и миграции: replay-as-migration + эры (N3)

**Цель.** Клиент обновляется и переименовывает поля без нас.

**Архитектура.**
- **Версионирование событий:** envelope получает аддитивное поле `schema_v`
  (отсутствие = v0; canonicalJSON старых событий не меняется — hash-цепочка
  цела, I-1). Правило чтения: бинарь N обязан fold'ить все события ≤N.
- **Golden-журналы совместимости:** `testdata/golden/journal-v*.jsonl` на
  каждую released-версию; contract-тест: текущий бинарь реплеит все golden и
  совпадает со snapshot-проекциями. Это ворота любого изменения fold-функций.
- **`kalita upgrade --to <ver>`:** стоп → pg_dump → подмена бинаря →
  `kalita verify` → старт (replay = миграция аддитивных изменений бесплатно) →
  smoke (/healthz,/readyz) → событие `node.upgraded {from,to}`. Upgrade не
  пишет в журнал ничего, кроме финального события. **Rollback = старый бинарь
  на том же журнале** (журнал не мутировал).
- **Эры (деструктивные изменения):** `export` → JSONL → трансформация по
  runbook-шаблонам (переименование/смена типа/удаление) → `import` в пустой
  журнал, первое событие `era.genesis {prev_era_final_checkpoint}` —
  **цепочка эр сцеплена чекпоинтами**: доказуемость истории непрерывна через
  разрушительную миграцию. Старый журнал архивируется целиком.

**LLD-вопросы (LLD-03):** матрица совместимости пак-DSL ↔ версия бинаря
(`requires kalita >= X` уже в манифесте — enforcement при старте); что входит
в smoke; авто-бэкап retention.

## H4. LLM-периметр: изоляция, детекция, honeypot (N4)

**Цель.** Обманутый агент бессилен — и это демонстрируемо.

**Архитектура (4 слоя).**
1. **Права — последний и главный рубеж** (есть): движок отклоняет запрещённое
   независимо от содержимого LLM-ответа. **Тест без LLM:** мок-модель
   возвращает злонамеренный JSON («approve сам», «смени статус», «прочти чужое»)
   → каждый вызов = permission denied. Этот тест — одновременно продуктовое
   демо («смотрите, что будет, если агента взломают»).
2. **Структурная изоляция промпта** (контракт agent_runner): системная
   инструкция и задача — вне данных; данные — в маркированных блоках
   `<data source="…" trust="untrusted">`; ответ — строго JSON-схема (уже так
   в handle_legal), свободный текст никогда не исполняется.
3. **Ingest-детекция:** эвристики инструкций-в-данных (императивы к
   assistant/system, «ignore previous», упоминания tools) → событие
   `ingest.flagged {source, reasons, score}` + пометка записи. Подсветка, не
   блокировка (false positives на юртекстах неизбежны).
4. **Honeypot-корпус в CI:** `testdata/honeypot/**` (отравленные договоры,
   резюме, письма). Уровень A (в CI, без LLM): детектор находит; движок
   отклоняет мок-атаки. Уровень B (ночной, локальная LLM): агент прогоняет
   корпус — 0 запрещённых действий, инъекция всплывает в assessment как находка.

**Не в этой версии:** egress-DLP (маскирование для облачных моделей) — правило
конфигурации: прод = локальная модель, облако = явный флаг с предупреждением.

**LLD-вопросы (LLD-01 приложение):** словарь эвристик и score; куда пишется
флаг (поле записи vs только событие); политика façade-воркеров при flagged.

## H5. WASM escape hatch v1 (N5)

**Цель.** Клапан для вычислимой кастом-логики без роста грамматики.

**Архитектура.**
- Грамматика (аддитивно): `component <name>: wasm hash=sha256:<h>
  in { f1: type, … } out <type>` — объявляется в паке; использование — только
  в computed и валидаторах: `total: money computed = tax_calc(amount, rate)`.
- Санбокс: wazero (pure-Go), **ноль host-imports** (нет WASI, часов, рандома,
  I/O — детерминизм по построению), fuel-лимит, memory-лимит, timeout.
- Модуль — в content-addressed blob store (механика files есть); hash в DSL
  сверяется при загрузке; подключение модуля = propose_change → подпись →
  событие `component.installed {name, hash}` (кто и что привнёс — доказуемо).
- Компонент не может по построению: видеть чужие поля (получает только in),
  мутировать, обходить permissions (I-2).

**LLD-вопросы (LLD-04):** ABI (каноничный JSON in/out через линейную память —
проще; или компонент-модель WASM — позже); кэш результатов (module,inputs);
бюджеты по умолчанию; SDK-шаблон авторства (Rust/TinyGo примеры).

## H6. Примитив `event` в DSL (PLATFORM-NEXT §3)

**Цель.** Именованные бизнес-факты: внутри пака, между паками, между узлами —
одна конструкция.

**Архитектура.**
- Грамматика (аддитивно): `event Name: field: type…` (payload-схема с
  валидацией как у entity, включая ref); `… emits Name(field=expr,…)` на
  переходе workflow; действие automation `emit Name(…)`; триггер
  `on event [pack.]Name:`.
- Журнал: `event.emitted {name, payload}` — пишется внутри op-скобок вместе с
  породившим переходом (H2), затем подписчики диспатчатся как automation
  (каждый — своё действие/отказ, I-3).
- Права: новый verb `emit [Name]` в permissions; MCP-тул `emit_event`
  (нужен inbound-коннекторам и bridge) — под этим verb'ом, полный аудит.
- Cross-pack: подписка `on event crm.OpportunityWon` резолвится при compose;
  отсутствие пака-эмитента = ошибка компиляции с fix_hint.
- Cross-node: bridge-агент (H8) читает `event.emitted` из журнала-источника и
  вызывает `emit_event` на целевом узле под least-privilege ролью —
  федерация не изобретает транспорт.

**Решения.** emits — часть перехода (атомарность скобками, не мульти-записью);
прямой emit из UI людям не даётся (только переходы/automation/MCP-verb);
payload не мутирует после эмита (это факт, не сущность).

**LLD-вопросы (LLD-01):** порядок диспатча подписчиков (детерминированный,
по имени пака); retention повторов (тот же backoff H2); версии payload-схемы
при эволюции пака (аддитивные поля — ок; прочее — через эру пака).

## H7. Product Kit (PLATFORM-NEXT §4)

**Цель.** Слой-переходник «пак → поставляемый вертикальный продукт»; ядро
остаётся нежным и нетронутым.

### H7.1 PK-1 — дизайн-система по атомарной модели
- Пакет `@kalita/ui` рядом с `@kalita/sdk`: `tokens.css` (CSS custom
  properties — темизация без билда) → атомы (Input, Select, Money, Badge,
  StatusChip, DateTime — вынести из FieldInput/FieldValue, сохранив их как
  диспетчер) → молекулы (FieldRow, RecordCard, ApprovalCard, TimelineItem) →
  организмы (`KList/KDetail/KBoard/KInbox` — уже в SDK) → **шаблоны лиц**
  (SearchFace, RiskCardFace, ChatFace).
- Контракт компонентов: потребляют дескрипторы `/api/meta` (поле/права/actions)
  — доменных знаний ноль; buildless обязателен (ADR-004).
- Каталог-витрина `web/catalog.html`: каждый компонент с примерами и knobs
  (наш storybook, без сборки). Встроенный админ-клиент постепенно пересобирается
  на эти же атомы (сейчас два fetch-клиента — сойдутся на @kalita/sdk).

### H7.2 PK-2 — продуктовый MCP (façade)
- Воркер-façade: доменные тулы (`kv.search/kv.ask/kv.upload`;
  `legal.submit_contract/legal.findings`) → композиции узловых вызовов.
- **Auth: строгий pass-through** — façade требует bearer конечного пользователя
  и проксирует его; собственного токена на мутации не имеет → права, аудит,
  rate-limit остаются точными (I-2). Façade добавляет семантику, не полномочия.
- Реестр: продуктовые тулы описываются в манифесте пака (`product.mcp` секция)
  — façade генерик-воркер читает манифест (не кодируется на продукт).

### H7.3 PK-3 — операторский чат (KChat + chat-runner)
- Пак `assistant`: сущности Session, Message — обычные записи (права
  `where owner=$me`, аудит и retention бесплатно — диалог governed по
  построению).
- Воркер chat-runner: локальная LLM + MCP-loop **под актором пользователя**
  (pass-through, как PK-2); инструменты — узловой MCP + продуктовые façade.
  Каждое действие из чата = обычное журналируемое действие актора; HITL-гейты
  работают как есть (чат не обходит подписи — I-2).
- KChat — организм PK-1; ядро не знает о чате ничего (решение «мозг снаружи»
  не нарушено).

### H7.4 PK-4 — обвязка поставки
- Манифест продукта в паке: `product { name, logo, colors, home: SearchFace,
  auth: password|invite }` — узловые `--brand*` флаги становятся значениями
  по умолчанию из пака.
- **Пароль как credential актора** (не consumer-масштаб): `actor.password_set
  {bcrypt}` в журнале, `/api/login` обменивает пароль на обычный bearer —
  UX-обёртка над токенами; массовый self-signup остаётся за внешним IdP
  (граница N7 не двигается).
- Deploy-шаблон на продукт (по образцу deploy/knowvault), status-страница,
  runbook-шаблоны — генерируются `kalita product scaffold`.

**Порядок.** Первый потребитель — KnowVault M2 (его чек-лист = черновик PK),
второй — Legal; генерализация строго на втором (правило второго потребителя).

**LLD-вопросы (LLD-05, LLD-06):** схема манифеста product; каталог-витрина;
формат MCP-манифеста тулов; сессии чата — лимиты и суммаризация контекста.

## H8. Федерация узлов (эскиз до триггера «≥2 узла»)

- Bridge-агент: воркер с двумя identity (по узлу), least-privilege с обеих
  сторон; конфиг = подписки (event-имена) → отображения (emit/create на цели).
- Транспорт: журнал-источник как outbox (`Since(seq)`), **exactly-once =
  at-least-once + IdempotencyKey = `{source_node, seq}`** на целевом узле —
  курсор не нужен как отдельное хранилище, он восстановим.
- Cross-node ref v1: **зеркальная запись** (mirrored-entity с полем
  `origin {node, id}`), синхронизируемая события́ми; `remote[…]` из DSL-SPEC
  §10b остаётся зарезервированным (слой 3).
- Identity-якорь: v1 — взаимная регистрация пары bridge-акторов (события на
  обоих узлах); общий root доверия — слой 3.
- Сводная наблюдаемость: journal-sink (T10) в штаб-узел; федеративных
  запросов нет — только реплики.

**LLD-07** пишется при триггере; зависимости: H6 (event), H3 (узлы разных
версий должны сосуществовать — schema_v решает).

## H9. Штаб рабочей силы (эскиз; AGENT-PLATFORM-VISION)

Пак `workforce` (Agent, Assignment, Policy, Budget, AgentIncident + дашборды)
на обычном узле; данные — из journal-sink'ов и bridge-подписок на task- и
approval-события рабочих узлов; управление — через emit на целевые узлы.
Ядро не расширяется (T8). Детализация — после триггера North Star.

## H10. Паспорт производительности и data-heavy паттерн

- **Профили:** P1 «пилотный микс» (5 MCP-агентов + 10 UI-читателей +
  automation-тик), P2 bulk (10k create), P3 replay (1M/10M синтетики),
  P4 auth-шторм (Authenticate под конкуренцией). Числа в CI; регресс >20%
  валит сборку; паспорт публикуется в релиз-нотах (продажный артефакт:
  «узел держит X, replay Y»).
- **Data-heavy паттерн (референс для datapulse):** сырьё и тяжёлые вычисления
  — у воркера (DuckDB/sqlite/Qdrant, ADR-002); синхронизация — fingerprint
  (паттерн KnowVault); в kalita — только governance-объекты (источники,
  группы, задачи, решения, метрики). Порог tiered storage — в мониторинге
  узла, реализация по факту.

## H11. Карта LLD и порядок исполнения

| LLD | Содержимое | Зависимости | Когда |
|---|---|---|---|
| **LLD-01** | H2 скобки/ошибки-события + H6 event + H4 периметр (общая журнальная механика) | — | первым: фундамент R1 |
| **LLD-02** | H1 WebAuthn | LLD-01 (формат событий) | R1 |
| **LLD-03** | H3 upgrade/эры/golden | LLD-01 | R2 |
| **LLD-04** | H5 WASM | — | R3 |
| **LLD-05** | H7.1/H7.4 дизайн-система + обвязка | — | с KnowVault M2 |
| **LLD-06** | H7.2/H7.3 продуктовый MCP + чат | LLD-05, H4 | за LLD-05 |
| **LLD-07** | H8 федерация (+H9 эскиз) | LLD-01 (event), LLD-03 (schema_v) | триггер ≥2 узла |

Формат каждого LLD: контракты (грамматика/схемы событий/API), псевдокод
критических путей, план миграции, тест-план приёмки (расширяет DoD
RELEASE-1.0 §4), оценка. Ревью LLD — обязательно против инвариантов I-1…I-5
этого документа.
