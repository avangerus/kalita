# DESIGN-REVIEW-01 — упростить и расширить: сверка с готовыми системами

Дата: 2026-07-02. Автор: Fable. Статус: критическая ревизия для фаундера.
Повод: после сессии проектирования (LLD-01..18, инварианты I-1..I-6,
PROD-READINESS) — «сильно усложнили». Две задачи: (A) честно найти, что
упростить/свернуть; (B) стресс-тест ядра реальными системами — чего им не
хватает в ядре, чтобы построиться на kalita.

Тон — самокритичный: часть сложности навёл я в этой сессии.

## A. Упрощение (против собственного дизайна)

### A1. «Faces» — лишний слой. Face = именованная схема, не код.
LLD-05 ввёл faces как 5-й слой дизайн-системы (atoms→…→faces). LLD-14 ввёл
UI-как-данные (схема-дерево). LLD-15 назвал faces «преднастроенными
деревьями». Это ДВА способа сказать одно. Face — просто именованная СХЕМА
(данные), а не отдельный код-слой.
**Свернуть:** дизайн-система = примитивы (atoms/molecules/organisms) +
СХЕМЫ, которые их компонуют. «Face» = поставляемая схема, ничего больше.
Минус один концепт, минус код-слой. (Правит LLD-05/14/15.)

### A2. Инфляция верболов прав. Заморозить словарь.
Права обросли верболами: act/approve/create/update/emit/tail (+read/query).
Каждая новая способность добавляла верб — дрейф к «верб на операцию».
**Подозрительны `tail` и `emit`:** не являются ли они `read`/`act`,
квалифицированными scope’ом (node-wide / event-name)? Точность least-privilege
(bridge получает только `tail`) — реальна, но её можно выразить scope’ом.
**Решение:** заморозить закрытый словарь верболов с обоснованием на каждый;
новые нужды маршрутизировать в существующие верб+scope, а не плодить. Ревизовать
`tail`/`emit` на предмет свёртки. (Не срочно, но зафиксировать дисциплину.)

### A3. Тройное «ожидание подписи». Один примитив.
Три механизма «намерение ждёт подписи человека»: `definition.proposed`
(изменение пака), `approval.requested` (HITL перехода), shadow-proposal
(LLD-09). Общее у всех: захваченное намерение + требуемая подпись +
применение-по-одобрению.
**Свернуть к одному примитиву «pending signed intent»**, который все три
специализируют. Плюс: shadow/HITL/pack-approval становятся согласованы по
построению, а не три параллельных пути. (Проверить применимость — объекты
разные: definition/record/каскад; но паттерн должен быть один.)

### A4. 18 LLD — это КАРТА, не порядок сборки.
Самое важное. Beachhead — ОДИН клиент (Legal). 18 LLD, 6 инвариантов, day-2
пласт — риск gold-plating ДО валидации ядрового цикла живым клиентом.
**Дисциплина:** доказать Legal-петлю (submit→агент-находки→HITL→решение,
governed/аудит/откат) МИНИМУМОМ ядра; пилот вскроет реальные гэпы — метод
pack-driven discovery уже сработал в этой сессии (паки вскрыли гэпы грамматики).
LLD-09..18 — валидированный БЭКЛОГ, не build-now список. Карта хороша именно
как карта; опасность — спутать её с планом стройки.

## B. Готовые системы → гэпы ядра

Для каждой: строится ли на kalita сегодня, чего не хватает, вердикт
(**cover** уже накрыто · **extend** малое расширение · **pattern** документируем
приём, не код · **boundary** сознательно НЕ строим).

| Система | Жанр | На kalita сегодня | Чего не хватает ядру | Вердикт |
|---|---|---|---|---|
| Jira / Linear | issue+workflow | да (workflow/HITL/automation/KBoard) | сохранённые виды/фильтры | **cover** (виды = схемы LLD-14) |
| Salesforce / CRM | объекты+процесс+отчёты | да (crm-пак) | построитель отчётов; formula | **cover** (отчёт=схема; formula=computed/WASM) |
| Zendesk / ServiceDesk | тикеты+SLA+очереди | да (servicedesk-пак) | клиентский портал; CSAT | **cover** ядро; портал=**boundary** (consumer, N7) |
| Airtable / Notion | гибкая БД + виды | частично | пользователь сам правит СХЕМУ в рантайме | free-form=**boundary**; лёгкое governed-изм.=**extend** |
| Metabase / BI | аналитика | да (data-heavy воркер, H10) | rollup/агрегаты во времени | **cover**; rollup=**extend** (минор) |
| Shopify | каталог+корзина+заказы+оплата | частично | оплата; корзина/склад высокочастотны | оплата=connector(отложено); корзина=**pattern** |
| Google Docs | real-time collab | нет | CRDT/OT совместное редактирование | **boundary** (не наша модель) |
| Slack | live-мессенджер | нет | real-time/высокочастотное эфемерное | **boundary** (KChat — операторский, не мессенджер) |
| Camunda | BPM | частично | параллельные ветки/подпроцессы | **extend** (workflow = один активный статус, подтв.) |
| Calendly | запись/расписание | частично | calendar-view; внешнее бронирование | view=отложено; booking=**boundary** (consumer) |

## C. Извлечённые ядровые темы

### Расширить (мало, высокорычажно)
- **E1. Паттерн transient-состояния (документ, НЕ код).** Высокочастотное
  эфемерное состояние (корзина, presence, черновик-сессия, live-набор) — у
  воркера/кэша; в журнал входит только СОВЕРШИВШИЙСЯ бизнес-факт (Order, не
  каждый клик по корзине). Без этого правила корзину смоделируют записями и
  упрутся в мьютекс/рост журнала (N6/N9). Это граница «что достойно события».
  Дёшево, спасает от целого класса ошибок моделирования.
- **E2. Лёгкое governed-изменение схемы.** Ставка на governance (пак меняется
  через propose→approve) — наш ПЛЮС, не баг; но аддитивное поле должно
  добавляться быстро (fast-path propose→approve), чтобы ощущалось «гибко как
  Airtable» без потери аудита. Эргономика существующего пути, не новый примитив.
- **E3. Параллелизм/подпроцессы workflow — по триггеру пака.** Реальный BPM
  («юр-ревью И фин-ревью параллельно → join → подпись») сейчас не выразим
  (один активный статус). НЕ строить наперёд; зафиксировать как известный лимит,
  расширить, когда пак-заказчик упрётся. Многие процессы моделируются без
  параллелизма (под-статусы / отдельные записи).
- **E4. Rollup-агрегаты по ref.** velocity/forecast/SLA-аналитика — минорное
  расширение computed (агрегация по коллекции ref во времени). По требованию.

### Границы (объявить явно — НЕ строить на kalita)
- **B1. Real-time совместное редактирование / CRDT** (Docs). Другая модель
  согласованности; не событийные governed-записи.
- **B2. Free-form citizen-dev схема без governance** (ядро Airtable). Наша ставка
  противоположна и это дифференциатор — не догонять.
- **B3. Consumer-масштаб портал/self-signup** — за внешним IdP (N7), уже решено.
- **B4. Live-мессенджер** (Slack). Высокочастотное real-time — не наш профиль.

### Уже покрыто (подтверждение — тут ничего не делать)
Jira / CRM / ServiceDesk / BI-governance — ядро + UI-как-данные (LLD-14) уже
накрывают. **Побочный выигрыш:** построитель отчётов/видов достаётся БЕСПЛАТНО
из схема-дерева (отчёт = схема над query) — целый жанр закрыт без нового ядра.
Это, кстати, аргумент за LLD-14 как за упрощающий, а не усложняющий слой.

## D. Рекомендация

**Свернуть (снять сложность):**
1. faces → именованные схемы (A1) — минус слой.
2. заморозить словарь верболов прав, ревизовать tail/emit (A2).
3. один примитив «pending signed intent», три специализации (A3).

**Добавить (мало, по делу):**
4. документ-паттерн transient→worker (E1).
5. fast-path аддитивного governed-изменения схемы (E2).
6. rollup по ref (E4) — когда попросит пак.

**Отложить до пак-триггера (не build-now):**
workflow-параллелизм (E3), федерация, WASM, DR/шреддинг/ротация (пром), широта
каталога компонентов. Это бэклог-карта, не план стройки (A4).

**Объявить вне периметра (не строить):**
collab/CRDT, free-form citizen-dev, consumer-портал (за IdP), live-мессенджер.

**Главный сдвиг:** перестать трактовать LLD-09..18 как очередь сборки. Сначала —
Legal-петля минимальным ядром; живой пилот назовёт реальный приоритет
расширений. Сложность дизайна оправдана как КАРТА рисков; вредна как обязательство
построить всё сразу.
