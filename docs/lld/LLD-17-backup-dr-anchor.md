# LLD-17 — backup / disaster recovery / внешний якорь чекпоинтов (O2, O3)

Дата: 2026-07-02. Автор решений: Fable. Реализация: Sonnet 5 по документу.
Родитель: PROD-READINESS §O2/§O3, EVENT-STORE §3 (чекпоинты/якорь), RELEASE-1.0
§N3 (pg_dump/upgrade). Инварианты I-1/I-5. Тесно связан с LLD-16 (шреддинг-ключи).

**Мотив.** N3 дал pg_dump для upgrade, но не DR. Прод-эксплуатация требует:
восстановить узел после потери диска (RPO/RTO), ПРОВЕРИТЬ бэкап (непроверенный =
отсутствующий), защитить бэкап (в нём перс.данные) и согласовать ТРИ хранилища —
журнал (PG) + файлы (content-addressed blob) + ключи (шреддинг-KEK'и субъектов
LLD-16, ключ узла LLD-18). Плюс O3: доказать регулятору «журнал не переписан»
без веры нашему узлу.

**Границы для исполнителя.** Sonnet НЕ решает сам: точку согласованности бэкапа
= seq чекпоинта (§1, необратимо — иначе restore рассинхронен); envelope-модель
ключей, делающую бэкап erasure-safe (§3, необратимо, ревью Fable — стык с
LLD-16); что бэкап проверяется `kalita verify` + хэшами блобов, а не «скопировал
и ладно» (§2); что якорь — декларативный конфиг + событие, не скрытый вызов (§5).

---

## 1. Бэкап-набор и точка согласованности

**Решение.** Единица бэкапа — НАБОР на seq запечатанного чекпоинта:
- журнал (события ≤ seq_checkpoint) + все файлы-блобы, на которые ссылаются эти
  события + манифест ключей на этот момент (см. §3) + сам чекпоинт (голова+подпись).
- Точка согласованности = `checkpoint.sealed.seq`: restore реплеит журнал до
  этого seq → проекции согласованы с файлами и ключами. Никаких «полу-состояний»:
  файл, на который ссылается событие ≤ seq, гарантированно в наборе.
- RPO — интервал чекпоинтов/бэкапов (конфиг); RTO — время restore+replay (число
  из паспорта N6, P3 replay-бюджет).

## 2. Целостность и проверка бэкапа (непроверенный = нет бэкапа)

**Решение.** Бэкап валиден, только если ПРОВЕРЕН:
- `kalita verify` на восстановленной копии: hash-цепочка + подписи + чекпоинт
  (работает без plaintext-ключей субъектов — LLD-16 §3).
- Сверка блобов: для каждого file-ref в журнале блоб присутствует и его хэш
  совпадает (content-addressed — «битый/подменённый файл» ловится).
- Регулярное restore-учение на чистой машине (DoD 12) — не «бэкап лежит», а
  «из него поднялся консистентный узел».

## 3. Ключи и erasure-safe бэкап (ядро, ревью Fable — стык LLD-16)

**Решение (envelope-шифрование, уточняет LLD-16).**
- Перс.данные шифруются полевым ключом **DEK**, DEK обёрнут ключом субъекта
  **KEK**. В событии/бэкапе едет ТОЛЬКО обёрнутый DEK (`{ct, wrapped_dek,
  key_id}`). KEK живёт в отдельном МАЛЕНЬКОМ key-store, НЕ в журнале и НЕ в
  data-бэкапе.
- **Стирание субъекта (LLD-16 §4) = уничтожение KEK** в live key-store И в
  key-бэкапах (их мало, sweep дёшев). После этого обёрнутые DEK'и во всех
  data-бэкапах (большие, неизменяемые) становятся нерасшифровываемыми — бэкап
  НЕ нужно догонять/переписывать. Так append-only data-бэкап и право на забвение
  сосуществуют: чистим крохотный KEK-стор, не трогаем неизменяемый журнал.
- Итог разделения: **data-бэкап** (журнал+файлы+обёрнутые DEK) — можно хранить
  долго, шифрован ключом бэкапа; **key-бэкап** (KEK субъектов + ключ узла) —
  свой строгий lifecycle, короче retention, sweep при стирании (LLD-18 хранит
  ключ узла/эпохи).

## 4. Restore / DR-процедура (runbook, DoD 12)

**Решение.** `kalita restore <backup-set>` → развернуть журнал+файлы → внести
key-манифест → replay до seq → `kalita verify` → smoke (/healthz,/readyz) →
событие `node.restored {from_backup, seq}`. Runbook (O10) с критерием успеха
«verify зелёный + узел отвечает + внешний якорь §5 подтверждает голову».
Учение — на чистой машине, нетехнарём по таймеру.

## 5. Внешний якорь чекпоинтов (O3)

**Решение.** Экспорт головы чекпоинта во ВНЕШНИЙ, не зависящий от узла якорь —
доказательство «не переписан» без веры оператору (против компрометации узла,
шире T4):
- v1: экспорт подписанного чекпоинта в клиентский офлайн-бэкап (уже возможно) +
  опционально RFC-3161 TSA (доверенная метка времени) или публикация хэша
  головы (нотариус/реестр). Якорь — ДЕКЛАРАТИВНЫЙ конфиг (тип, периодичность),
  сам факт — событие `checkpoint.anchored {seq, anchor_type, receipt}`.
- Egress якоря — под тем же правилом, что все внешние вызовы (SECURITY правило 3:
  объявленный egress воркера), не скрытый вызов из ядра. По умолчанию — офлайн-
  экспорт в контуре; TSA/нотариус — явный флаг (триггер: спор/страховка).
- `kalita verify --anchor <receipt>` сверяет голову журнала с внешней меткой.

## 6. Приёмочные тесты (фиксированы)

1. `TestBackupSetConsistentAtCheckpoint` — набор на seq чекпоинта содержит все
   ссылаемые блобы и key-манифест; restore→replay даёт согласованные проекции.
2. `TestBackupVerifyCatchesCorruption` — подмена блоба/события в бэкапе → verify/
   хэш-сверка ловит и указывает место.
3. `TestRestoreDrill` — потеря диска → restore на чистой машине → verify зелёный,
   узел отвечает, `node.restored` записан.
4. `TestErasedSubjectStaysErasedAfterRestore` — стёрли субъекта (KEK уничтожен) →
   restore из СТАРОГО data-бэкапа НЕ воскрешает его данные (обёрнутый DEK
   нерасшифровываем без KEK). Ключевой стык с LLD-16.
5. `TestExternalAnchorRoundtrip` — экспорт якоря → `checkpoint.anchored`;
   `verify --anchor` подтверждает голову; расхождение головы → fail.
6. Golden/I-1: узел без бэкап/якорь-событий реплеится как прежде.

## 7. PR-нарезка

PR-1: бэкап-набор + точка согласованности + `kalita verify` бэкапа + блоб-сверка
      (тесты 1, 2).
PR-2: envelope DEK/KEK + разделение data-/key-бэкапа + erasure-safe (тест 4).
      ← **ревью Fable** (согласование с LLD-16, необратимо).
PR-3: `kalita restore` + DR-runbook + учение (тест 3).
PR-4: внешний якорь (офлайн-экспорт v1, TSA за флагом) + `verify --anchor`
      (тест 5).

**Порядок:** PR-1/PR-3 — до передачи узла клиенту (нельзя ставить в прод без
проверенного restore). PR-2 — синхронно с LLD-16 PR-1 (общая envelope-модель).
PR-4 — при первом требовании доказательства регулятору (эскиз готов).
