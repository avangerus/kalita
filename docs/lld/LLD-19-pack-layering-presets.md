# LLD-19 — слоёная модель паков: `dsl.core.*`, отраслевые пресеты, клиентский оверлей

Дата: 2026-07-02. Автор решений: Fable. Реализация: Sonnet 5 по документу.
Родитель: ADR-003/004 (WordPress-модель, buildless), T8 (четырёхслойный тест
принадлежности), LLD-03 (upgrade/эры), LLD-13 (data-pack), LLD-14 (headless UI).
Формализует продуктовый хребет: как kalita поставляет отраслевые решения, не
переписывая их под каждого клиента.

**Мотив (фаундер).** Клиенты хотят: (1) БЭК построенный быстро; (2) ДИЗАЙН —
свой. И мы не хотим «таскать» — пересобирать вертикаль под каждого. Ответ:
**слои паков над `dsl.core.*`** — отраслевые пресеты собираются из общего ядра,
клиент кастомизирует ОВЕРЛЕЕМ (не правкой пресета), фронт — свой через headless.

**Ловушка, которую этот LLD закрывает.** «Преднастроенные DSL-конфиги» сами по
себе НЕ убирают «таскать»: если клиент правит пресет НА МЕСТЕ, его копия
расходится, апгрейд = ручной merge. Убирает «таскать» только СЛОЙНОСТЬ: пресет
нетронут и апгрейдим, изменения клиента — отдельный слой; `dsl.core.*` —
стабильный версионированный API.

**Границы для исполнителя.** Sonnet НЕ решает сам: `dsl.core.*` — стабильный
API, только аддитивные изменения + своя версия (§2, необратимо, ревью Fable);
клиентская кастомизация — ОВЕРЛЕЙ + точки расширения, не in-place правка пресета
(§4, необратимо — это и решает «таскать»); namespace-резолюцию слоёв (§3);
что апгрейд пресета сохраняет оверлей через replay-as-migration (§5, LLD-03).

---

## 1. Пять слоёв (уточняет T8)

| Слой | Что | Кто владеет | Темп изменений |
|---|---|---|---|
| **L0 Go-ядро** | рантайм, компилятор DSL, event-store, Permission Engine | мы | редко («в ядро — смелым») |
| **L1 `dsl.core.*`** | DSL-стандартная библиотека: `core.User/Comment`, базовые роли, общие workflow/миксины | мы | аддитивно, версионировано |
| **L2 отраслевой пресет** | вертикаль из L1 (legal, servicedesk, crm…): сущности + дефолт-workflow + роли + data-pack + дефолт-схемы UI | мы (релиз) | релизами, апгрейдим |
| **L3 клиентский оверлей** | аддитивная кастомизация + заполнение точек расширения пресета | клиент | свободно, переживает апгрейд L2 |
| **L4 фронт + воркеры** | свой дизайн (headless LLD-14), интеграции (воркеры T8) | клиент | свободно |

Ключ: L2 и L1 — НАШИ, нетронуты у клиента → апгрейдимы. L3/L4 — клиента →
не ломаются нашим апгрейдом. «Бек быстро» = поставить L1+L2; «дизайн свой» = L4.

## 2. `dsl.core.*` — стабильный версионированный API (необратимо, ревью Fable)

**Решение.** `dsl.core.*` — это СТАНДАРТНАЯ БИБЛИОТЕКА DSL, импортируемая ВСЕМИ
паками → она публичный API с гарантией стабильности:
- Изменения только АДДИТИВНЫЕ (новые сущности/поля/роли/миксины); удаление/
  переименование/смена типа существующего символа `core.*` — запрещено вне эры
  (I-1 на уровне DSL-библиотеки). Ломать `dsl.core.*` = ломать все пресеты сразу.
- Своя версия `core.version`; пак объявляет `requires core >= X` (механика
  `requires kalita >= X` уже есть — распространить на core-lib). Несовместимость
  ловится при compose, не в рантайме.
- Состав L1 растёт по правилу ВТОРОГО потребителя: символ переезжает в `core.*`,
  только когда его просит второй пак (иначе живёт в паке-авторе). `core.User/
  Comment` — уже там; кандидаты — Attachment, Address, Money-mixin, Auditable.

## 3. Namespace и резолюция слоёв

**Решение.** Явные namespace: `core.*` (L1) / `<industry>.*` (L2, напр.
`legal.Contract`) / `<client>.*` (L3, напр. `acme.RiskTag`). Резолюция при
compose снизу вверх; `ref[legal.Contract]`, `ref[core.User]` работают через
границы слоёв. Коллизия имён между слоями — ошибка compose с указанием слоёв
(не тихое затенение). Клиент не может определять символы в `core.*`/`<industry>.*`
(чужой namespace) — только в своём `<client>.*` (изоляция оверлея).

## 4. Кастомизация = оверлей + точки расширения (необратимо — решает «таскать»)

**Решение (не обсуждается — это ядро анти-«таскать»).** Клиент НЕ правит файлы
пресета. Кастомизация — отдельный оверлей-пак `<client>.*`, применяемый ПОВЕРХ
пресета:
- **Аддитивно (дефолт, I-1):** клиент добавляет сущности/поля/роли/схемы UI в
  своём namespace — пресет нетронут, апгрейд L2 не конфликтует.
- **Точки расширения:** пресет ОБЪЯВЛЯЕТ, что можно донастроить без форка —
  hook’и workflow (доп. переход/гард), слоты схем UI, параметры (ставки, SLA,
  лейблы, бренд §H7.4). Клиент заполняет объявленные точки — контракт апгрейда
  их сохраняет (WordPress parent/child: пресет=parent, оверлей=child).
- **Глубокий override** (заменить переход/право/поле пресета) — ВОЗМОЖЕН, но
  переводит клиента в явное состояние «diverged»: событие/пометка, апгрейд L2
  такого символа требует ревью (не тихий merge). Дивергенция — осознанный выбор
  с ценой, а не дефолт. Так «таскать» не возникает по умолчанию, но не запрещено
  тем, кто готов платить.

## 5. Апгрейд пресета через слои (LLD-03)

**Решение.** Апгрейд L1/L2 = замена НАШИХ слоёв новой версией → recompose с
неизменным L3-оверлеем → replay-as-migration (LLD-03: аддитивное = бесплатно;
деструктивное в пресете = эра с runbook). Оверлей клиента переживает, если
трогал только точки расширения/свой namespace. `kalita upgrade` проверяет
`requires core`/`requires <industry>` совместимость ДО применения. Дивергентные
override (§4) — в отчёте апгрейда как требующие внимания.

## 6. Фронт: бек быстро + дизайн свой (LLD-14)

**Решение.** L2-пресет ПОСТАВЛЯЕТ дефолтные схемы UI (faces=именованные схемы,
DESIGN-REVIEW A1) → работает из коробки. Клиент (L4) либо оставляет их, либо
рисует свой фронт целиком через headless-контракт (данные+поведение+права,
LLD-14 §2) — не трогая L0–L3. «Бек быстро» и «дизайн свой» — буквально два конца
одного контракта.

## 7. Упрощающий вывод (не усложняющий)

12 продуктов портфеля + отраслевые пресеты + клиентские решения — это ОДИН
механизм: слоёные паки над `dsl.core.*`. Не 12 самописных продуктов, а
композиции слоёв. Это снимает сложность портфеля, а не добавляет: апгрейд,
дистрибуция, кастомизация — одни правила для всех вертикалей (стык DESIGN-REVIEW).

## 8. Приёмочные тесты (фиксированы)

1. `TestCoreLibVersionGate` — пак с `requires core >= X` при несовместимом
   `dsl.core.*` → ошибка compose, не рантайм; аддитивный рост core не ломает
   старый пак (I-1).
2. `TestPresetInstallsFromCore` — отраслевой пресет (L1+L2+data-pack+схемы)
   ставится и работает из коробки; дефолт-схемы рендерятся (LLD-14).
3. `TestClientOverlayAdditive` — оверлей `<client>.*` добавляет сущность/поле;
   пресет нетронут; namespace-коллизия между слоями → ошибка compose.
4. `TestPresetUpgradePreservesOverlay` — апгрейд L2 v1→v2 (аддитивный) →
   оверлей клиента цел, replay консистентен (LLD-03); эра при деструктивном.
5. `TestExtensionPointVsDivergence` — заполнение объявленной точки расширения
   переживает апгрейд без пометки; глубокий override → состояние diverged +
   отчёт апгрейда.
6. `TestHeadlessFrontendSwap` — клиент подменяет фронт через headless, бек L0–L3
   не изменён; governance/права те же (LLD-14 §2).
7. Golden/I-1: одиночный пак без слоёв/оверлея компилируется и реплеится как был.

## 9. PR-нарезка

PR-1: namespace `core.*/<industry>.*/<client>.*` + резолюция при compose +
      коллизии (тест 3). ← **ревью Fable** (модель имён — фундамент слоёв).
PR-2: `dsl.core.*` как версионированная либа + `requires core` + аддитив-гейт
      (тесты 1). ← **ревью Fable** (стабильный API — необратимо).
PR-3: пресет-сборка (L1+L2+data-pack+дефолт-схемы) + инсталл (тест 2).
PR-4: оверлей-модель + точки расширения + diverged-состояние (тесты 3, 5).
      ← **ревью Fable** (анти-«таскать» контракт — необратимо).
PR-5: апгрейд через слои (стык LLD-03) + отчёт дивергенции (тест 4).

**Порядок:** L1/namespace (PR-1/2) — фундамент, но НЕ строить наперёд всю
machinery: минимально — под ВТОРОЙ пресет (правило второго потребителя;
Legal — первый, второй вскроет реальные точки расширения). До тех пор пресет =
обычный пак; слоёная machinery включается на втором клиенте/вертикали
(дисциплина DESIGN-REVIEW A4: карта, не порядок стройки).
