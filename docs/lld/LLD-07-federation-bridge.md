## 1. Что такое bridge (модель)

Bridge — воркер с ДВУМЯ identity: governed-актор на узле-источнике (роль с
`read`-grant на нужные сущности + `read_journal`) и governed-актор на
узле-приёмнике (роль с `emit [Name]` или `create`-правами, least-privilege).
Он читает `event.emitted` из журнала источника и вызывает `emit_event` на
приёмнике. Никакой узел не знает о существовании другого напрямую — знает
только bridge (граница периметра остаётся явной).

```
узел A (источник)                bridge-worker              узел B (приёмник)
  journal.Since(seq) ──read──▶  cursor, map, retry  ──emit_event──▶  dispatch
  event.emitted{LeadWon}                                             on event → create Deal
```

## 2. Транспорт и exactly-once (формула — не обсуждается)

- Bridge держит курсор `last_seq` на источник. Цикл: `GET journal since=last_seq`
  (через MCP `read_journal` или REST) → для каждого `event.emitted`,
  подпадающего под подписку конфига → `emit_event` на приёмник → продвинуть
  курсор ПОСЛЕ подтверждённой доставки.
- **exactly-once = at-least-once + идемпотентный ключ.** Ключ доставки =
  `bridge|<source_node_id>|<source_seq>` (детерминирован из события источника).
  При падении bridge между доставкой и продвижением курсора — повтор с тем же
  ключом; `ByIdemKey` на приёмнике (PR-5 сделал idempotency обязательной)
  схлопывает дубль. Курсор — не критичное хранилище: потеря = переигрывание
  от меньшего seq, идемпотентность спасает. **Отдельный durable-курсор не
  обязателен для корректности** (только для эффективности — bridge может
  восстановить его как `max source_seq`, уже отражённый на приёмнике, если
  origin-провенанс §3 включён).
- НИКАКОГО sync-RPC: bridge читает журнал (pull), пишет через emit_event —
  обе стороны асинхронны. Узел-источник не ждёт узла-приёмника никогда.

## 3. Cross-node ref v1 — зеркальная запись (mirror), не удалённый лукап

`ref[X]` остаётся локальным (TECHDEBT: удалённый лукап не делаем). Вместо
этого — зеркало:
- Пак приёмника объявляет сущность с полем провенанса
  `origin: ref[core.Origin]?` где `core.Origin` = `{node_id: string,
  remote_id: string}` — НОВЫЙ core-pack-примитив (проверить: возможно, хватает
  двух string-полей в самой сущности без нового типа — тогда internal/ не
  трогаем, это предпочтительно). Подписчик `on event` на приёмнике создаёт
  локальную запись, кладя в origin `{node_A, remote_id}`.
- Идемпотентность создания зеркала: ключ `emit_event` (§2) гарантирует, что
  повтор события не создаст второе зеркало.
- `remote[node.Entity]` из DSL-SPEC §10b остаётся ЗАРЕЗЕРВИРОВАННЫМ (слой 3) —
  в v1 не реализуем.

## 4. Identity-якорь v1

- Пара bridge-акторов регистрируется на обоих узлах обычным `kalita agent add`
  (события `actor.registered` на каждом) — взаимной регистрации достаточно для
  доказательства принадлежности в v1. Общий root доверия / shared authority —
  слой 3, НЕ здесь.
- Секреты (токены обоих узлов) — в конфиге воркера (T8, SECURITY #5), не в DSL.

## 5. Конфиг bridge (данные, не код)

`workers/bridge/config` (env или файл 0600): `SOURCE_URL`, `SOURCE_TOKEN`,
`TARGET_URL`, `TARGET_TOKEN`, `SOURCE_NODE_ID`, и подписки — список
`{event: "crm.LeadWon", target_action: "emit", target_event: "sales.DealSeeded",
field_map: {...}}`. Маппинг полей события источника в payload события
приёмника — декларативная таблица, не код.

## 6. Прототип-доказательство (что строим сейчас)

Два узла на одной машине (разные порты, разные Postgres-схемы/базы —
`kalita_a`, `kalita_b`), демо-сценарий из README «лид с сайт-узла → сделка в
CRM-узле»:
- узел A: мини-пак `site` с `event LeadCaptured(name, company, email)`,
  эмитится при создании/переходе Lead;
- узел B: пак `crm` (существующий) с `on event site.LeadCaptured: create Lead(...)`
  ИЛИ отдельной сущностью-приёмником;
- bridge переносит событие; проверяется: лид появился на B ровно один раз;
  повторный прогон bridge с того же курсора НЕ создаёт дубль (exactly-once);
  origin на записи B указывает на A.
- Скрипт `deploy/federation-demo/` поднимает оба узла + bridge (по образцу
  deploy/knowvault).

## 7. Приёмочные тесты (фиксированы)

1. `TestBridgeDeliversOnce` (интеграционный, два MemStore-узла в одном
   процессе через тестовые обёртки, ИЛИ два реальных узла в docker-демо):
   событие на A → ровно одна запись на B; origin = {A, remote_id}.
2. `TestBridgeExactlyOnceOnReplay`: bridge перечитывает журнал A с seq=0
   повторно → на B по-прежнему одна запись (идемпотентный ключ §2).
3. `TestBridgeCrashBeforeCursorAdvance`: доставка прошла, курсор не продвинут,
   рестарт bridge → повтор доставки → дубля на B нет.
4. `TestBridgeLeastPrivilege`: bridge-актор на B имеет только `emit`/`create`
   грант — попытка иного действия отклонена Permission Engine.
5. `TestNoSyncRPC` (архитектурный, ревью + отсутствие кода): узел A не
   содержит вызова узла B; вся связь — через bridge-worker. (Проверяется
   grep'ом: internal/ не импортирует и не адресует чужой узел.)

Тесты 1–4 — в workers/bridge (python, как прочие воркеры) + один Go-тест на
идемпотентность emit_event на стороне приёмника, если не покрыт PR-5.
