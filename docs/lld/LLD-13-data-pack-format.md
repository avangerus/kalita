# LLD-13 — формат data-pack: поставка справочных данных (T9)

Дата: 2026-07-02. Автор решений: Fable. Реализация: Sonnet 5 по документу.
Родитель: RELEASE-1.0 §3 R3 (data-packs формат, T9), HLD-V1 §H10 (bulk-профиль
P2), MASTERPLAN (производственный календарь РФ как первый потребитель).
Зависимости: LLD-01 §5 (идемпотентность), пак-манифест, bulk-create путь.

**Мотив.** Пак сегодня = DSL (схема + логика), но многие вертикали требуют
СПРАВОЧНЫХ ДАННЫХ: производственный календарь РФ (рабочие/выходные/сокращённые
дни — нужен дебиторке/HR для сроков), справочники валют/стран/ставок НДС,
классификаторы. Сейчас положить их некуда, кроме ручного create — не
воспроизводимо, не версионируемо, не поставляемо как часть продукта.

**Границы для исполнителя.** Sonnet НЕ решает сам: что справочные данные — это
обычные governed-записи в журнале, а НЕ второй механизм хранения (§1,
необратимо — вводить параллельное read-only хранилище запрещено, это раскол
единственной истины); идемпотентный ключ поставки (§2 — re-install и обновление
не должны дублировать, необратимо); что обновление справочника аддитивно
(§3, I-1). Формат файла — по §4, но семантика загрузки фиксирована здесь.

---

## 1. Модель (не обсуждается): справочник = seed-записи в журнале

**Решение.** Data-pack НЕ вводит нового хранилища. Справочные строки
материализуются как обычные `record.created` под ролью пака при установке —
governed по построению: версионируются, аддитивны, реплеятся, доступны через
обычные query/ref, подчиняются ABAC. «Второй слой read-only данных» —
запрещённая альтернатива (раскол истины, обход choke point I-2).
- Целевая сущность объявлена обычным `entity` в DSL пака (напр.
  `entity CalendarDay { date, kind: enum[work,weekend,short,holiday] }`).
- Ссылки на справочник из других записей — обычный `ref[CalendarDay]`.

## 2. Идемпотентная поставка (необратимо — ключ)

**Решение.** Каждый датасет объявляет НАТУРАЛЬНЫЙ ключ; загрузка идемпотентна
по `{pack, dataset, natural_key}` (LLD-01 §5):
- Первая установка пака → bulk-create недостающих строк (профиль P2, LLD-12).
- Повторная установка / рестарт → НИ ОДНОГО дубля (ключ уже в журнале).
- Это же свойство делает загрузку безопасной при kill-9 посередине bulk
  (op-скобки LLD-01 §2 + идемпотентность — доигрывается без дублей).

## 3. Обновление справочника (аддитивно, I-1)

**Решение.** Новый релиз data-pack (календарь следующего года, новая ставка НДС)
= НОВЫЕ строки с новыми натуральными ключами → добавляются, старые не трогаются.
- Изменение существующей строки (исправление ошибки в справочнике) —
  обычный governed update по натуральному ключу (журналируется, откатываемо),
  НЕ переустановка.
- Удаление устаревших — обычный governed путь (не «перезалив»). Так справочник
  живёт по правилам платформы, а не особым механизмом.
- Деструктивная смена схемы справочника — через эру пака (LLD-03), как любая
  сущность.

## 4. Формат файла и манифест

**Решение (форму фиксируем, детали сериализации — исполнителю).**
- Данные: `packs/<pack>/data/<dataset>.jsonl` — по строке-записи на линию
  (JSONL, чтобы bulk стримился, не грузился целиком — согласуется с P2).
- Декларация в манифесте пака: секция `data { <dataset>: entity=<Entity>,
  key=<field|[fields]>, file=<path> }` — generic-загрузчик читает манифест,
  НЕ кодируется под конкретный справочник (правило второго потребителя: календарь
  первый, генерализация — на втором датасете).
- Установка: `kalita pack install` (или существующий путь установки пака)
  прогоняет data-секции → идемпотентный bulk-create под ролью пака, событие
  `data.seeded {pack, dataset, count}` (сколько реально добавлено — виден факт).

## 5. Первый потребитель

Производственный календарь РФ: `entity CalendarDay` + `data/calendar-ru-2026.jsonl`
+ `data/calendar-ru-2027.jsonl`. Демонстрирует: bulk-установку, идемпотентность
(двойная установка = 0 дублей), аддитивное расширение (добавили 2027 — 2026
цел), ref из дебиторки на CalendarDay для расчёта сроков. Генерализация формата
— строго на ВТОРОМ датасете (валюты/НДС), не раньше (правило второго потребителя).

## 6. Приёмочные тесты (фиксированы)

1. `TestDataPackInstallSeeds` — установка пака с data-секцией → строки как
   record.created под ролью пака; `data.seeded` с верным count.
2. `TestDataPackIdempotent` — повторная установка / рестарт → 0 дублей
   (ключ `{pack,dataset,natural_key}`).
3. `TestDataPackAdditiveUpdate` — установка календаря-2027 поверх 2026 →
   2026 не тронут, 2027 добавлен (I-1).
4. `TestDataPackBulkResilient` — kill-9 посреди bulk → рестарт → полный
   справочник без дублей (op-скобки + идемпотентность).
5. `TestDataPackRefUsable` — ref[CalendarDay] из другой сущности резолвится,
   ABAC применяется (справочник — обычные governed-записи).
6. Golden/I-1: пак без data-секции устанавливается как прежде; старый журнал
   реплеится без изменений.

## 7. PR-нарезка

PR-1: манифест-секция `data` + generic-загрузчик + идемпотентный bulk +
      `data.seeded` (тесты 1, 2, 4).
PR-2: производственный календарь РФ как пример-датасет + ref-потребитель
      (тесты 3, 5).

**Порядок:** независим от UI/transport; зависит только от bulk-профиля P2
(LLD-12) для замера установки крупного справочника. Может идти параллельно
любой волне (зона — packs/, установочный путь).
