# LLD-18 — секреты и жизненный цикл ключей: хранение, инъекция, ротация (O4)

Дата: 2026-07-02. Автор решений: Fable. Реализация: Sonnet 5 по документу.
Родитель: PROD-READINESS §O4, SECURITY P1 #5 (секреты), EVENT-STORE §3/§4
(ключ узла, `actor.key_rotated`). Инвариант I-4 (секреты только node/worker),
I-5 (офлайн-доказуемость). Связь: LLD-16/17 (KEK субъектов), LLD-02 (WebAuthn).

**Мотив.** Три эксплуатационных дыры вокруг секретов: (1) PG DSN в env/.env
(SECURITY P1 #5) — нужен файл 0600/docker-secrets; (2) ключ УЗЛА подписывает
чекпоинты — его ротация не должна рвать проверяемость старых чекпоинтов (I-5);
(3) инъекция секретов в воркеров без утечки в журнал/DSL. `actor.key_rotated`
для акторов уже есть — нужна аналогичная эпоха для ключа узла и дисциплина
verify по эпохам.

**Границы для исполнителя.** Sonnet НЕ решает сам: эпоховую модель ключа узла —
verify выбирает ключ по эпохе события, ротация не рвёт I-5 (§2, необратимо,
ревью Fable); что секреты НИКОГДА не в DSL/журнале, только node/worker (§1/§3,
I-4); что ротация — журналируемое событие с overlap-периодом (§2). Крипто-
примитивы не менять (Ed25519 узел/агент, WebAuthn человек — EVENT-STORE §4).

---

## 1. Инфра-секреты: хранение (SECURITY P1 #5)

**Решение.** DSN, TLS-ключи, токены воркеров — из конфиг-файла с правами 0600
и/или docker/systemd secrets, НЕ из общего env и НЕ из .env в образе:
- `kalita` читает секреты из указанного secret-пути; отсутствие/слабые права
  (не 0600) → отказ старта с внятной ошибкой (fail-fast, стык O6 config-check).
- В журнал секрет попадает ТОЛЬКО как хэш (SECURITY правило 5) — распространить
  на все новые пути. `kalita config check` не печатает значения секретов.

## 2. Ротация ключа узла: эпохи (ядро I-5 — ревью Fable)

> **НЕ реализовано (STATUS.md, post-release PR-2)** — `node.key_rotated`/
> `key_epoch` в коде нет; есть только `actor.key_rotated` (registry.go:362).

**Решение (не обсуждается).** Ключ узла подписывает чекпоинты; его нельзя
«просто заменить» — старые чекпоинты должны остаться проверяемыми.
- Ротация = событие `node.key_rotated {epoch, new_pubkey, at}` в журнал. Каждый
  `checkpoint.sealed` несёт `key_epoch`. `kalita verify` выбирает публичный ключ
  по эпохе чекпоинта — старые чекпоинты валидны под старым ключом, новые под
  новым. I-5 сохранён через границу ротации.
- **Overlap:** старый ключ остаётся валидным для верификации НАВСЕГДА (публичный,
  в журнале); приватный старый выводится из активной подписи после ротации.
  Компрометация ключа → ротация + пометка эпохи как compromised (событие) —
  чекпоинты скомпрометированной эпохи требуют перекрёстной проверки внешним
  якорем (LLD-17 §5).
- Список публичных ключей по эпохам — из журнала (offline verify самодостаточен:
  `kalita verify --pub` берёт эпохи из журнала, не из живого узла).

## 3. Ротация ключей акторов/агентов

**Решение.** `actor.key_rotated` (уже в taxonomy) — верификация подписи события
использует ключ актора, ВАЛИДНЫЙ НА МОМЕНТ события (по ts/seq), не текущий:
- Старые подписи агента остаются проверяемыми после ротации его ключа (как
  человеческие подписи после перерегистрации passkey — LLD-02 §4).
- Отзыв ключа (компрометация) → `actor.disabled`/новая регистрация; подписи ДО
  отзыва валидны, ПОСЛЕ — нет (граница по seq события отзыва).

## 4. Инъекция секретов воркерам (I-4)

**Решение.** Воркер (agent_runner, connector, bridge, chat_runner, product_mcp)
получает секреты (API-ключ модели, токен коннектора, свой identity-токен) через
env/примонтированный secret-файл процессного слоя — НЕ через DSL, НЕ из журнала:
- В паке — только ДЕКЛАРАЦИЯ потребности («этому воркеру нужен секрет X»),
  значение — на деплое (docker secret). Egress-домены воркера декларируются
  (LLD-09 §3, SECURITY правило 3).
- Least-privilege identity воркера (паттерн inbound.py/bridge) — токен воркера
  скоупится минимальными правами; утечка токена воркера ограничена его ролью
  (I-2). Ротация токена воркера = отключить старого актора + выдать нового.

## 5. Субъектные KEK (стык LLD-16/17)

**Решение.** KEK субъектов (крипто-шреддинг) — часть key-store под этим же
lifecycle: генерация при первом pii-событии субъекта, уничтожение при
`subject.erased`, отдельный key-бэкап со sweep (LLD-17 §3). KEK не в журнале
(I-4), не в data-бэкапе.

## 6. Приёмочные тесты (фиксированы)

1. `TestSecretsFromFile0600` — секреты из файла 0600 читаются; слабые права/
   отсутствие → отказ старта; секрет не печатается в config check; в журнале —
   только хэш.
2. `TestNodeKeyRotationEpochs` — ротация ключа узла → `node.key_rotated`;
   старые чекпоинты verify под старой эпохой, новые под новой; offline verify
   берёт эпохи из журнала (I-5).
3. `TestOldAgentSignatureVerifiesAfterRotation` — подпись агента до ротации его
   ключа остаётся валидной; после отзыва — новые отклонены с seq-границы.
4. `TestWorkerSecretNotInJournalOrDsl` — секрет воркера не появляется в DSL/
   журнале; пак содержит лишь декларацию потребности.
5. `TestCompromisedEpochFlagged` — пометка эпохи compromised → чекпоинты этой
   эпохи требуют внешнего якоря (стык LLD-17).
6. Golden/I-1: узел без ротаций реплеится как прежде; verify старого журнала цел.
