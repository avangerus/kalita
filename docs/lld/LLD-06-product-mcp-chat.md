# LLD-06 — продуктовый MCP-façade + операторский чат (KChat)

Дата: 2026-07-02. Автор решений: Fable. Реализация: Sonnet 5 по документу.
Родитель: HLD-V1 §H7.2 (PK-2), §H7.3 (PK-3). Зависимости: LLD-05 (faces/atoms,
ChatFace), LLD-01 PR-5 (emit_event, идемпотентность MCP), H4 (периметр/promptbox).
Снимает с паузы ENH-09. Зона: workers/, packages/ (ChatFace), небольшой
core/product pack `assistant`.

**Границы для исполнителя.** Sonnet НЕ решает сам: модель auth §1 (строгий
pass-through — САМОЕ важное решение обоих PK, ошибка = дыра в правах); то, что
чат-история — обычные governed-сущности §2 (не отдельное хранилище — иначе
диалог вне аудита); что HITL чат НЕ обходит §2. В ядре (internal/) изменений
быть НЕ должно — façade и chat-runner суть Worker (T8), общаются с узлом только
по MCP под токеном пользователя.

---

## 1. PK-2 — продуктовый MCP-façade

Воркер `workers/product_mcp/` (stdlib-only): экспонирует доменные MCP-тулы
поверх узлового MCP — KnowVault: `kv.search / kv.ask / kv.upload`;
Legal: `legal.submit_contract / legal.findings`. Каждый тул = композиция
узловых вызовов (query/create/act/emit_event/search_perimeter).

- **Auth: строгий pass-through (НЕ обсуждается).** Façade НЕ имеет собственного
  токена на мутации. Он ТРЕБУЕТ bearer конечного пользователя во входящем
  вызове и проксирует ИМЕННО его на узловой MCP. Следствие (HLD I-2): права,
  ABAC, аудит, rate-limit, HITL остаются точными — façade добавляет СЕМАНТИКУ
  (удобные доменные тулы), но НОЛЬ полномочий. Актор в журнале = пользователь,
  не «сервисный аккаунт продукта». Любой тул, которому «нужен свой токен для
  записи», — красный флаг, отклонить дизайн.
- **Реестр тулов — данные пака, не код воркера**: секция `product.mcp` в
  манифесте пака описывает доменные тулы (имя, входы, композиция из узловых
  вызовов декларативно). Generic faças-воркер читает манифест — не кодируется
  под конкретный продукт (иначе каждый продукт = новый воркер).
- Периметр: тулы, принимающие внешний текст (kv.upload, submit_contract),
  прогоняют его через promptbox/детектор (LLD-01 §6, H4) перед узловым вызовом.

«Чат с рабочим пространством, где аудит/права/RAG уже в чате» = любой
MCP-клиент (Claude Desktop, кастомный), подключённый к этому продуктовому MCP.
ENH-09 реализуется в этой рамке: локальная модель — сразу; облачная — после
egress-DLP (правило конфигурации H4).

## 2. PK-3 — операторский чат в UI (KChat + chat-runner)

Чат для нетехнаря ВНУТРИ узла (не внешний Claude Code — тот уже работает через
узловой MCP). Две части:

- **Пак `assistant`** (обычный DSL-пак): `entity Session {owner: ref[core.User],
  title, started_at}` и `entity Message {session: ref[Session], role: enum[user,
  assistant, tool], body: text, created_at}`. Права `where session.owner = $me`.
  Следствие: **диалог governed по построению** — аудит, retention, ABAC, undo
  приходят бесплатно из ядра; чат-история не выходит за периметр и не является
  отдельным нетронутым хранилищем.
- **Воркер `workers/chat_runner/`**: локальная LLM + MCP-loop ПОД АКТОРОМ
  пользователя (pass-through, как §1). Инструменты в loop = узловой MCP +
  продуктовые façade-тулы. Каждое действие из чата = обычное журналируемое
  действие этого пользователя; **HITL-гейты срабатывают как есть** — если
  агент в чате инициирует переход, требующий подписи, он паркуется в approval-
  инбокс, чат его не обходит (I-2). Промпт собирается через promptbox (H4):
  сообщения пользователя — данные, не команды.
- **ChatFace** (organism из LLD-05): окно чата, поток Message, кнопка «спросить
  свою систему / сделай за меня»; рендерит pending-approval, если действие
  чата упёрлось в HITL.

## 3. Приёмочные тесты (фиксированы)

1. `TestFacadePassThrough` — façade-тул, вызванный с bearer пользователя A,
   пишет в журнал под актором A; без bearer → отказ; façade НЕ имеет токена,
   способного писать самостоятельно.
2. `TestFacadeRespectsABAC` — пользователь без прав на сущность зовёт доменный
   тул → denied тем же Permission Engine (façade ничего не «расширяет»).
3. `TestFacadeToolFromManifest` — доменный тул описан в product.mcp манифеста,
   generic façade его отдаёт; неизвестный продукт не требует правки воркера.
4. `TestChatActionIsJournaledAsUser` — действие из chat-runner под актором
   пользователя = обычное событие с actor=пользователь.
5. `TestChatDoesNotBypassHITL` — действие чата, требующее approval(Role),
   паркуется в инбокс, не исполняется до подписи.
6. `TestChatHistoryIsGoverned` — Message виден только owner сессии (ABAC),
   попадает в аудит-журнал, поддерживает undo.
7. Периметр: kv.upload/submit_contract с отравленным текстом → детектор
   флагует (переиспользование honeypot-корпуса), узловой вызов не исполняет
   инъекцию.
