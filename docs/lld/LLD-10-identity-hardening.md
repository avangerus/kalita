# LLD-10 — identity hardening: атомарность, инвайт-проекция, lockdown, rate-limit (N7)

Дата: 2026-07-02. Автор решений: Fable. Реализация: Sonnet 5 по документу.
Родитель: RELEASE-1.0 §N7, HLD-V1 (I-1..I-5). Зависимости: LLD-01 (события,
идемпотентность), паттерн инкрементальной проекции Registry (уже в ядре).
Ссылки на код — из сверки RELEASE-1.0 §7 (TOCTOU §7.12, инвайты §7.9,
constant-time bootstrap).

**Мотив.** Реестр акторов прост и хорош, но четыре дыры ломают «узел переживает
год чужими руками»: гонка регистрации (TOCTOU-дубль), инвайты через full-scan
журнала (O(журнала) на портальный онбординг, 0 покрытия у ~130 строк Redeem),
нет аварийного тормоза (lockdown, V1-GATE P1), нет rate-limit на auth. Consumer-
масштаб (тысячи внешних клиентов, OAuth) — сознательно НЕ здесь.

**Границы для исполнителя.** Sonnet НЕ решает сам: атомарность Register — под
одним захватом, проверка+Append неделимы (§1, необратимо — корректность прав);
семантику lockdown (§3 — аварийный admin, что именно инвалидируется, как
секрет выводится, необратимо, ревью Fable); что consumer-auth НЕ реализуется
(§5, за IdP-мостом). Ключи людей не хранятся на сервере (только публичные —
инвариант EVENT-STORE §4, не двигать).

---

## 1. Атомарность регистрации (необратимо — корректность)

**Решение.** `Register`/`EnsureActor` — проверка существования и Append нового
актора под ОДНИМ захватом Registry.mu (сейчас check и append раздельны —
TOCTOU §7.12: два конкурентных Register одного actor_id создают дубль).
- Идемпотентно: повторный Register того же (actor_id, ключ) → тот же результат,
  не второе событие (LLD-01 §5 идемпотентность).
- Гонка двух РАЗНЫХ ключей на один actor_id → один выигрывает, второй получает
  детерминированный отказ `ACTOR_EXISTS`, не молчаливую перезапись.

## 2. Инвайты — инкрементальная проекция (необратимо — производительность+корректность)

**Решение.** Инвайты переводятся с full-scan журнала (§7.9) на инкрементальную
проекцию по паттерну Registry: fold событий инвайтов в структуру
`token_hash → {invite, state: pending|redeemed|revoked}`.
- Redeem резолвится по индексу O(1), не сканом.
- Однократность: Redeem под захватом проверяет state==pending и Append'ит
  redeemed атомарно (та же TOCTOU-защита, что §1) — инвайт нельзя погасить дважды
  конкурентно.
- Покрытие: Redeem-путь (сейчас 0 у ~130 строк) — тесты happy + двойное гашение
  + revoked + expired.

## 3. `kalita lockdown` — аварийный тормоз (необратимо — ревью Fable)

**Решение (семантика железная, не обсуждается).**
- Событие `node.lockdown {emergency_admin_token_hash, at}` → проекция-флаг
  «узел в lockdown». Пока флаг стоит, `Authenticate` отклоняет ВСЕ токены,
  кроме одного аварийного admin.
- **Аварийный токен:** генерируется узлом в момент команды, выводится оператору
  в stdout ОДИН раз; в журнал попадает только его хэш (I-4 — секрет не в журнале).
  Роль аварийного actor — полный admin, единственная живая identity под
  lockdown.
- Снятие — событие `node.lockdown_lifted {at}`: прежние токены НЕ
  восстанавливаются автоматически валидными по умолчанию — они валидны, если не
  отозваны иным событием; lockdown лишь временно затыкает вход. (Решение: lockdown
  — заслонка аутентификации, НЕ массовый revoke; массовый отзыв — отдельная
  осознанная операция, чтобы lockdown был обратим одной командой.)
- Оба перехода журналируются и офлайн-видны (I-5): `kalita verify` показывает
  окна lockdown в истории.

## 4. Rate-limit и auth-fail-лог

**Решение.** IP-rate-limit на `/api` и `/mcp` входных точках аутентификации;
constant-time сравнение секретов (распространить bootstrap-паттерн, уже
constant-time — §N7).
- Провалы аутентификации агрегируются: НЕ по событию на попытку (иначе
  журнал-флуд при переборе), а порог → одно событие `auth.throttled {ip,
  window, count}` при срабатывании лимита (I-3 — факт защиты виден, но не
  ценой роста журнала).
- Лимит — узловой параметр (не DSL, I-4): токен-бакет per-IP, дефолты в конфиге.

## 5. Сознательно НЕ в 1.0

Consumer-auth (массовый self-signup, OAuth-соцвход, сброс пароля, GDPR-согласие)
— НЕ строить в ядре. Триггер разморозки: первое реальное требование публичного
портала → внешний IdP on-prem (Keycloak/Authentik) + воркер-мост, маппящий
внешние identity в акторов. Ядро не учится в OAuth (TECHDEBT P1, RELEASE-1.0 §5).
Пароль-как-credential актора (`actor.password_set`, /api/login → bearer) —
это LLD-05 §3/H7.4, НЕ consumer-масштаб, граница не двигается.

## 6. Приёмочные тесты (фиксированы)

1. `TestRegisterAtomicUnderRace` — N конкурентных Register одного actor_id
   (разные ключи) под `-race`: ровно один успех, остальные `ACTOR_EXISTS`,
   один актор в проекции.
2. `TestInviteProjectionRedeemOnce` — Redeem по проекции O(1); двойное
   конкурентное гашение → один успех; revoked/expired → отказ. (Закрывает
   0-покрытие.)
3. `TestLockdownInvalidatesAllButEmergency` — после `node.lockdown` прежние
   токены → 401 на обоих транспортах; аварийный токен работает; после
   `node.lockdown_lifted` прежние снова принимаются.
4. `TestLockdownSecretNotInJournal` — журнал содержит только хэш аварийного
   токена, не сам токен (grep-проверка события).
5. `TestAuthThrottle` — перебор с одного IP → отказ по лимиту + одно
   `auth.throttled`, не N событий.
6. Golden/I-1: старый журнал без новых событий реплеится без изменений;
   `kalita verify` показывает окна lockdown, если они есть.
