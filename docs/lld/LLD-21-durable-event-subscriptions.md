# LLD-21 — надёжные событийные подписки (умные интеграции)

Дата: 2026-07-02. Автор решений: Fable. Реализация: Sonnet 5 по документу.
Родитель: LLD-08 (read_events outbox), LLD-07 (bridge — доказанный паттерн),
LLD-01 §5 (обязательная MCP-идемпотентность), SECURITY правило 3 (объявленный
егресс). Инварианты I-1..I-6, особенно I-3 (ошибка — событие, не тихий стопор).

**Мотив.** Реакция на «что случилось в системе» сегодня делается хрупким
`webhook`-действием: движок создаёт TaskWebhook БЕЗ идемпотентности, ретраев,
гарантии доставки (fire-and-forget) — упал сервис в момент, вызов потерян;
повторилась automation, вызов ушёл дважды. При этом `bridge.py` УЖЕ делает это
правильно вручную (курсор на диске save-after-confirm, ключ `{node,seq}`,
transient-retry). Каждый интегратор катит свой цикл — нет переиспользуемого
примитива. Цель: обобщить bridge в надёжную обвязку-подписчик, сделать её
ДЕФОЛТОМ, а хрупкий webhook пустить через неё.

**Границы для исполнителя.** Sonnet НЕ решает сам: «ровно один раз» = at-least-
once + идемпотентность, курсор — лишь оптимизация (§3, необратимо — корректность,
ревью Fable); обвязка живёт В ВОРКЕРЕ (T8), ядро НЕ становится брокером — только
отдаёт поток (§2); governed-ошибка = dead-letter+событие, НЕ вечный стопор
курсора (§4, I-3); DSL-декларация подписки аддитивна (§5, I-1, ревью Fable —
новая поверхность компилятора + егресс-governance). Три формы интеграции НЕ
смешивать (§1).

---

## 1. Три формы интеграции (развести, перестать путать)

| Форма | Что | Механизм сегодня | Вердикт |
|---|---|---|---|
| **Read-capability** | синхронно ПРОЧИТАТЬ внешнее по запросу (пикер папок) | `integration` + `/api/call` proxy (GET к воркеру) | оставить как есть — это НЕ про события |
| **Inbound** | внешнее → узел (форма→Lead) | connector-воркер, idem per-request | оставить (inbound.py — образец) |
| **Event-подписка** | воркер НАДЁЖНО реагирует на события узла | руками (bridge.py), примитива нет | **этот LLD** |

`integration` (read) и `subscription` (react) — РАЗНЫЕ конструкции, не путать:
первая тянет данные для показа, вторая durable-реагирует на факты.

## 2. Обвязка-подписчик (воркерная библиотека — обобщение bridge.py)

**Решение.** Переиспользуемая библиотека `workers/lib/subscribe.py` (stdlib-only):
воркер = `subscribe(node, subscription_id, events=[...], handler=fn,
cursor_path=...)`. Библиотека владеет всем механизмом надёжности; handler —
единственный кастомный код.
- Цикл (из bridge.py): `read_events(since=cursor, kinds=[event.emitted])`,
  фильтр по именам событий подписки → для каждого факта `handler(fact, act)` →
  handler мутирует узел через MCP под СВОИМ least-privilege токеном → курсор
  сохраняется на диск ПОСЛЕ подтверждения (save-after-confirm).
- **Ядро НЕ трогаем:** оно уже даёт outbox (журнал + read_events + обязательная
  идемпотентность записи). Доставку/ретраи/курсор держит воркер (T8). Никакого
  push-брокера в ядре.
- `bridge.py` РЕФАКТОРИТСЯ на эту библиотеку (доказательство второго потребителя:
  bridge + coverage_bot + KnowVault-sink); поведение bridge не меняется (его
  тесты зелёные до/после).

## 3. Контракт «ровно один раз по эффекту» (корень корректности — ревью Fable)

**Решение (не обсуждается).** Гарантия = **at-least-once доставка + идемпотентный
эффект**, НЕ «надёжный курсор»:
- Ключ идемпотентности каждого действия handler'а — детерминированный,
  `<subscription_id>|<source_seq>` (namespace на подписку — две подписки на одно
  событие не сталкиваются). Обязательная MCP-идемпотентность (LLD-01 §5)
  схлопывает дубль на узле.
- **Курсор — ОПТИМИЗАЦИЯ, не корректность:** упал между действием и сохранением
  курсора → на рестарте факт переобработается тем же ключом → узел вернёт тот же
  результат, второго эффекта нет. Потеря/сброс курсора → переобработка с 0
  безопасна (дедуп). Это ровно доказанная модель bridge.py, обобщённая.
- Handler, делающий НЕСКОЛЬКО мутаций на факт, деривит суб-ключи
  `<subscription_id>|<source_seq>|<step>` — каждый шаг идемпотентен.

## 4. Политика governed-ошибки (улучшение над bridge, I-3)

**Проблема bridge.py:** при governed-отказе (permission/validation — детерминирован,
ретрай не поможет) курсор НЕ продвигается → одна «ядовитая» запись ВЕЧНО клинит
всю подписку (тихий стопор).
**Решение (I-3 — отказ виден, конвейер не встаёт):**
- **Транзиентная ошибка** (сеть/таймаут/узел недоступен) → retry с backoff,
  курсор НЕ двигать (правильно — это временно).
- **Governed/детерминированная ошибка** (permission denied, validation) →
  НЕ ретраить бесконечно: событие `subscription.failed {subscription_id,
  source_seq, error_code, error_message}` (dead-letter, виден в аудите/дашборде) + продвинуть курсор
  за ядовитый факт (или в явную park-очередь). Одна битая запись НЕ вешает поток.
- Оператор видит dead-letter’ы на дашборде (стык O5/O7); нет тихого зависания.

## 5. Декларативная подписка в DSL (governance/видимость — аддитивно, ревью Fable)

**Решение.** Реактивная проводка ОБЪЯВЛЕНА в паке (born-governed, не спрятана в
конфиге воркера) — аддитивный top-level блок (как product.mcp добавляли):
```
subscription CoverageSync:
  on event OutOfOffice, EmployeeDeactivated
  sink worker CoverageBot            # внутренний воркер — governance = его ABAC-роль
  # либо: sink endpoint "https://..."  # ВНЕШНИЙ егресс
```
- Внутренний sink (воркер) — реальный барьер = least-privilege роль воркера
  (I-2): даже «поехавший» handler ограничен своими правами.
- **Внешний sink (endpoint)** — это ЕГРЕСС: домен объявлен и в белом списке
  (SECURITY правило 3, стык egress-отчёта LLD-09); доставка — через ту же обвязку
  §2 (durable), НЕ сырой fire-and-forget.
- Компилятор валидирует: имена событий существуют (как `on event`), sink-цель
  задана. Аддитивно (I-1): паки без `subscription` компилируются как были.

## 6. Хрупкий webhook → durable (или на пенсию)

**Решение.** `webhook`-действие (TaskWebhook, fire-and-forget) СУПЕРСЕДИТСЯ:
внешняя реакция выражается `subscription ... sink endpoint`, доставляется durable-
обвязкой (§2) с идемпотентностью и retry. Существующие webhook мигрируют.
Если оставляем `webhook` для явно-некритичных уведомлений — помечаем его в
доке/линте как «без гарантий доставки», чтобы никто не строил на нём важное.

## 7. Наблюдаемость подписки (стык O5/O7)

Обвязка эмитит heartbeat/лаг (позиция курсора vs голова журнала) — мёртвая/
отстающая подписка ВИДНА (не тихо стоит). Дашборд узла показывает: активные
подписки, их лаг, dead-letter’ы (§4). Без внешних SaaS (правило периметра).

## 8. Приёмочные тесты (фиксированы)

1. `TestSubscribeExactlyOnceEffect` — обвязка обрабатывает поток; убить между
   действием и сохранением курсора → рестарт → эффект РОВНО один (дедуп по
   `{sub,seq}`); сброс курсора в 0 → переобработка без вторых эффектов.
2. `TestSubscribeTransientRetries` — узел временно недоступен → retry, курсор не
   двигается; восстановился → доставка, курсор идёт.
3. `TestSubscribeGovernedDeadLetters` — ядовитый факт (permission denied) →
   `subscription.failed` + курсор ПРОДВИНУТ за него; следующий факт
   обрабатывается (конвейер не встал). НЕ бесконечный ретрай.
4. `TestBridgeOnHarnessUnchanged` — bridge.py на обвязке: демо федерации проходит
   как раньше, exactly-once сохранён (регресс-страховка).
5. `TestSubscriptionDeclParses` — `subscription` блок парсится; неизвестное
   событие → ошибка компиляции; внешний endpoint без whitelist → ошибка/флаг;
   пак без subscription компилируется (I-1).
6. `TestExternalSinkIsDurableNotFireAndForget` — sink endpoint: доставка
   идемпотентна и ретраится; узел-источник упал/перезапущен → без потерь/дублей.
7. Golden/I-1: паки без подписок реплеятся; go test ./... зелёный.

## 9. PR-нарезка

PR-1: `workers/lib/subscribe.py` (обвязка: read_events-цикл, durable-курсор,
      ключ `{sub,seq}`, retry, governed-dead-letter) + рефактор bridge.py на неё
      (тесты 1,2,3,4). ← **ревью Fable** (контракт exactly-once §3, политика §4).
PR-2: DSL-блок `subscription` (парсер/AST/семантика, аддитивно) + валидация
      имён событий и sink (тест 5). ← **ревью Fable** (поверхность компилятора).
PR-3: внешний sink через обвязку + егресс-whitelist (SECURITY правило 3) +
      суперсед webhook (тесты 6); пометить старый webhook «без гарантий».
PR-4: heartbeat/лаг + dead-letter на дашборде (§7, стык O5/O7).

**Порядок:** PR-1 — сердце (обвязка + рефактор bridge как второй потребитель),
самостоятельно ценно даже без DSL. PR-2/3 — governance-слой. PR-4 — наблюдаемость.
Первый реальный потребитель после bridge — coverage_bot из пака `people`
(демонстрация «реагируй на OutOfOffice» на обвязке).
