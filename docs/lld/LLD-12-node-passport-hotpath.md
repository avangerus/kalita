# LLD-12 — паспорт узла и hot-path: бенчмарк-профили, auth O(1), replay-бюджет (N6+N9)

Дата: 2026-07-02. Автор решений: Fable. Реализация: Sonnet 5 по документу.
Родитель: RELEASE-1.0 §N6/§N9, HLD-V1 §H10 (профили P1–P4). Зависимости:
ADR-001 (один мьютекс — НЕ трогать), ADR-002 (журнал десятки млн — измерить,
не верить). Сверка: Authenticate O(акторов) §7.5, MemStore alias §7.13.

**Мотив.** ADR-001/002 сознательно просты, но их потолок НИКЕМ не назван числом,
а «узел держит X» — продажный артефакт (релиз-ноты) и ворота V1-GATE. Плюс два
конкретных hot-path уже O(n): Authenticate по числу акторов, инвайты по журналу
(последнее закрыто в LLD-10). Правило релиза: конкурентность НЕ переделываем
(риск ради несуществующей нагрузки) — делаем потолок ИЗМЕРИМЫМ и сужаем только
доказанные горячие точки.

**Границы для исполнителя.** Sonnet НЕ решает сам: что архитектуру лока НЕ
трогаем (§0 — ADR-001 остаётся, только замер + точечные O(1)-индексы); что
tiered storage НЕ строится (§4 — порог в мониторинге, реализация по факту);
контракт auth-индекса (§2 — тот же результат Authenticate, но O(1); необратимо
на hot-path, ревью Fable). Индексы — вторичные проекции, не меняют журнал (I-1).

---

## 0. Что НЕ делаем (решение зафиксировано)

Engine.mu / Registry.mu, модель «один узел = один клиент», Append вне лока —
НЕ трогаем (ADR-001). Переделка лока под несуществующую нагрузку — запрещена.
Всё ниже — измерение + точечные индексы БЕЗ смены модели конкурентности.

## 1. Паспорт узла — бенчмарк-профили в CI

**Решение.** Suite из четырёх профилей (H10), числа в CI, регресс >20% валит
сборку, паспорт публикуется в релиз-нотах:
- **P1 «пилотный микс»:** 5 MCP-агентов + 10 UI-читателей + automation-тик
  одновременно → мутаций/с, p99 латентность.
- **P2 bulk:** 10k create (профиль установки data-pack — LLD-13).
- **P3 replay:** 1M и 10M синтетических событий → время старта (сейчас замерено
  только 100k = 1.07с; ADR-002 обещает десятки млн — проверить или опровергнуть).
- **P4 auth-шторм:** Authenticate под конкуренцией (заодно ловит TOCTOU N7
  через `-race`).
- Синтетик-генератор журнала — детерминированный (сид фиксирован в тесте, не
  Date.now/rand на пути данных).

## 2. Authenticate O(1) (необратимо на hot-path — ревью Fable)

**Решение.** Индекс `token_hash → actor` (инкрементальная проекция, паттерн
Registry) заменяет O(акторов)-скан (§7.5). Контракт: РЕЗУЛЬТАТ Authenticate
неизменен (тот же актор/отказ), меняется только сложность. Constant-time
сравнение сохраняется (не деградировать безопасность ради скорости).
- Индекс — вторичная проекция из тех же событий актор/credential; на журнал не
  влияет (I-1), падает и перестраивается из журнала.
- Приёмка: P4 показывает O(1) (латентность не растёт с числом акторов).

## 3. MemStore паритет с PGStore (корректность стора)

**Решение.** `MemStore.All`/`Since` отдают КОПИИ событий, а не указатели на
общие (§7.13 — сейчас алиасы: мутация возвращённого события вызывающим портит
стор, поведенческое расхождение с PGStore, где события десериализуются заново).
Это скрытый источник «работает в тестах на PG, врёт на Mem» и наоборот.
- Приёмка: тест — мутация поля возвращённого события НЕ меняет содержимое стора;
  один и тот же сценарий даёт идентичные проекции на MemStore и PGStore.

## 4. Tiered storage — НЕ в 1.0 (триггер разморозки)

**Решение.** НЕ строить вслепую. Порог (ADR-002, ~1M записей проекции) — в
мониторинге узла; алерт на дашборде при 50% порога. Реализация tiered —
по факту достижения, не по вере. Snapshot-проекции — тоже НЕ в 1.0, пока
P3 replay-бюджет держится (<5с в паспорте). Оба — в RELEASE-1.0 §5, размораживаются
числом из паспорта, а не заранее.

## 5. Приёмочные тесты (фиксированы)

1. `BenchmarkP1PilotMix` / `P2Bulk` / `P3Replay` / `P4AuthStorm` — числа в CI,
   зафиксированный baseline, регресс >20% валит (гейт).
2. `TestAuthConstantTimeAndO1` — Authenticate: латентность не растёт с числом
   акторов (P4); сравнение остаётся constant-time.
3. `TestMemStoreReturnsCopies` — мутация возвращённого события не меняет стор;
   MemStore и PGStore дают идентичные проекции на одном сценарии.
4. `TestReplayBudget1M` — replay 1M синтетики укладывается в объявленный
   бюджет паспорта (число, не «ощущение»); при превышении — явный fail с
   рекомендацией «пора snapshot» (триггер §4).
5. Golden/I-1: индексы не меняют журнал; старые журналы реплеятся без изменений.

## 6. PR-нарезка

      (тест 1).
PR-2: Authenticate hash-индекс (тесты 2). ← **ревью Fable** (hot-path проверки
      прав, необратимо).
PR-3: MemStore копии + Mem/PG-паритет тест (тест 3).
PR-4: replay 1M/10M бенч + порог-алерт в мониторинг (тест 4).

любой другой волне (зона — eventstore/identity/bench, пересечение с LLD-10
только на auth-проекции — согласовать индекс token_hash как общий).
