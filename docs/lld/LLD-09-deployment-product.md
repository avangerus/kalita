# LLD-09 — deployment-продукт: shadow-режим, «неделя в цифрах», egress-отчёт (N10)

Дата: 2026-07-02. Автор решений: Fable. Реализация: Sonnet 5 по документу.
Родитель: RELEASE-1.0 §N10, HLD-V1 (I-1..I-5, choke point I-2), T11 (причины
покупать). Зависимости: LLD-01 (op-скобки, event.emitted, идемпотентность),
механика proposals (уже в ядре), поле-ставка роли в DSL (уже выразимо).

**Мотив.** Три артефакта, которые продают продление и снимают страх юриста
пилота, — и все три СТРОЯТСЯ из журнала, который уже есть, без нового движка.
Соблазн отложить «код до денег» опровергается тем, что shadow нужен самому
пилоту (юрист боится «а вдруг агент натворит») — значит это часть продажи, не
пост-продаж.

**Границы для исполнителя.** Sonnet НЕ решает сам: shadow — это перенаправление
в СУЩЕСТВУЮЩУЮ механику proposals на уровне Permission Engine (§1, необратимо —
новая семантика роли над choke point'ом, ревью Fable); что egress-отчёт —
самодекларация воркера + событийный лог, НЕ сетевой перехват (§3, честная
граница «lite»); что все три артефакта — read-модель/оверлей над журналом, а не
параллельное хранилище (I-1). Отчёты не мутируют состояние.

---

## 1. Shadow-режим (необратимо — ревью Fable)

**Решение (не обсуждается).** Shadow — рантайм-оверлей на роль, НЕ новый путь
исполнения и НЕ форк движка. Переключается событиями:
`role.shadow_enabled {role}` / `role.shadow_disabled {role}` — проекция держит
множество shadow-ролей. Выключение — одно событие (RELEASE-1.0 §N10).

- **Точка перехвата — Permission Engine (I-2), единственная.** Любая мутация
  (create/update/act/emit) от актора, чья роль в shadow-множестве,
  НЕ применяется, а материализуется как **proposal той же мутации** через
  существующую механику proposals («что бы я сделал», полный целевой payload).
  Чтение (read/query/search) shadow НЕ трогает — агент видит всё как обычно,
  но его рука не доходит до состояния.
- **Одобрение proposal = применение реальной мутации** существующим путём
  (одобрение уже journaled, HITL-подпись как есть — I-2 не обходится). Отклонение
  — событие отказа (I-3), агент узнаёт исход как из обычного HITL.
- **Инвариант:** в shadow НИ ОДНО событие класса record.created/updated/
  <transition> от shadow-актора не появляется в журнале напрямую — только
  proposal и его последующее одобренное применение. Это проверяемое свойство,
  а не «агент старается».
- Лента shadow в UI — организм из LLD-05 (список proposal-записей shadow-ролей
  «что предложил бы агент»); ядро отдаёт их обычным query по proposal-сущности,
  нового API нет.

## 2. «Неделя в цифрах» — `kalita report`

`kalita report --since <dur> [--role R] [--format md|html]` — чистая свёртка
журнала, ноль записи.
- Метрики из журнала: число действий агентов vs людей; часы×ставка (ставка —
  атрибут роли в DSL, уже выразимо; действие→нормо-часы по декларации роли);
  длина очереди подписей и её возраст; нарушения SLA (из stuck-механики
  automation). Разрез по роли/паку.
- Вывод — Markdown/HTML-документ (на почту директору воркером-отправителем, не
  ядром). HTML — тот же buildless-рендер, что catalog (LLD-05), без сборки.
- **Решение:** report читает journal через `read_events`/проекции (LLD-08), НЕ
  заводит своей структуры; если роль не декларирует ставку — часы×ставка
  опускаются с пометкой, не падает (I-3 дух — явно, не молча).

## 3. Egress-отчёт (честная граница «lite» — необратимо в части модели)

**Решение (не обсуждается): это самодекларация + событийный лог, НЕ перехват
трафика.** Ядро не может (и не должно, T8) инспектировать сеть воркера. Модель:
- Воркер декларирует whitelist egress-доменов в СВОЁМ манифесте (декларативно).
- Фактический внешний вызов воркер логирует событием `egress.called
  {worker, domain, purpose, ref?}` через `emit_event` (LLD-01 §5, под verb
  `emit`, полный аудит, идемпотентно).
- Отчёт `kalita egress-report --since <dur>` сверяет декларацию с фактом:
  страница «что покидало периметр» + аномалии (вызов домена вне декларации →
  подсветка).
- **Граница, которую НЕЛЬЗЯ продавать иначе:** это доверенная кооперация наших/
  клиентских воркеров (T8 — воркеры запускает оператор в контуре), а не
  гарантия против враждебного воркера. Полный egress-DLP (перехват/маскирование)
  — за релизом (RELEASE-1.0 §5, H4). Зафиксировать это в тексте отчёта и SECURITY.

## 4. Приёмочные тесты (фиксированы)

1. `TestShadowRedirectsToProposal` — актор shadow-роли: create → в журнале
   proposal, НЕ record.created; одобрение proposal → record.created появляется;
   `role.shadow_disabled` → следующая мутация применяется напрямую.
2. `TestShadowDoesNotBypassHITL` — shadow-мутация, чьё применение требует
   approval(Role), после одобрения proposal всё равно паркуется в HITL (два
   гейта не схлопываются).
3. `TestShadowReadUnaffected` — shadow-актор читает/query как обычно (перехват
   только на мутациях).
4. `TestReportFromJournal` — фикстура журнала за 7д → report даёт корректные
   счётчики; роль без ставки → часы опущены с пометкой, без падения.
5. `TestEgressReportReconciles` — egress.called по декларированному домену →
   в отчёте; вызов недекларированного домена → подсвечен как аномалия.
6. Golden/I-1: без shadow-событий и egress-событий старый журнал реплеится
   байт-в-байт; report/egress-report на v0-журнале не падают (пустые секции).
