# LLD-16 — право на забвение в append-only: crypto-shredding (O1)

Дата: 2026-07-02. Автор решений: Fable. Реализация: Sonnet 5 по документу.
Родитель: PROD-READINESS §O1, EVENT-STORE §6 (зарезервировано: per-subject key,
слот `payload {encrypted, key_id}`), SECURITY P2 #8. Инварианты: сталкивается с
I-1 (аддитивность/журнал не чистится) и I-5 (офлайн-доказуемость) — и разрешает
их, НЕ нарушая. Зависимость: LLD-17 (бэкап обязан уважать уничтожение ключа).

**Мотив.** Legal-пилот обрабатывает перс.данные (договоры, ФИО, резюме, жалобы).
152-ФЗ/GDPR дают субъекту право на удаление. Физически стереть событие =
сломать hash-цепочку = убить доказуемость ВСЕГО журнала. Крипто-шреддинг
разрешает противоречие: данные шифруются ключом на субъекта; удаление =
уничтожение ключа → payload нечитаем, а цепочка и подписи целы (хэш и подпись —
над ШИФРТЕКСТОМ).

**Границы для исполнителя.** Sonnet НЕ решает сам: что шифруется — поле-scoped
по ДЕКЛАРАЦИИ пака, не «весь event» (§1, необратимо); что хэш/подпись считаются
над шифртекстом, поэтому verify переживает стирание (§3, необратимо — ядро
доказуемости, ревью Fable); что стирание журналируется и авторизуется как
деструктивная операция с HITL (§4); поведение проекций после шреддинга —
tombstone, не крах (§2, I-3). Ключи — на уровне node (I-4), никогда в DSL/журнал.

---

## 1. Что и как шифруется (декларация, не догадка)

**Решение.** Шифрование — ПОЛЕ-scoped по декларации пака, не по всему событию:
- В DSL поле помечается как перс.данные субъекта: `field: text pii subject=<ref|key>`
  — объявляет, что содержимое поля принадлежит субъекту данных, идентифицируемому
  `subject` (ref на сущность-субъекта или natural-key субъекта).
- При журналировании такое поле в payload не пишется открытым: пишется
  `{encrypted: true, key_id: <subject_key_id>, ct: <base64 ciphertext>}` (слот
  EVENT-STORE §6). Остальные поля (статус, ts, actor, refs, суммы) — открыты:
  они НЕ перс.данные, и governance/аудит по ним обязан пережить стирание.
- Ключ — **на субъекта** (один ключ на субъекта данных): в одном событии разные
  pii-поля разных субъектов шифруются РАЗНЫМИ key_id. Стирание одного субъекта
  не трогает данные другого в том же событии.
- Крипто: AEAD (напр. XChaCha20-Poly1305/AES-GCM), ключ субъекта — в node-key-
  store (I-4). Nonce на событие-поле, aad = {event_id, field} (привязка
  шифртекста к месту — нельзя переставить).

## 2. Проекции после шреддинга (tombstone, не крах — I-3)

**Решение.** Стёртое поле в проекции = явный tombstone `«[стёрто: subject X,
<дата>]»`, НЕ пустота и НЕ ошибка:
- Запись-носитель ПРОДОЛЖАЕТ существовать: факт governed-обработки («по субъекту
  X было принято решение Y, одобрено Z») остаётся доказуемым — часто это и есть
  законное основание хранения после стирания перс.данных.
- Computed/ref/валидаторы, зависящие от стёртого поля, обрабатывают tombstone
  явно (I-3): не падают, дают tombstone/пометку. Стёртое поле нельзя снова
  редактировать (оно не «пустое», оно «стёрто»).
- Replay детерминирован в обоих состояниях: ключ есть → расшифровка в проекцию;
  ключ уничтожен → tombstone. Старые журналы (ключи на месте) реплеятся как были
  (I-1); golden с ключами — без изменений.

## 3. Доказуемость переживает стирание (ядро, ревью Fable)

**Решение (не обсуждается).** Хэш-цепочка и подписи считаются НАД ШИФРТЕКСТОМ:
- `hash = SHA-256(prev_hash || canonical(event с ct вместо plaintext))` — стирание
  ключа НЕ меняет ни одного байта события → цепочка цела, чекпоинты валидны.
- Подписи (Ed25519 агента над мутацией, WebAuthn над approval-строкой) — над
  канонической формой С ШИФРТЕКСТОМ; approval-строка (LLD-02 §2) содержит
  record_id/transition, НЕ pii-поля → стирание её не трогает.
- `kalita verify` работает БЕЗ ключей субъектов: проверяет цепочку и подписи по
  шифртексту. Доказуемость «журнал не переписан» сохраняется после любого
  стирания — это продаётся регулятору напрямую (I-5 усилен, не ослаблен).

## 4. Операция стирания (авторизованная, журналируемая)

**Решение.** Стирание субъекта = деструктивная governed-операция:
- Команда/эндпоинт `erase-subject <subject_id> --reason` → требует роли с правом
  + HITL-подписи (как любое необратимое действие; enforcement-флаг прода).
- Механизм: уничтожение ключа субъекта в key-store. Событие
  `subject.erased {subject_id, key_ids[], reason, at}` в журнал — стирание САМО
  доказуемо (юридически нужно доказать, что запрос исполнен). Событие НЕ содержит
  перс.данных.
- Необратимо по построению (в этом смысл). Tombstone + событие — доказательство
  исполнения. Идемпотентно: повторное стирание — no-op (ключ уже уничтожен).
- **Зависимость LLD-17:** ключ субъекта обязан быть уничтожен и в бэкапах, иначе
  restore «воскресит» стёртое. Решение: ключи субъектов в бэкапе хранятся так,
  что уничтожение уважается (см. LLD-17 §ключи) — стирание распространяется на
  key-манифест бэкапа, а не на неизменяемый журнал.

## 5. Приёмочные тесты (фиксированы)

1. `TestPiiFieldStoredEncrypted` — поле `pii` в журнале = `{encrypted,key_id,ct}`,
   не plaintext; не-pii поля открыты.
2. `TestEraseMakesUnreadableChainIntact` — erase-subject → проекция поля =
   tombstone; hash-цепочка и чекпоинты verify проходят; запись-носитель жива.
3. `TestVerifyWithoutKeys` — `kalita verify` на копии БЕЗ ключей субъектов:
   цепочка и подписи валидны (доказуемость не зависит от plaintext).
4. `TestErasePerSubjectIsolation` — событие с pii двух субъектов; стёрли одного →
   второй читается; ct первого нечитаем.
5. `TestEraseIsJournaledAndAuthorized` — стирание без прав/подписи отклонено;
   с подписью → `subject.erased` в журнале, без перс.данных; повтор идемпотентен.
6. `TestReplayDeterministicAfterErase` — replay журнала со стёртым субъектом даёт
   стабильный tombstone; журнал без стираний реплеится как прежде (golden/I-1).
7. `TestComputedHandlesTombstone` — computed/валидатор над стёртым полем не
   падает, отдаёт tombstone-семантику (I-3).

## 6. PR-нарезка

PR-1: DSL `pii subject=…` + шифрование поля при журналировании + key-store
      субъектов (тесты 1, 4). ← **ревью Fable** (модель ключей/крипто).
PR-2: хэш/подпись над шифртекстом + `kalita verify` без ключей (тесты 3).
      ← **ревью Fable** (ядро доказуемости — необратимо).
PR-3: проекции-tombstone + computed/validator обработка (тесты 6, 7).
PR-4: `erase-subject` + HITL + `subject.erased` + идемпотентность (тесты 2, 5);
      согласование с LLD-17 (уничтожение ключа в бэкапе).

**Порядок:** PR-1/PR-2 — фундамент, до любого хранения перс.данных у пилота
(лучше ДО первого реального договора в проме). Приоритет поднять с SECURITY-P2
до пилот-блокера, если пилот с реальными перс.данными.
