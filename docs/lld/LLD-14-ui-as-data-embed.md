# LLD-14 — UI как данные: дерево из закрытого реестра, headless/visual, инвариант «ноль HTML от агента»

Дата: 2026-07-02. Автор решений: Fable. Реализация: Sonnet 5 по документу.
Родитель: HLD-V1 §H7.1 (Product Kit UI), H4 (периметр — тот же принцип «данные ≠
команды», применённый к презентации). Надстройка над LLD-05 (реестр компонентов):
LLD-05 даёт БИБЛИОТЕКУ (atoms→faces), LLD-14 даёт СХЕМУ (дерево-данные), РЕНДЕРЕР
и модель встраивания. Вводит сквозной инвариант **I-6**.

**Мотив (требование фаундера).** Три связанных свойства, которых нет явно в LLD-05:
1. UI собирается ДЕРЕВОМ из компонентов декларативно — kalita сам строит формы,
   автор не пишет HTML.
2. Один компонент встраивается на чужой сайт в двух видах: как готовая
   визуальная форма целиком, ИЛИ как чисто функциональный примитив (данные+
   поведение+права), поверх которого потребитель рисует свой визуал.
3. **Никто через MCP/агента не рисует бесконтрольный HTML.** Презентация — не
   канал для свободной разметки от LLM.

**Границы для исполнителя.** Sonnet НЕ решает сам: формат узла дерева и
инвариант I-6 (§1 — необратимая поверхность безопасности рендера, ревью Fable);
что visual СТРОИТСЯ из headless, а не дублирует логику (§2); что внешний embed
изолирован Shadow DOM и работает под pass-through токеном (§3, ошибка = дыра в
правах/стилях); что агентский/MCP-ввод НИКОГДА не путь к HTML (§4). Реестр
компонентов — из LLD-05, здесь не переопределяется, только дополняется схемой.

---

## 0. Инвариант I-6 (сквозной, добавляется к I-1..I-5)

**UI — из закрытого реестра, не из HTML.** Всё, что рендерится, производит
доверенный рендерер из ЗАМКНУТОГО набора компонентов по декларативному
дереву-данным. Ни данные (props/дерево), ни агент/MCP, ни ответ модели не могут
внести сырой HTML/скрипт/стиль-побег или узел вне реестра. Единственный
производитель разметки — рендерер (choke point презентации, как I-2 для
мутаций). Проверяемое свойство, не «стараемся эскейпить».

## 1. UI-схема — дерево-данные над реестром (необратимо — ревью Fable)

**Решение (не обсуждается).** Экран/форма = декларативное ДЕРЕВО узлов:
```
node := { type: <имя компонента из реестра>, props: <данные>, slots: { <slot>: [node…] } }
```
- Рендерер — детерминированный интерпретатор: обходит дерево, для каждого узла
  берёт компонент из реестра по `type`, передаёт `props`, рендерит slots.
  Узел с `type` вне реестра → отвергается (не рендерится, событие/ошибка), не
  «падает» и не «додумывает».
- `props` — только ДАННЫЕ. Строковые значения выводятся как текст (эскейплены).
  Нет узла-типа «сырой html»; нет пути внести разметку через значение поля.
- Rich-text (описания, ответы агента) — не HTML, а безопасный markdown-
  ПОДМНОЖЕСТВО, рендеримое тем же реестром в whitelist-узлы (жирный/список/
  ссылка с проверкой схемы URL), см. §4.

**Откуда берётся дерево (три источника, один инвариант):**
- **Автоген из `/api/meta`** (дефолт, ноль авторской работы): рендерер строит
  форму entity автоматически — поле→atom по типу (диспетчер FieldInput из
  LLD-05 становится генератором поддерева). Это «сам собирал формы».
- **Авторская схема в паке** (опция): автор объявляет дерево формы декларативно
  (порядок, группировки, какой face) — ДАННЫЕ в манифесте/DSL пака, не код.
  Переопределяет автоген. Governed артефакт (ревьюабельный, версионируемый).
- **Никогда — рантайм от агента** (см. §4).

## 2. Headless / visual — один контракт, два выхода

**Решение.** Компонент существует в двух формах над ОДНИМ контрактом (meta+SDK),
visual = надстройка headless, логика не дублируется:
- **Headless (функциональный примитив):** отдаёт МОДЕЛЬ — данные (`/api/meta` +
  значения), поведение (submit/act/валидация через `@kalita/sdk`), права (что
  доступно актору) — БЕЗ визуала. Потребитель рисует своим дизайном. Это
  «функциональная вещь, перерисовать всё самому».
- **Visual (готовая форма):** headless + стандартный рендерер (§1) + токены/стили
  (LLD-05). «Целиком форма как есть».
- Инвариант реализации: visual НЕ содержит своей бизнес-логики/валидации —
  только presentation поверх headless. Тест доказывает: обе формы дают
  идентичные вызовы SDK на одном сценарии (§5).

## 3. Внешний embed (чужой сайт)

**Решение.** Поставка компонента на сторонний сайт — двумя способами, оба
governed и изолированные:
- **Visual embed:** web-component `<kalita-face name="RiskCardFace" …>` (или
  `<script>`+mount). Рендерится в **Shadow DOM** — стили хоста не текут внутрь и
  наоборот (изоляция в обе стороны), CSP-совместимо, без `eval`. Потребитель
  вставляет тег, получает работающую governance-форму (права/аудит/HITL внутри).
- **Headless embed:** тот же контракт §2 через `@kalita/sdk` — потребитель
  берёт данные/поведение/права и рисует сам.
- **Auth: строгий pass-through** (как LLD-06 §1): embed требует bearer конечного
  пользователя и проксирует его; СВОЕГО токена на запись не имеет. Встраивание
  на публичной странице без токена = read-only/логин-приглашение, не запись.

## 4. Агент/MCP не рисует HTML (ядро требования)

**Решение (не обсуждается).**
- UI-схемы (деревья §1) — АВТОРСКИЙ governed артефакт пака ИЛИ автоген из meta.
  **Агент через MCP оперирует доменными данными, НЕ UI-схемами** — у него нет
  тула «отрендерь HTML/верни разметку». MCP-поверхность (LLD-06) — доменные
  тулы над данными, не над презентацией.
- Ответ агента в KChat (LLD-06) — это `Message.body` (текст) → рендерится как
  текст или безопасный markdown-подмножество (§1), НИКОГДА как HTML. Даже
  полностью «взломанный» агент (H4) не может внести скрипт/разметку в UI: его
  выход проходит тот же реестр-choke-point I-6, что и всё остальное.
- Если однажды понадобится «агент компонует экран» — он сможет произвести только
  ДЕРЕВО ИЗ РЕЕСТРА (данные), которое валидируется I-6 как авторская схема; сырой
  HTML недостижим по построению. (Не в v1 — зафиксировано как путь, не фича.)

## 5. Приёмочные тесты (фиксированы)

1. `TestRendererClosedRegistry` — дерево со всеми known-компонентами рендерится;
   узел с неизвестным `type` → отвергнут (событие/ошибка), рендер не падает.
2. `TestPropsNeverBecomeMarkup` — строковое значение поля, содержащее
   `<script>…`/HTML, выводится как ТЕКСТ; ни один путь props→разметка не
   исполняется (I-6).
3. `TestAutogenFormFromMeta` — форма entity строится из `/api/meta` без авторской
   схемы (поле→atom); авторская схема переопределяет порядок/face.
4. `TestHeadlessAndVisualParity` — headless и visual одного компонента дают
   идентичные вызовы SDK на одном сценарии (visual не дублирует логику).
5. `TestEmbedShadowIsolationAndPassThrough` — visual embed на хост-странице:
   стили хоста не влияют и не утекают (Shadow DOM); действие пишет под токеном
   пользователя; без токена — нет записи.
6. `TestAgentOutputRendersAsText` — злонамеренный `Message.body` от агента
   (скрипт/HTML) в KChat рендерится как текст/безопасный markdown, не как
   разметка (стык с H4/LLD-06).
7. Golden/I-1: встроенный админ-клиент на новом рендерере даёт те же формы;
   старые экраны не сломаны.
