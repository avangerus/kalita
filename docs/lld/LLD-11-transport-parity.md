# LLD-11 — паритет транспортов: общий transport-слой, parity-тест, автоген контракта (N8)

Дата: 2026-07-02. Автор решений: Fable. Реализация: Sonnet 5 по документу.
Родитель: RELEASE-1.0 §N8, HLD-V1 (I-1..I-5). Зависимости: единый движок
(engine) уже есть; дублирование обвязки — сверка §7.4/§7.3/§7.7.

**Мотив.** Бизнес-логика в engine едина, но обвязка REST и MCP продублирована
(сборка Actor из заголовков, журнальный JSON, request-структуры) и уже
расходится: README «~22 инструмента» vs 27 в коде; golden «20 кейсов» vs 41.
Каждая новая ручка усиливает дрейф — и однажды REST и MCP начнут писать РАЗНЫЕ
события на одну операцию. Это тихая эрозия I-2 (один choke point) на уровне
входа.

**Границы для исполнителя.** Sonnet НЕ решает сам: КОНТРАКТ паритета (§2 —
одна операция через оба транспорта даёт байт-идентичные события, кроме
actor/ts; это инвариант, не деталь); что контракт MCP генерируется ИЗ кода, а
не пишется руками (§3 — счётчики не должны врать по построению). Форму DTO
исполнитель выводит сам — фиксируется РЕЗУЛЬТАТ (паритет), не структура.
Рефакторинг НЕ меняет наблюдаемое поведение (I-1: golden зелёный до и после).

---

## 1. Общий transport-слой

`internal/transport` — единая точка, откуда оба входа (REST-handlers,
MCP-tools) берут:
- сборку `Actor` из контекста запроса (заголовки bearer/подпись у REST,
  MCP-контекст у MCP) — один код, одна модель актора;
- построение журнального JSON события (envelope) — один сериализатор;
- request-DTO операций (create/update/act/query/...) — одна структура на
  операцию, оба транспорта её наполняют.

**Решение:** engine остаётся единственным исполнителем (choke point не
переносится в transport — слой только СОБИРАЕТ вызов и РАЗБИРАЕТ результат,
не принимает решений о правах/мутациях). Дублирования быть не должно: если
REST и MCP расходятся хоть в одном поле сборки Actor или envelope — это баг слоя.

## 2. Parity-тест (главная приёмка — инвариант, не обсуждается)

**Решение.** Табличный тест: набор канонических операций (create, update, act
с HITL, query, emit) выполняется дважды — через REST-путь и через MCP-путь на
одинаковом входе — и сравниваются порождённые события: **байт-идентичны, кроме
полей actor и ts** (и идемпотентного ключа, если транспорт-специфичен).
- Любая новая операция обязана попасть в эту таблицу (гейт: список операций
  transport-слоя и таблица parity-теста сверяются — расхождение валит CI).
- Это превращает «транспорты не расходятся» из обещания в проверяемый инвариант.

## 3. Автоген контракта MCP (счётчики перестают врать)

**Решение.** `kalita mcp contract > docs/MCP-CONTRACT-v1.md` — контракт (список
тулов, входы/выходы) генерируется ИЗ `tools.go`, не пишется руками. CI-гейт:
сгенерированный контракт совпадает с закоммиченным (как golden) — число тулов
в доке не может разойтись с кодом по построению. README ссылается на контракт,
не дублирует счётчик.

## 4. Устойчивость входа

`recover()` вокруг Compile/dispatch (§7.7): паника парсера на агентском/клиентском
DSL или на кривом MCP-вводе → structured error транспорта (E-код), НЕ смерть
узла. Паника — это тоже сбой, и он не должен ронять процесс, обслуживающий
других акторов (дух I-3: отказ — управляемое событие/ответ, не крах).

## 5. Приёмочные тесты (фиксированы)

1. `TestTransportParity` — таблица операций: REST vs MCP → байт-идентичные
   события (кроме actor/ts/idemkey). (Главный.)
2. `TestParityTableCoverage` — каждая операция transport-слоя присутствует в
   parity-таблице (гейт от «забыли добавить»).
3. `TestMcpContractMatchesCode` — `kalita mcp contract` == закоммиченный
   docs/MCP-CONTRACT-v1.md; расхождение = fail (счётчики честны).
4. `TestDispatchPanicIsStructuredError` — намеренно паникующий ввод
   (кривой DSL/MCP-payload) → E-код-ответ, процесс жив (проверка на обоих
   транспортах).
5. Golden/I-1: полный набор golden-кейсов зелёный ДО и ПОСЛЕ рефакторинга —
   наблюдаемое поведение не изменилось (это и есть страховка рефакторинга).
