# LLD-22 — `include`: миксины полей (keystone горизонтали)

Дата: 2026-07-06. Автор решений: Fable. Реализация: Sonnet 5 по документу.
Родители: PLATFORM-STDLIB §B1 (keystone), DSL-CORE-LIB §4 (вскрытый гэп),
LANGUAGE.md §8 (admission gate), инвариант I-1 (аддитивность).

**Мотив.** Самое повторяющееся в enterprise — стандартная обвязка записи.
Замер по нашим же пакам: `owner:`×14, `assignee:`×8, `name:`×26, `email:`×13,
`from/to:`×4, `amount:`×5 — каждый пак копипастит одни и те же группы полей.
Механизма переиспользования ГРУППЫ полей в языке нет (проверено: ноль
`include|mixin` в internal/dsl). Это блокер всего `core.fields` и главный
источник дрейфа паков. Одновременно 3 пака руками объявляют `created_at` —
анти-паттерн: метаданные создания/изменения деривятся из журнала (PLATFORM-
STDLIB §A), их объявление руками — ложная правда (поле живёт своей жизнью,
журнал — своей).

**Границы для исполнителя.** Sonnet НЕ решает сам: семантику инлайна и правило
коллизий (§2, необратимо — форма языка, ревью Fable); список seed-миксинов и
их состав (§3, зафиксирован); что НЕ миксин (§4). Пак-определяемые миксины
(`mixin Имя:` в DSL) — ЗА ТРИГГЕРОМ, в этом LLD их НЕТ (§5).

---

## 1. Конструкция (аддитивно, base-tier)

Внутри `entity` — строка `include <core.Миксин>` (одна или несколько):

```dsl
entity Ticket:
    include core.Assignable          # + owner, assignee
    include core.Named               # + name
    title: string required
    status: enum[new, done] = new
```

- `include` допустим только В НАЧАЛЕ тела entity (до первого поля) — читатель
  видит состав сразу, а не выискивает в середине.
- Паки без `include` компилируются как раньше (I-1); golden-паки нетронуты.

## 2. Семантика инлайна (ревью Fable — форма языка, необратимо)

**Решение.** Компилятор ИНЛАЙНИТ поля миксина в EntityDecl на семантической
фазе (до engine): результирующая Model неотличима от руками написанных полей.
- **Порядок:** поля миксинов — в порядке include-строк, затем собственные поля.
  Детерминированно (реплей/golden/meta стабильны).
- **Коллизии — громко, никаких тихих слияний/override:**
  - миксин-поле совпало по имени с собственным полем → ошибка компиляции
    (`E0xx_MIXIN_FIELD_COLLISION`, hint: «переименуй поле или убери include»);
  - два миксина принесли одно имя → та же ошибка (какие include столкнулись);
  - override поля миксина — НЕ поддержан в v1 (не тихая фича; появится только
    через admission gate отдельным решением).
- **Никакой пропагации типов «миксин знает про entity»:** миксин — чистый
  список FieldDecl, без ссылок на хоста. ref-цели миксина валидируются как
  обычные (core.User существует всегда).
- **Неизвестный миксин** → ошибка компиляции с перечнем доступных.
- Инлайн происходит ДО всех остальных семантических проверок — permissions на
  `Entity.owner`, computed, unique, workflow видят поля миксина как родные.

## 3. Seed-миксины v1 (закрытый список, по доказанным потребителям)

Реестр — в компиляторе (Go, рядом с coreEntities в internal/dsl/core.go),
namespace `core.*`. Состав v1 — ровно четыре, по замеру повторов:

| Миксин | Поля | Потребители (замер) |
|---|---|---|
| `core.Assignable` | `owner: ref[core.User] default=$me` · `assignee: ref[core.User]` | 14+8 |
| `core.Named` | `name: string required` | 26 |
| `core.Contact` | `email: string` · `phone: string` | 13+3 |
| `core.Period` | `from: date` · `to: date` | 4+4 |

- Точные типы/модификаторы выше — ЗАФИКСИРОВАНЫ (не «примерно»). Кому нужен
  иной состав — объявляет поля руками, это нормально.
- `core.Money` (amount+currency) — НЕ в v1: форма currency (enum? ref на
  reference Currency?) зависит от нерешённого `reference`-конструкта. Каталог.
- `core.Sequenced` — НЕ в v1: `number: serial format="..."` уже одна строка,
  миксин без параметров ничего не экономит, а параметры миксинов v1 не имеет.
- Расширение списка — строго по второму потребителю (DSL-CORE-LIB §5).

## 4. Что НЕ миксин (важно, закрывает анти-паттерн)

`created_at/by`, `updated_at/by` — НЕ поля и НЕ миксин: они деривятся из
журнала (PLATFORM-STDLIB §A). `core.Auditable` НЕ создаётся. Вместо этого:
- engine отдаёт created/updated meta из журнала в read-модели записи (если
  ещё не отдаёт — зафиксировать гэп в TECHDEBT, отдельная задача, не тут);
- 3 пака с ручным `created_at` — кандидаты на чистку (отдельно, не в этом PR).

## 5. Явно ЗА триггером (в этом LLD отсутствуют)

Пак-определяемые миксины (`mixin Имя:` как top-level) · параметризованные
миксины · override/exclude полей миксина · миксины поведения (flow/permissions
в миксине — только ПОЛЯ, ничего больше). Каждое — отдельное решение через
admission gate, когда пак докажет нужду.

## 6. Приёмочные тесты (фиксированы)

1. `TestIncludeInlinesFields` — entity с include compiles; Model содержит поля
   миксина + собственные, в правильном порядке; create/read работают.
2. `TestIncludeCollisionLoud` — собственное поле `owner` + `include
   core.Assignable` → ошибка компиляции с именем поля и миксина; два миксина
   с пересечением имён → ошибка.
3. `TestIncludeUnknownMixin` — `include core.Nosuch` → ошибка с перечнем
   доступных.
4. `TestIncludePermsSeeMixinFields` — permissions `update [X.owner]` на
   включённое поле валидируются и работают (позиция include до полей).
5. `TestIncludePositionEnforced` — include после первого поля → ошибка.
6. Golden/I-1: все существующие паки компилируются без изменений;
   `go test ./...` зелёный.

## 8. Пост-фактум PR-2 (2026-07-06): честная метрика ретрофита — НОЛЬ

Ретрофит существующих паков дал 6×`core.Named` (net 0 строк) и НОЛЬ замен
Assignable/Contact/Period: сырой замер §Мотив считал ИМЕНА полей, а не пары
с точными типами/модификаторами. Факты: `owner`(14) и `assignee`(8) ни разу
не встречаются ВМЕСТЕ на одной entity; email/phone в паках — богатые типы
`email`/`phone`, не `string`; пары from/to — не в начале entity или в event.
Выводы (обязательны к соблюдению):
- ценность миксинов — ФОРВАРДНАЯ (новые паки/пресеты L2), не ретрофит;
- НЕ добавлять новые миксины и не менять состав v1 без доказанного
  потребителя «вживую», а не по grep-замеру (урок этого раздела);
- кандидат на пересмотр при первом реальном потребителе: Contact с типами
  `email`/`phone` вместо `string` (реальные паки используют богатые типы).
