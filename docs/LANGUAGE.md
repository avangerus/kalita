# LANGUAGE — как правильно построен язык kalita

Дата: 2026-07-03. Статус: выведенное понимание (сессия проектирования языка).
Это описание ЦЕЛЕВОГО языка. Текущий DSL (DSL-SPEC) сходится к нему итерациями.
Родители: ARCHITECTURE.md (якорь), DSL-CORE-LIB.md (устав core), LLD-19 (слои).
Проверено столкновением с тремя независимыми внешними дизайнами (Agentic
Workbench, ESL v1.0, EOM DSL 1.0) — ядро сошлось у всех, дельта учтена ниже.

---

## 0. Зачем язык (старше всех правил)

Язык kalita — НЕ язык моделирования и не конфиг. Это **ревью-поверхность,
которая держит ИИ-агента честным**: агент строит систему, человек ЧИТАЕТ и
ПОДПИСЫВАЕТ контракт. Ценность языка — в читаемости и запечатанности, не в
мощи автора. Легибельность — несущая конструкция, не удобство.

## 1. Один инвариант (из него выводится всё)

> **В любой момент человек может: (1) прочитать весь контракт за один присест,
> (2) доказать, что произошло, (3) откатить любое действие.**

Граница языка — НЕ линия, проведённая раз, а давление: любой кандидат (слово,
конструкция, поле) допускается вопросом «инвариант ещё держится?». Полезность —
не аргумент.

- читаемо-всегда → бюджет легибельности: словарь мал и закрыт, код дорог и помечен;
- доказуемо-всегда → журнал событий + детерминированный replay + действие только
  по выданному полномочию;
- обратимо-всегда → у каждого эффекта есть обратный; необратимое — только через
  явный человеческий гейт.

## 2. Три страты (кто чем владеет)

| Страта | Что | Владелец | Судьба |
|---|---|---|---|
| **Намерение** | цели/политики почти естественным языком | человек+агент (диалог) | не исполняется напрямую |
| **Контракт** | ЭТОТ язык: состояние, полномочия, инварианты, команды, события | **человек** (читает, подписывает) | версионируется, живёт годами |
| **Исполнение** | UI, механика, реализация агентов, код | машина (генерится) | одноразово, пересобираемо |

Путь: воображение →(ИИ)→ намерение →(ИИ)→ контракт →(ЧЕЛОВЕК: ревью+подпись)→
→(детерминизм)→ система →(события)→ журнал →(diff)→ эволюция.
Каждый ИИ-шаг зажат между детерминированными/человеческими чекпойнтами.
Доверие устанавливается ОДИН раз и в одном месте — на ревью контракта.

## 3. Один закон изменений: команда→факт

Свободного CRUD нет. Мир меняется только **именованной командой**, записанной
**фактом** (append-only журнал, hash-chain). CRUD = предустановленные команды
(create/update/delete), они ЗАПЕЧАТАНЫ — в них нельзя навалить логику; человек
их не читает, он им доверяет. Переопределение встроенного — громкий именованный
акт (`overrides`), отдельно ревьюится.

Двое ворот вокруг любой команды:
```
команда → [ворота 1: контракт входа] → логика (декларативная ИЛИ handler)
        → [ворота 2: права + инварианты домена] → факт в журнал (или error-факт, I-3)
```
Handler ПРЕДЛАГАЕТ (возвращает факт/вердикт), домен РЕШАЕТ. Правила живут в
домене, видимые глазами — не в коде (анти-anemic-model, анти-ServiceNow).

Два вида событий, не путать:
- **факт команды** — пишется всегда и молча, имя от команды (Promote→Promoted),
  автор его НЕ объявляет; нужен для аудита/replay/отката;
- **сигнал** (`emit Имя`) — факт, нарочно выставленный наружу для подписчиков.

Где живёт команда: **субъект решает место** (один аггрегат → у сущности;
ноль/много → у модуля, но только как тонкий оркестратор per-aggregate команд);
**сложность решает форму** (декларативно или handler). Две независимые оси.

## 4. Граница язык / код

Всё логическое — это ASK (вопрос) или CHANGE (изменение).

**ASK в языке**, если чисто и тотально (уровень формулы Excel/CEL): чтение полей,
навигация по ref, сравнения, and/or/not, ограниченные агрегаты
(count/sum/exists/min/max), условное значение. Всегда завершается, ничего не делает.
**ASK в коде** (`check`), если: внешний вызов, семантика/ИИ, безграничный поиск.

**CHANGE в языке**, если это конечная сборка ЗАПЕЧАТАННЫХ глаголов:
`set · create · notify · emit · assign · call <команда>` с ASK-аргументами,
без циклов по набору. **CHANGE в коде** (`handler`), если: цикл, многошаг
с решениями, внешний вызов, вычисление отсутствующего в данных.

Тест одной фразой: *«ответ/действие уже лежит в данных и достижим нашими
глаголами без шагов → язык; надо ВЫЧИСЛИТЬ, СХОДИТЬ наружу или ПЕРЕБРАТЬ → код».*

Контракт кода: короткая функция про одно; вход — запись + read-only ctx;
выход — факт или вердикт; прямой записи в хранилище НЕТ. Длинный/широко-лезущий
handler — флаг на ревью (гейт сложности — обязателен, не пожелание).

Принцип выражений: **не изобретать свой язык выражений** — семантика равна
существующему bounded-языку (CEL-класс: детерминированный, sandboxed, без
сайд-эффектов). Взято из ESL-ревью.

## 5. Лексикон (~10 слов, закрытый)

СТРУКТУРА
- `entity` — вещь: поля, типы, связи, инварианты, flow, реакции — всё в одном месте
- `reference` — справочник TURNKEY: key/display/seed → автоматом пикер, права
  (все читают / стюард пишет), без дублей, архив вместо удаления, история.
  Bool — для флага; enum — для технических малых множеств; reference — для
  бизнес-настраиваемых справочников (подтверждено всеми внешними ревью)
- типы: text int money date bool enum[…] ref[…] file (+geo)
- модификаторы: required · unique [where …] · = default · = computed

ПОВЕДЕНИЕ
- `flow` — жизненный цикл: `из -> в : команда [guard …] [requires approval(Роль)]`
- `command` — именованное изменение вне flow
- `before <команда>` — проверка-ворота (формула или `check <handler>`)
- `after <команда>` — реакция (запечатанные глаголы или handler)
- `emit` — выставить факт наружу
- `invariant` / `validate` — что всегда истинно (в домене, глазами)

УПРАВЛЕНИЕ
- `role` — полномочия человека: глагол + сущность/поле + where (ABAC,
  default-deny, deny>allow)
- `agent` — актор-агент: brief + `can` (закрытый список полномочий) +
  `autonomy` по уровням риска (auto/approval/forbidden) + бюджет/анти-каскад (§7)

ESCAPE
- `handler` / `check` — маркер «здесь код» (Python-воркер), в слотах
  before/after/command

СЦЕНАРИИ (обязательная часть контракта — взято из ESL-ревью)
- `scenario` — Given/When/Then на командах. Читается человеком И исполняется
  (replay-механика уже есть). Пак без сценариев на аггрегат не деплоится:
  ревьюер подписывает не только структуру, но и поведение на примерах.

Каждая команда несёт `risk` (low/medium/high/critical); autonomy агента
определяется риском действия, не перечислением.

## 6. Чего в языке НЕТ (и почему — по инварианту)

- **UI/Screen/View-язык** — платформа рисует сама из закрытого реестра
  (LLD-14/15, I-6). Опционально: именованный фильтр `view X = Entity where …`.
  Ручные Screen-декларации (EOM-стиль) отвергнуты: это работа машины.
- **`fact` как конструкт** — факт выводится из команды автоматически.
- **`subscription`/`sink`/`automation`-блоки** — растворены в `after`/`emit`
  (durable-механика LLD-21 — под капотом).
- **storage-хинты, индексы, materialized views** — механизм исполнения, не
  контракт. Оптимизация живёт в L0/runtime.
- **циклы, функции, произвольный поток управления** — по определению (§4).
- **45-сущностная онтология** (EOM-стиль) — runtime-механика (WorkItem,
  ProcessInstance, ReadModel, AgentRun) остаётся ПОД капотом ядра, в языке ей
  не место. Язык — то, что человек читает; движок — то, чему он доверяет.
- **Отказ от event sourcing** (ESL-стиль «audit+outbox достаточно») — отвергнут:
  без replay нет «доказуемо», без событийного субстрата дорого «обратимо».

Открытый вопрос (кандидат ×3 внешних ревью): **WorkItem** — единая очередь
работы для людей и агентов как примитив. Оценивается по инварианту; пока
покрывается entity+flow+assignee.

## 7. Агент в языке (дельта агентной эры)

Агент — актор первого класса, симметричен человеку (то же choke point, тот же
журнал), но с дополнительной governance-обвязкой:
- **полномочия** — закрытый allow-список действий (`can`), всё остальное
  запечатано; и запрет-список для явности критичного;
- **автономия по риску** — low:auto / medium:approval / high:approval|forbidden /
  critical:forbidden;
- **предложение перед мутацией** — рискованное действие агента = proposal,
  человек утверждает (наш pending-intent);
- **бюджет и анти-каскад** (взято из EOM-ревью): лимит стоимости/запусков,
  глубина причинной цепочки (causal depth), запрет самотриггера
  (агент А → задача агенту А), on-limit → блок + супервизор. Журнал уже несёт
  causality — механика дешёвая, дыра реальная (cascading failures, NIST);
- **в аудите агента**: версия брифа/скилла, модель, confidence,
  proposed vs executed actions.

## 8. Два тира + admission gate

- **base** — весь декларативный словарь §5. Сломать нельзя, читают все.
- **extended** — handler/check, реализация агентов, федерация. Технический гейт:
  extended-конструкты отвергаются компилятором, пока владелец узла явно не
  включил режим (сертификация/партнёрство — бизнес-слой поверх).

Admission gate нового слова: узнаваемое бизнес-существительное? кросс-вертикально?
стабильно? примитив, не решение? — иначе НЕ добавлять. Кастомная логика —
всегда воркер, никогда новая грамматика. Предпочитать вычитание
(Salesforce убил 2 из 3 способов автоматизации — вот дисциплина).

## 9. Ревью-поверхность (стадия подписи)

Дифф контракта компилируется в **Impact Analysis** для человека (взято из
ESL-ревью): «изменится API, добавится поле, роль X получит доступ к Y» — а не
сырой дифф. Плюс прогон сценариев (§5) на диффе. Подпись человека — единственная
точка установления доверия; всё до неё — ИИ, всё после — детерминизм.

## 10. Как язык эволюционирует

Не от хотелок и не от чужих роадмапов — от боли реального пака через процедуру:
requirement → выразимо декларативно? / нужен новый запечатанный глагол? /
это код? / это дыра семантической модели? Язык меняется только когда пак
вскрывает дыру МОДЕЛИ (как reference и field-mixin), и каждый кандидат проходит
инвариант §1 и гейт §8. Проверка жизнеспособности: на одном ядре собираются
Helpdesk, Jira-like, KnowVault, CRM-lite (+ наш beachhead Legal).

## Приложение: канонический пример (Helpdesk, суть языка на одном экране)

```dsl
reference Category:
  code: string key
  name: string display
  seed: TECH "Техническая", BILL "Оплата"

entity Ticket:
  title:     string required
  requester: ref[Customer] required
  category:  ref[Category]
  priority:  enum[low, normal, high, critical] = normal
  assignee:  ref[User]
  status:    enum[new, triaged, assigned, resolved] = new

  invariant: resolved implies assignee != none

  flow:
    new      -> triaged  : classify   risk low
    triaged  -> assigned : assign     risk medium
    assigned -> resolved : resolve    risk high  requires approval(Lead) when priority = critical

  command checkSla: handler sla_check            # код — помечен, короткий, про одно
  after checkSla: notify(assignee, "SLA под угрозой") when sla.at_risk
  after resolve:  emit TicketResolved(ticket)

role Operator:
  read, update Ticket where assignee = me

agent TriageBot:
  brief: "Определи категорию и приоритет по тексту"
  can:   read Ticket, run classify
  autonomy: { low: auto, high: forbidden }
  budget: { daily_runs: 500, causal_depth: 3 }

scenario "critical требует одобрения":
  given Ticket(priority: critical, status: assigned, assignee: bob)
  when  resolve by bob
  then  approval required from Lead
```

Что видит ревьюер за минуту: данные, процесс с рисками, кто (человек/агент)
что может, где код, и подписанное поведение на примере. Это и есть язык.
