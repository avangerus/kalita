# LANGUAGE 0.9 — как правильно построен язык kalita

Дата: 2026-07-03. Статус: 0.9 — философия и ядро выведены, контрактные дыры
закрыты по итогам пяти внешних ревью (Agentic Workbench, ESL v1.0, EOM DSL 1.0,
два ревью этого документа). НЕ финал: до 1.0 — обкатка на паках (§10).
Родители: ARCHITECTURE.md (якорь), DSL-CORE-LIB.md, LLD-19 (слои).
Это ЦЕЛЕВОЙ язык; текущий DSL (DSL-SPEC) сходится к нему итерациями.

## 0. Зачем язык (старше всех правил)

Язык kalita — НЕ язык моделирования и не конфиг. Это **ревью-поверхность,
которая держит ИИ-агента честным**: агент строит систему, человек ЧИТАЕТ и
ПОДПИСЫВАЕТ контракт. Ценность языка — в читаемости и запечатанности, не в
мощи автора. Легибельность — несущая конструкция, не удобство.

## 1. Один инвариант (из него выводится всё)

> **В любой момент человек может:**
> **(1) прочитать контракт одного аггрегата — и impact любого изменения —
> за один присест** (весь контракт — навигируем, не «читается залпом»);
> **(2) доказать, что произошло — и почему НЕ произошло — по подписанному
> контракту и журналу;**
> **(3) откатить обратимое, компенсировать компенсируемое; некомпенсируемое
> исполняется только через явный человеческий гейт с evidence.**

Граница языка — НЕ линия, проведённая раз, а давление: любой кандидат (слово,
конструкция, поле) допускается вопросом «инвариант ещё держится?». Полезность —
не аргумент.

- читаемо → бюджет легибельности: словарь мал, код дорог и помечен, дифф
  компилируется в человеческий impact (§9);
- доказуемо → журнал (hash-chain) + детерминированный replay + действие только
  по выданному полномочию + отказ тоже факт (I-3);
- обратимо → три класса эффектов: reversible (откат), compensable
  (`compensate`), irreversible (`irreversible` + гейт + evidence). Обещание
  «откатить всё» — ложь; честная триада — контракт.

## 2. Три страты и объект подписи

| Страта | Что | Владелец | Судьба |
|---|---|---|---|
| **Намерение** | цели/политики почти естественным языком | человек+агент (диалог) | не исполняется напрямую |
| **Контракт** | ЭТОТ язык | **человек** (читает, подписывает) | версионируется, живёт годами |
| **Исполнение** | UI, механика, реализация агентов, код | машина (генерится) | одноразово, пересобираемо |

Путь: воображение →(ИИ)→ намерение →(ИИ)→ контракт →(ЧЕЛОВЕК: ревью+подпись)→
→(детерминизм)→ система →(события)→ журнал →(diff)→ эволюция.
Каждый ИИ-шаг зажат между детерминированными/человеческими чекпойнтами.

**Подпись — не философия, а объект**: contract snapshot = {версия, hash,
кто подписал, когда, сценарии прошли, impact принят} — фактом в журнал.
(Механика уже есть: definition.proposed + approval + подписанные чекпойнты;
здесь она возводится в контрактное понятие.)

**Допуск устанавливается на ревью; доверие ПОДДЕРЖИВАЕТСЯ непрерывно**:
runtime-аудит, сценарии на диффе, метрики агентов, отзыв автономии (§7).
Смена модели/handler'а/брифа = новая версия = новый дифф на подпись.

## 3. Один закон изменений: команда→факт

Свободного CRUD нет. Мир меняется только **именованной командой**, записанной
**фактом** (append-only журнал, hash-chain). CRUD = предустановленные команды
(create/update/delete), они ЗАПЕЧАТАНЫ — в них нельзя навалить логику.
Переопределение встроенного — громкий именованный акт (`overrides`), отдельно
ревьюится.

Двое ворот:
```
команда → [ворота 1: контракт входа] → логика (декларативная ИЛИ handler)
        → [ворота 2: права + инварианты домена] → исход фактом
```
**Четыре исхода, все — фактами** (доказуемо и «почему не сработало»):
- applied — применена, изменения записаны;
- rejected — не прошла ворота (вход/права/инвариант) — error-факт с правилом;
- failed — handler/внешнее упало — error-факт;
- pending — ждёт approval (HITL) — факт ожидания, затем applied/rejected.

Handler ПРЕДЛАГАЕТ (возвращает факт/вердикт), домен РЕШАЕТ. Правила живут в
домене, видимые глазами — не в коде.

Два вида событий:
- **факт команды** — пишется всегда, имя от команды (Promote→Promoted), автор
  его НЕ объявляет;
- **сигнал** (`emit Имя`) — факт, нарочно выставленный наружу для подписчиков.

Где живёт команда: **субъект решает место** (один аггрегат → у сущности;
ноль/много → у модуля, только как тонкий оркестратор per-aggregate команд);
**сложность решает форму** (декларативно или handler). Две независимые оси.

Классы эффектов на команде: по умолчанию reversible; `compensate <команда>` —
объявленная компенсация; `irreversible` — требует человеческий гейт, журнал
хранит evidence (кто видел, что подтвердил).

## 4. Граница язык / код

Всё логическое — ASK (вопрос) или CHANGE (изменение).

**ASK в языке**, если чисто и тотально (класс CEL/формулы Excel): чтение полей,
навигация по ref, сравнения, and/or/not, ограниченные агрегаты
(count/sum/exists/min/max), условное значение. **ASK в коде** (`check`):
внешний вызов, семантика/ИИ, безграничный поиск.

**CHANGE в языке** — конечная сборка ЗАПЕЧАТАННЫХ глаголов:
`set · create · notify · emit · assign · call <команда>` с ASK-аргументами,
без циклов. **CHANGE в коде** (`handler`): цикл, многошаг с решениями,
внешний вызов, вычисление отсутствующего в данных.

Тест: *«ответ/действие уже лежит в данных и достижим нашими глаголами без
шагов → язык; надо ВЫЧИСЛИТЬ, СХОДИТЬ наружу или ПЕРЕБРАТЬ → код».*

**Контракт кода — enforceable manifest, не пожелание:**
```dsl
handler sla_check@1:
  input: Ticket
  ctx:   read[SlaPolicy, core.Calendar]     # что можно читать
  output: verdict                            # или fact
  deterministic: true                        # false → external[...], помечен
  timeout: 2s
```
Handler не может: писать в хранилище, звать команды в обход домена, менять
права, эмитить факты напрямую, читать вне объявленного ctx. Версия (`@1`)
обязательна — replay без версий недоказуем.

**Против «handlers съедят язык» — давление, не богатый формульный DSL** (тот
путь ведёт в YAML-программирование): доля и размер handler'ов — метрика на
ревью-поверхности; повторяющийся handler-паттерн — кандидат в запечатанный
глагол через admission gate (§8). Язык растёт вычитанием кода, не сложением
грамматики.

Принцип выражений: не изобретать свой язык — семантика равна существующему
bounded-языку (CEL-класс). **Читаемый синтаксис — surface; каноническая форма —
типизированный AST** (компилятор видит точную структуру: verb/entity/fields/
where). Дифф, impact analysis и policy-валидация работают по AST, не по тексту.

## 5. Лексикон (малый, закрытый; критерий — §8)

СТРУКТУРА
- `entity` — вещь: поля, типы, связи, инварианты, flow, реакции — в одном месте
- `reference` — справочник TURNKEY: key/display/seed → автоматом пикер, права
  (все читают / стюард пишет), без дублей, архив вместо удаления, история.
  Минимальный по конструкции: иерархия = ref на себя; локализация/scoped —
  за триггером. Bool — флаг; enum — технические малые множества; reference —
  бизнес-настраиваемые справочники
- типы: text int money date bool enum[…] ref[…] file (+geo)
- модификаторы: required · unique [where …] · = default · = computed ·
  `sensitive` (PII-маркер, LLD-16: crypto-shredding, маскирование, retention —
  контракт ответственности, не хранение)

ПОВЕДЕНИЕ
- `flow` — жизненный цикл: `из -> в : команда [guard …] [requires approval(Роль)]`
- `command` — именованное изменение вне flow; классы эффектов:
  `[irreversible] [compensate <команда>]`; вход человека — контракт
  (`input: resolution required, comment optional` — что человек ОБЯЗАН увидеть
  и заполнить; не UI, а interaction contract)
- `before <команда>` — проверка-ворота (формула или `check <handler>`)
- `after <команда>` — реакция (запечатанные глаголы или handler)
- **время — тоже контракт**: `when <расписание>: run <команда>` и
  `after X: in <срок> run <команда> unless <условие>` — SLA, сроки, эскалации
  ЧИТАЮТСЯ, не прячутся в код (durable-механика — под капотом, LLD-21)
- `emit` — выставить факт наружу
- `invariant` / `validate` — что всегда истинно (в домене, глазами)

УПРАВЛЕНИЕ
- `role` — полномочия человека: глагол + сущность/поле + where (ABAC,
  default-deny, deny>allow)
- `agent` — актор-агент (§7)

ESCAPE
- `handler` / `check` — маркер «здесь код», с манифестом §4

СЦЕНАРИИ (обязательная часть контракта)
- `scenario` — Given/When/Then на командах; читается человеком И исполняется
  (replay-механика). Пак без сценариев на аггрегат не деплоится. Типы покрытия:
  happy · guard · approval · forbidden · compensation (+ agent-proposal).
  Сценарии участвуют в impact analysis: изменение flow показывает, какие
  подписанные сценарии затронуты.

Каждая команда несёт `risk` (low/medium/high/critical).

## 6. Чего в языке НЕТ (и почему — по инварианту)

- **UI/Screen/View-язык** — платформа рисует сама из закрытого реестра
  (LLD-14/15, I-6). Что человек ОБЯЗАН увидеть на действии — не UI, а
  `input`-контракт команды (§5). Опционально: `view X = Entity where …`.
- **`fact` как конструкт** — выводится из команды автоматически.
- **`automation`/`subscription`-блоки** — растворены в `after`/`when`/`emit`;
  durable-доставка, retry, идемпотентность, DLQ — механика ядра (LLD-21).
- **storage-хинты / индексы / matview** — механизм. На нашем масштабе платформа
  индексирует сама; capability-аннотации (queryable/reportable) — только по
  триггеру производительности, через gate.
- **циклы, функции, произвольный поток управления** — по определению (§4).
- **большая онтология (45 сущностей EOM-стиля)** — runtime-механика
  (ProcessInstance, ReadModel, AgentRun) живёт ПОД капотом. **WorkItem —
  признан runtime-примитивом** (единая очередь работы людей и агентов; approval,
  proposal-review, эскалация — его виды), но в языке он выражается глаголами
  (`assign review to Lead when …`), не keyword'ом.
- **multi-tenancy** — узел kalita single-tenant в контуре клиента BY DESIGN
  (продуктовый тезис, не пробел).
- **bulk-операции** — модульная команда-оркестратор поверх идемпотентных
  per-aggregate команд; отдельный примитив — за триггером.
- **Отказ от event sourcing** — отвергнут; механика проработана в LLD:
  эры/upcast и golden replay (LLD-03), снапшоты = подписанные чекпойнты
  (LLD-01), забвение/retention при неизменном hash-chain (LLD-16),
  DR/якорь (LLD-17). Temporal-запросы («состояние на дату») — производные
  журнала от ближайшего чекпойнта.
- **миграция с legacy** — честный пробел уровня платформы (не языка):
  паттерн — mirror-by-events как strangler; отдельный LLD по триггеру
  первого brownfield-клиента.

## 7. Агент в языке

Агент — актор первого класса, симметричен человеку (тот же choke point, тот же
журнал), с governance-обвязкой:

- **полномочия** — закрытый allow-список (`can`), всё остальное запечатано;
- **автономия — условная политика, не 4 константы** (та же ABAC-механика
  `where`, что у ролей):
  ```dsl
  autonomy:
    assign: auto when confidence > 0.85 and customer.tier != vip, else propose
    resolve: propose                       # всегда через человека
    external_send: forbidden
  revoke: autonomy when rejection_rate > 20% over 7d   # доверие поддерживается
  ```
- **предложение перед мутацией** — рискованное действие = proposal (наш
  pending-intent), человек утверждает; **отклонённый/исправленный proposal
  ОБЯЗАН породить feedback-факт** (причина, коррекция) — иначе контроль
  одноразов и ничему не учит (eval-датасет, метрики супервизора);
- **бюджет и анти-каскад**: лимиты запусков/стоимости, глубина причинной
  цепочки, запрет самотриггера, on-limit → блок + супервизор;
- **версии — часть контракта**: `brief: triage@3`, `model: profile fast-local@2`,
  handler@N — replay и «что именно было подписано» без версий недоказуемы;
- **в аудите**: версии, confidence, proposed vs executed actions.

## 8. Два тира + admission gate

- **base** — весь декларативный словарь §5; читают все, сломать нельзя.
- **extended** — handler/check, реализация агентов, федерация. Технический гейт:
  компилятор отвергает extended, пока владелец узла явно не включил режим.

Admission gate нового слова — не «слово №11 запрещено», а критерий:
> **новое слово допускается, только если оно УМЕНЬШАЕТ суммарный объём
> контракта и ПОВЫШАЕТ ревьюируемость** (плюс: бизнес-существительное,
> кросс-вертикально, стабильно, примитив — DSL-CORE-LIB §2).

Кастомная логика — всегда воркер, никогда новая грамматика. Предпочитать
вычитание. Словарь честно называется «закрытый с governed-ростом»: изменения
словаря — редкие, через gate, зафиксированные (RFC-процедура), не дрейф.

## 9. Ревью-поверхность (стадия подписи)

Дифф контракта компилируется в **Impact Analysis** для человека: «роль X
получит доступ к sensitive-полю Y; затронуты интеграции A,B; затронуты
подписанные сценарии S1,S3; изменение необратимого действия Z» — не сырой
дифф. Ревью многоуровневое: компилятор/валидаторы (автоматически) → impact →
человек подписывает. Подпись = contract snapshot (§2). Против rubber-stamping
работает малость диффа (аддитивная эволюция) — подписывается изменение,
не мир.

## 10. Как язык эволюционирует

Не от хотелок и не от чужих роадмапов — от боли реального пака:
requirement → выразимо декларативно? / нужен новый запечатанный глагол? /
это код? / это дыра семантической модели? Язык меняется только когда пак
вскрывает дыру МОДЕЛИ, каждый кандидат проходит §1 и §8.
Метрика здоровья: доля контракта в декларативе vs handler'ах — публична на
ревью; рост доли кода = сигнал дыры языка, а не повод писать больше кода.
Проверка жизнеспособности 1.0: на одном ядре собираются Helpdesk, Jira-like,
KnowVault, CRM-lite (+ beachhead Legal), и их контракты проходят ревью
живым человеком за разумный присест.

## Приложение А: канонический пример (Helpdesk)

```dsl
reference Category:
  code: string key
  name: string display
  seed: TECH "Техническая", BILL "Оплата"

entity Ticket:
  title:     string required
  requester: ref[Customer] required
  category:  ref[Category]
  priority:  enum[low, normal, high, critical] = normal
  assignee:  ref[User]
  status:    enum[new, triaged, assigned, resolved] = new

  invariant: resolved implies assignee != none

  flow:
    new      -> triaged  : classify   risk low
    triaged  -> assigned : assign     risk medium
    assigned -> resolved : resolve    risk high  requires approval(Lead) when priority = critical

  command resolve:
    input: resolution required, comment optional   # что человек обязан увидеть

  after assigned: in 2h run checkSla unless resolved   # время — контракт
  when daily 09:00: run checkSla

  command checkSla: handler sla_check@1
  after checkSla: notify(assignee, "SLA под угрозой") when sla.at_risk
  after resolve:  emit TicketResolved(ticket)

role Operator:
  read, update Ticket where assignee = me

scenario "critical требует одобрения":          # happy/approval
  given Ticket(priority: critical, status: assigned, assignee: bob)
  when  resolve by bob
  then  approval required from Lead
```

## Приложение Б: агентный пример (proposal-механика — центр агентной эры)

```dsl
agent TriageBot:
  brief: triage@3
  model: profile fast-local@2
  can:   read Ticket, run classify, run assign
  autonomy:
    classify: auto
    assign:   auto when confidence > 0.85 and requester.tier != vip, else propose
  budget: { daily_runs: 500, causal_depth: 3 }
  revoke: autonomy when rejection_rate > 20% over 7d

scenario "бот предлагает назначение VIP":       # agent-proposal
  given Ticket(status: triaged, requester.tier: vip)
  when  assign by TriageBot to alice
  then  proposal created
  and   approval required from Lead

scenario "бот не может закрыть":                 # forbidden
  given Ticket(status: assigned)
  when  resolve by TriageBot
  then  rejected by permission
```

Что видит ревьюер: данные, процесс с рисками и временем, кто (человек/агент)
что может и при каких условиях, где код и его манифест, что необратимо, и
подписанное поведение на примерах — включая границы агента. Это и есть язык.
